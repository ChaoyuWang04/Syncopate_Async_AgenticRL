# `docs/upstream/` · 上游提交线的维护守则

> 这个文件夹放**要提给上游开源项目的东西**（verl / PyTorch / NCCL …）。
> 它不是实验记录——实验记录在 `../infra_exp/E*.md`，这里只放**对外要说的话和要交的代码**。
>
> 分工：**infra 负责人**在真实训练里撞到问题、自己查清并修好 → 按 §3 的模板落成一个
> `DRAFT-` 包 → **Claude** 做上游考据、按对方模板成稿、备好可推分支 → **Chaoyu** 点头后提交。

---

## 1 · 文件夹命名 = 状态（一眼看清）

```
DRAFT-<主题>     infra 负责人已交发现，**Claude 还没做上游考据**；不许提交
READY-<主题>     材料齐备、按 §2 自检全过，**等 Chaoyu 点头**
OPEN-<主题>      已提交（issue/PR 在飞），等 CI / review
MERGED-<主题>    已合入 —— 保留，它是「这条线做完了」的证据
CLOSED-<主题>    被拒/被关，**不删**：写清为什么被拒，下次别再撞同一堵墙
PARKED-<主题>    我们主动决定不提（例如影响面太窄），写清判断依据
```

改状态就 `git mv` 改前缀，**同时**把包内 README 第一行的状态句改掉，两处必须一致。
⚠️ 改名后跑一次 `grep -rn "<旧名>" docs/` 把交叉引用补上。

## 2 · 一个「合格的待提交包」必须有什么

`READY-` 之前，下面每一项都要在：

| 文件 | 内容 | 判据 |
|---|---|---|
| `README.md` | 状态句 · 一句话结论 · 文件清单 · 证据指针 · 提交前清单 | 别人不看别的文件也知道这是什么 |
| `analysis.md` | 中文证据链：触发条件 / 根因（**带行号和版本**）/ 后果 / 修法论证 / 被否决的方案 | 推翻过的想法**就地留着示错**，不删 |
| `submission-EN.md` | 上游要粘贴的英文正文（issue + PR，**按对方模板分好节**） | 复制即可用，无占位符残留 |
| `*.patch` 或分支 | 可直接 `git apply` / 已推的分支 | 基于上游 **main**，非我们的旧版本 |
| 复现脚本 | 依赖越少越好（纯 PyTorch > 依赖 verl > 依赖我们的仓库） | **与 issue 里内联的那份逐字相同** |
| 测试 | 按上游的测试约定写（目录/风格/注册方式） | **实弹验证过修前红、修后绿** |

### 2.1 提交前自检（每一条都要能指出证据，不能靠印象）

```
□ 上游考据：搜过 issue+PR（贴查询链接与命中数）· 确认 main 上问题仍在（源码逐字核对）
□ 有没有人修过：有没有被关掉的同类 PR？为什么被关？我们的定位要不要跟着换
□ 声明审计：正文里每个数字都能指到"哪次跑、哪个产物文件"；推断句必须标 [推断]
□ 判据验负例：测试在修复前**确实红**，且红在**行为**上（不是只红在配置断言上）
□ 按对方模板逐条执行：不是照抄章节标题，是**真的把每一步做掉**（见 §4）
□ 内部信息扫描：无我们的路径、实验代号、邮箱、内部文档名
```

## 3 · 给 infra 负责人的模板（写完直接建 `DRAFT-<主题>/README.md`）

> 目标：让 Claude 能**不问你问题**就接着做考据和成稿。
> 原则：**能贴实测就别写形容词**；不确定的地方**明写"未验证"**比含糊过去有用得多。

```markdown
# 提交包 · <一句话标题>（E<编号>）

> **状态：问题描述 + 修改范围。** 待 Claude 考据后成稿。
> 目标仓库：<verl-project/verl | pytorch/pytorch | …>
> 类型：<bug report | feature request>
> 我们钉死的版本：<verl 0.8.0 / torch 2.9.0 …>

## 一句话
<现象 + 后果。如果是静默失败，一定要写"不报错/指标正常"。>

## 触发条件（最小配置）
```yaml
<能让别人复现的最小配置片段>
```
<谁会撞上？是默认配置就会撞，还是要一个特定组合？>

## 根因（带行号与版本）
| 位置 | 现状 |
|---|---|
| `<file.py>::<func>`（~L<n>） | <它做了什么，为什么错> |
<★ 分清「读码得到的事实」与「据此的推断」，推断句标 [推断，未验证]。>

## 判据（怎么知道它错了）
```
修复前   <实测输出/数字>
修复后   <实测输出/数字>
```
<判据要落在**行为**上（梯度是否相同、载荷含不含 X），不是落在配置上。>

## 证据（指到具体产物）
```
logs/<...>                 <这份日志证明什么>
_audit/infra/<...>.json    <机器可读产物>
scripts/<...>.py           <复现脚本；说明它依赖什么：纯 PyTorch？要 verl？要我们的仓库？>
```

## 我们本地的修法
<diff 或 monkeypatch 位置。如果和上游可能的做法不同，说明为什么。>

## 影响面
<多少人会踩？失败是静默还是报错？我们付了多少代价（时间/白跑的实验）？>

## 我们验过什么 / 没验过什么
```
✅ 验过：<...>
⬜ 没验：<...>          ← 这一栏空着比写错更糟，一定要填
```

## 我知道的上游情况（可选，Claude 会重查）
<搜过的 issue/PR 编号、维护者说过什么。没搜过就写"没搜过"。>
```

### 3.1 什么样的发现值得提上游

```
✅ 值得   静默的正确性问题（不报错、指标正常，但结果是错的）—— 优先级最高
✅ 值得   上游 main 上仍然存在，且我们有可复现的判据
✅ 值得   普适性论证成立：不是只有我们这种配置会撞
🟡 看情况 性能问题：要能给出端到端数字，不能只有微基准
⛔ 不提   我们自己配置错了 / 只影响我们的特殊改动 / 上游已修
```

## 4 · Claude 的工作准则（这些都是付过学费才写下来的）

**① 先考据，再动笔。** 每个包动手前必须回答：上游有没有人报过？有没有被关掉的同类 PR？
main 上还在不在？—— 包①差点以"没人提过"的框架提交，实际上 PyTorch 那条**已被确认并关成
not_planned**；包④差点以"从未接上"提交，实际是**重构回归、且修复 PR 刚被维护者关掉**。
**定位错了，整份材料的说服力会当场归零。**

**② 按对方模板"执行"，不是"照抄"。** 模板里的每一条都要真做：
说 `pre-commit run` 就真跑（包①第一次只跑了 ruff 就打了勾，补跑后是 **14 个钩子**，
其中 mypy 和 autogen-trainer-cfg 从没跑过）；说"贴一个相似 PR 的查询链接"，
就要确认那个链接**真能返回东西**（第一版只命中我们自己刚提的 issue）。

**③ 声明不能超出证据。** 写"在两种配置下都验证过"之前，数一数**真的探过几个**
（包①写了 "both configurations"，实际只探了修复后的两档）。

**④ 内联的脚本必须真跑过，且它的输出就是正文里的那张表。** 包①的 issue 里那段复现脚本
最初从没跑过，而表里的数来自**另一个脚本**（模型/损失/种子都不同）——看起来有出处，
其实对不上。**现在的规矩：脚本存成仓库文件 → 跑它 → 用它自己的输出填表 → 内联版与仓库版逐字相同。**

**⑤ 判据要验负例，而且要红在行为上。** 包①的测试第一版在**配置断言**上就红了，
根本没走到梯度那步 —— 那只证明了配置、没证明行为。已改成行为判据在前、机制判据在后。

**⑥ 提交前把话说死。** 向 Chaoyu 报"准备好了"之前，§2.1 自检逐条过一遍，
**并说清哪些是实测、哪些是推断、哪些没测**。

## 5 · 提交流程（verl 为例，走过一遍的实操）

```
1. issue      https://github.com/verl-project/verl/issues/new/choose → Bug report
              ⚠️ 是**结构化表单**（System Info / Reproduction / Expected behavior），不能整篇贴
              System Info 要跑 `python scripts/diagnose.py`，**在干净的上游 main 上跑**
              （在我们分支上跑会打出上游不存在的 commit hash）
2. fork       网页点一次即可；四个包共用同一个 fork（SSH 密钥已绑账号，无需 token）
3. push       cd /workspace/_upstream/verl && git push fork <branch>
4. PR         标题 `[{模块}] {类型}: {描述}`（CI 会检查格式）；正文按 PULL_REQUEST_TEMPLATE 六节
5. CLA        PR 开完机器人会留言 → 点链接签（DCO 已由 commit 的 Signed-off-by 满足）
6. CI         ⚠️ **Slack 进不去**（限 anyscale/bytedance/together.ai 域名）⇒ 走**飞书群**申请
7. 收尾       把 PR 编号写回包内 README，`git mv` 改前缀 `READY-` → `OPEN-`
```

⚠️ **commit 必须带 `-s`**（DCO）；分支基于**上游 main**，不是我们的旧克隆。

## 6 · 被 `wontfix` 之后怎么办（2026-08-20 用包① 换来的）

**发生了什么**：包① 从提交到被关只有 **44 分钟**，维护者打 `wontfix` 标签、关 PR、连带关 issue，
**没有留任何评论**。同一个维护者关掉过 #7202（包④要引用的那个 PrefixGrouper 复活 PR），
那次至少给了一句理由。

### 6.1 先分清三件事，别急着改材料

```
① 材料错了吗？        —— 证据链/复现/测试/验证是否仍然成立（包① 全部成立）
② 定位错了吗？        —— 我们主张的"该谁修"对不对
③ 对方的策略变了吗？  —— 例如"这个子系统整体在退场，一律不收"
```
⚠️ **被拒 ≠ 我们错了。** 但也**不许**默认是对方的问题 —— 先把 ① 自查一遍再说。

### 6.2 零解释的关闭，值得问一句（成本极低，答案影响后续所有包）

问法：**给对方台阶、提供更小的替代方案、明说"哪个答案我都能接受"**。
不要辩论、不要重复已经写过的论证。范本见 `CLOSED-verl-fsdp-size-1/README.md` 里的草稿。

★ 关键是问出**是哪一类拒绝**：
- 「这个子系统不再维护」⇒ 同子系统的其它包要重新定位（包③ 也是 FSDP1，直接受影响）
- 「这个配置不受支持」  ⇒ 改提「让它硬失败」的小 PR（比修行为容易被接受得多）
- 「不感兴趣」          ⇒ 停止投入，把包改成 `PARKED-`，我们本地补丁照常用

### 6.3 关闭之后要做的三件事

```
1. 目录改 `CLOSED-`，README 顶部写清：谁关的、什么时候、给没给理由、改动有没有进 main
   ⚠️ **核对是否真的没合入**：`merge_commit_sha` 有值 ≠ 已合并（那只是 GitHub 算的试合并）
      判据是去 `origin/main` 上看那几行代码
2. 写清「材料是否作废」—— 通常没有：本地补丁照常用，日后可原样复用
3. 把学到的写回本文件（就像这一节）
```

### 6.4 ⛔ 不要做的

```
⛔ 不要在没得到理由前重开或重提同一个 PR
⛔ 不要因为一次被拒就下调证据标准（"反正也不会被收"）—— 材料是我们自己的资产
⛔ 不要把"被拒"写成"我们错了"，也不要写成"上游不讲理" —— 写清事实，理由未知就写未知
```
