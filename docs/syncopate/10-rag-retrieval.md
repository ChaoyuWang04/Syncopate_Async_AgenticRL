## 0 · 三十秒读懂

**我们没有做向量化。项目里没有 embedding、没有向量库、没有 ANN 索引。**
检索是**确定性的词法覆盖率打分**，每条 case 自带 1–2 篇语料，线性扫描。

这不是偷懒，是三条实测推出来的：**真向量库会污染 GRPO 的组内比较**、
**BM25 结构上产生不了"查不到"**、**手头的 encoder 没有分离带**。

⇒ 一句话：**这不是一个检索系统，是一个"检索结果模拟器"。**
它的职责不是"从一百万篇里找最相关的"，而是**确定性地造出三种局面**
（查到了 / 查到的是过期的 / 查不到），好让模型去学**拿到结果之后怎么办**。

| | 状态 |
|---|---|
| 语料层 / 检索层 / 工具层 / 判据层 / 造题层 | ✅ 完成 |
| 阈值标定（真语料重标定） | ✅ 2026-08-16 补跑，满分 |
| **§14 两项核心验收（过期检出率 / 无检索幻觉率）** | ⛔ **从未在模型上量过** |
| Recall@k / 引用准确性 / 检索延迟 | 🟡 两个门槛仍是【待定】，延迟未实现 |

## 1 · 存的是什么

钉死的前提：**会变的进 RAG，不变的进权重，绝不能错的进代码。**
所以 RAG 里存的是**"规矩"和"经验"**，不是实时数据（那归 `campaign.get_metrics`）。

| 库 | 表 | 工具 | 切分粒度 | 关键字段 |
|---|---|---|---|---|
| 半结构化 | `policy_clauses` | `policy.search` | **一条条款** | `valid_from/valid_to`、`supersedes` |
| 非结构化 | `insights` | `insight.search_claims` | **一条结论** | `status: active/superseded/refuted` |

```
[POL_0001_BUDGET_V1] 单日预算涨幅上限   不得超过前一日的 20%   有效期 …~2026-09-05  ← 已过期
[POL_0001_BUDGET_V2] 单日预算涨幅上限   不得超过前一日的 50%   2026-09-06 起  取代 V1
[CLAIM_A1] US 地区真人出镜素材的 D7 ROAS 高于纯 CG   status=active  N=42
```

★ **取代关系是从新条款反查的**（新版本声明 `supersedes=<旧 id>`），不在旧条款上写
`superseded_by` —— 语料是增量追加的，写旧条款等于每加一版都要回改历史，
而那正是"版本"这个概念要避免的。

★ `status` 字段**不能省**：它是 M12 飞轮的物理接口 —— 飞轮跑出相反结论时
把旧条目标 `refuted` 而不是删掉，**你需要知道"我们曾经这么以为"**。

## 2 · 检索怎么实现的

```python
def overlap_score(query, document):          # corpus.py:58
    q, d = set(tokenize(query)), set(tokenize(document))
    return len(q & d) / len(q)               # 查询词有多少出现在文档里

_TOKEN = re.compile(r"[A-Za-z0-9_]+|[一-鿿]") # 英文按词，中文按单字
MATCH_THRESHOLD = 0.35                        # 低于它 = 没查到，不是"返回最像的"
```

排序键是 `(-分数, 文档 id)`；带上 id 是因为分数相同时 dict 顺序会影响结果 ——
栽过一次「prompt 内容取决于 dict 插入顺序」。

**中文为什么按单字切**：不想引入分词器依赖 —— 分词器版本变了检索结果就跟着变，
等于把一个隐藏的非确定性源引进来（同 flash-attn 垫片那条教训：依赖要能钉死）。

这个看起来很笨的选择，恰好把「专业术语不好向量化」这个问题绕过去了：
**中文专业术语是复合词，换说法仍共享大部分字。** 实测（文档 = 单日涨幅那条）：

```
单日预算涨幅上限        1.000  ✅  标准问法（= 条款标题）
单日涨幅限制            0.833  ✅  换说法
日预算能涨多少          0.667  ✅  大白话
Meta 单日涨幅有什么限制  0.667  ✅  直接抄用户原话
预算调整规则            0.500  ✅  很泛的问法
每天预算最多能加多少     0.250  ❌  完全换词 —— 词汇失配，见 §6
budget daily increase   0.000  ❌  英文占不到这个便宜
```

**存储**：没有索引、没有数据库、没有建库过程。语料就是
`env_snapshot.readonly_tables` 里的普通 dict，落盘是 JSON，**逐 case**。
实测规模：**每条 case 1–2 篇**（152 条有语料的 case，中位数 2）。线性扫描。

## 3 · 三个决策，每个都有实测

### ① 为什么不用真向量库 —— 和检索质量无关，和 GRPO 有关

GRPO 把同一条 case **并发跑 8 遍**互相比分。近似最近邻、共享索引、运行时建库，
都会让「这次召回了、下次没召回」成为组内 reward 的差异来源 ——
**而那个差异会被当成"模型这次做得更好"记进 advantage。**

这是项目里一条既有纪律的同一形态：**RL 里任何跨 rollout 的随机性都是污染**
（失败注入必须确定性、由 case 声明，是同一条）。

⇒ 检索被做成 `(查询, 本 case 语料, reference_now)` 的**纯函数**。
要造「同一个问题答案不同」，靠**造一对只有语料不同的 case**，不靠检索的随机性。

### ② BM25 出局 —— 它结构上产生不了"查不到"

四方案同集对照（17 查询 × 10 条款的自建种子集，2026-08-14）：

```
方案                最佳阈值     命中/12   误召回   正确留空/5
词法覆盖率           0.35–0.40     11        2        4       ← 采用
CJK 二元组           0.05          11        2        4
BM25（按查询归一）    任意           11      ★ 6      ★ 0
Qwen3-0.6B 向量      0.70           9       ★ 6      ★ 0
```

**看最后一列，不是看命中率** —— 四个方案的命中率几乎一样（11/11/11/9），
拉开差距的是"正确留空"。

BM25 归一化后 **top1 恒为 1.0**（它给的是相对排序，不是绝对相似度），
⇒ **任何阈值都必然返回至少一条**。而「无检索幻觉率」这项验收
**要求"查不到"必须能发生**，用 BM25 的话它在构造上永远触发不了。

> ★ **BM25 是排序器，不是判定器。**

⚠️ **一次自我更正**：原先写的淘汰理由是"BM25 奖励长文档偶然重合"，
实测把这个解释推翻了，真机制是上面这条。**编一个理论写进注释**是本项目的老毛病。

### ③ 向量出局 —— 相关与不相关之间没有分离带

`Qwen3-0.6B` mean-pooling 出句向量，实测**任意两段文本余弦都落在 0.6–0.9**：
阈值定高全漏、定低全中，**中间没有中间**。

原因：它是 **causal decoder（生成模型），不是检索模型**，
mean-pool 向量各向异性强 —— 所有向量挤在一个窄锥里，所以什么和什么都"挺像"。

⚠️ **结论要带成立范围**：这**不代表 embedding 不行**，只代表手头这个模型不行。
真正的检索模型（bge / e5 类）大概率可用，代价是联网依赖 + 版本会影响检索结果 ——
而那又回到决策①的确定性问题。

## 4 · 阈值 0.35 的标定

工具：`scripts/calibrate_retrieval.py`，两种用法 ——
① 种子集（换打分函数时用）② `--from-batch`（**造完题之后必须跑这个重标定**）。

原注释里留着一句警告：「标定基准只有 17 条查询 × 10 条条款，而且是我自己写的，
**远不够定案**，真模板出来后必须重标定」。

**⚠️ 这次重标定在 2026-08-16 之前从没跑过**（`corpus.py` 的修改时间早于 v12 数据生成）。
补跑结果：

```
180 条评测项（应命中 123 / 应留空 57），逐 case 语料
阈值 0.35：命中且排首 123/123 · 误召回 0 · 漏召回 0 · 正确留空 57/57
平台期 0.30–0.75
```

**满分，且平台期宽达 0.45**，说明这个数站得住。分离带：

```
应命中的查询  最低分 1.000        应留空的查询  最高分 0.286
```

★ **这个宽度是设计的结果，不是运气**：造题时的**双向断言**由测试守着
（`tests/authoring/test_policy_drill.py`）—— 该命中的档断言 gold 查询真的命中且中对，
空洞档断言真的返回空。**没有这两条断言，阈值调到天上也没用。**

★ **两类错误代价不对称**：漏召回比误召回更毒 —— gold 要求作答但检索给不出，
会让"转人工"被判错、"编造"反而蒙对，**等于在训练我们正要消灭的那个行为**。

## 5 · 两项验收怎么落地成 cap

M8 之前，「过期检出率」和「无检索幻觉率」只是文档里的两个词，**进不了 reward**。

| cap | 封顶 | 判据 |
|---|---|---|
| `cited_expired_policy_cap` | **0.00** | 终答的 `cited_clause_id` 指向一条 `expired=true` 的条款 |
| `no_retrieval_hallucination_cap` | 0.20 | 检索明确返回空，仍给出确定性结论 |

**两条都做了自动闭合**（新 cap 若不闭合，存量 case 立刻被打中、历史基线全部作废）：

```
cited_expired        只有终答契约声明了 cited_clause_id 才生效  ⇒ 存量 820 条恒不命中
no_retrieval_halluc  ① 没发生过 no_match，或 ② 没有字段依赖它  ⇒ 两层，存量两层都不满足
```

★★ **第二条的判据踩过一个坑，值得记住。**

**原写法**：有过空检索 + 给了确定结论 = 幻觉。
**实测**：**当场把自己的 gold 判错了** —— `insight_conflict` 的 absent 档，
复盘库里没有历史结论，但模型手里有 `campaign.get_metrics` 的实际数据，
**照数据作答是正确的**，不是编造。
**改成**：判据必须挂在「**这个答案依赖那次检索**」上 ——
本 case 声明了某个终答字段要靠该检索背书（`AnswerField.evidence_tool`），
而那次检索返回了空，这时再给确定结论才算幻觉。

```
POL / empty     字段 evidence_tool=policy.search    ⇒ 武装 ✅
CONF / absent   字段 evidence_tool=get_metrics      ⇒ 不武装 ✅
```

**教训**：写「什么算错」之前，先把「什么算对」的轨迹拿来过一遍判据（坑 #10）。
逃生口要写在最前面 —— 转人工 / clarify / defer 一律放行，**那正是标准答案。**

★ 只认工具**真的返回过**的条款 id：模型编一个 id 出来属于幻觉，归另一条 cap 管。
**两种错误的修法完全不同，不能混。**

## 6 · 2026-08-16 审查发现的三件事

### ★★★ ① SFT 桶里 POL / CONF 各 0 条 —— M8 的验收路径整个断掉（已修）

v12 的 SFT 桶只有 6 个模板（ATTR 88 / GEO 78 / LOW 46 / BUD 24 / RAG 18 / FAIL 11），
**M8 新增的两个模板一条都没进。**

**根因不是"选得不好"，是保底只写在 `dead_grid` 分支里，而 v12 走的是
`difficulty_proxy` 分支**（v11 走 dead_grid，所以以前没暴露）。
`_difficulty_rank` 按 (难度, gold 链长) 降序取前 20%，
而 POL 的 gold 只有「一次检索 + 终答」，链最短 ⇒ 整个模板被挤出桶外。

**后果**：07 文档开头那句「**p=0 的格子 RL 永远够不着**」⇒ 没进 SFT 的模板，
冻结 EVAL 上量出来的一定是"没学会" —— **而这个结论和 RAG 实现好坏完全无关**。
会把一个分桶 bug 误判成 RAG 设计问题，然后去改根本没错的地方。

**修法**（`split.py`）：保底提成 `_apply_sft_floors`，**两个分支走同一个函数**；
三个轴 `behavior / template / outcome` 各挡一种形态。

⚠️ 两处设计取舍，都是被实测逼出来的：

- **在场保底只对 `difficulty_proxy` 开。** 一开始两个分支都开，撞坏一条既有测试
  （dead_grid 下活格 LOW 被硬拽进 SFT 桶）。判据是
  **「说不说得出为什么这个模板不需要 SFT」** —— dead_grid 说得出（它在 EVAL 上是活的，
  而 SFT 的职责是把 p 从 0 抬到 5–10%，不是抬到 90%），difficulty_proxy 说不出。
- **两类保底上限策略不同。** behavior 要**饱和**（不设上限）；template/outcome 要
  **在场**（最多吃一半，给 RL 留口粮）。第一版给 behavior 也加了"最多一半"，
  直接把 `defer` 保底从 12 削到 8 —— 那正是当年 defer 77%→36% 的那条线。

**结果**：POL/CONF 各 0 → 16，19 个模板全部 >0。代价：SFT 265→477、RL 1063→819。

### ② 两项验收的分母只有 4 条（已修）

冻结 EVAL 里 `rag_state:superseded` 4 条、`rag_state:empty` 4 条 ——
**错一题就是 25%**，而这两项的目标是"趋近 0"。和 M7 那个
「配对 MDE 0.013 比效应量还大」是同一种病：**尺子比要量的东西粗**。

根因：`RARE_BEHAVIOR_EVAL_QUOTA` 只按 **behavior** 加厚，
而 POL/CONF 的 behavior 恰好是最常见的 `tool_call` ⇒ 只拿到 `eval_per_stratum=2`。

**修法**：新增 `OUTCOME_EVAL_QUOTA`，按**结局档**加厚，4 → 12。

★ **这个加厚是严格增量的，且由构造保证**：取样写法是 `sorted(strata[key])[:take]`，
调大 `take` 只在尾部追加 ⇒ 冻结 EVAL 的老 case_id 一个不动
（已对 git HEAD 逐条核过：222 → 254，**丢失 0 条**），
历史基线 `_audit/v11_sft_e1_m2.json` 对它们仍然逐条配对可比。

### ③ 选型可复述但不可复现（未修，已评估）

四方案对照的**结论**记在注释里，但那三个被淘汰方案的**代码已经没了** ——
`calibrate_retrieval.py` 现在只剩 `overlap_score` 一个打分器。

按本项目"结论要能被重新量出来"的纪律，这是一笔技术债。
好在 `sweep(items, thresholds, scorer=...)` 留了 `scorer` 参数，插回去不算大工程。
⇒ **以后要换检索方案，第一步是先把那三个对照打分器补回来。**

## 7 · 已知局限与训推缺口（都是显式记账，不藏）

**① 词汇失配** —— 「每天预算最多能加多少」vs「单日预算上调不得超过前一日的 20%」
表层几乎无共同词，实测**四种方案全军覆没**。这是词法检索的固有边界。

它真正的危险不是"检索差"，是**会教出一个错技能**：把查询词凑成文档原词。
那个技能对真向量库无用甚至有害 —— **训推不一致里最坏的一种：
不是能力没学到，是学了个错的。**

⇒ **造题纪律**（写在 `corpus.py`，由测试守着）：

```
✅ 该训的：拿到结果之后怎么办 —— 用现行版还是过期版、查不到时转人工还是硬答
❌ 不该训的：怎么把查询词凑成文档里的原词
不许设计"要换三次说法才查得到"的题。
```

§14 的两项验收都只考"怎么处理结果"、不考"怎么组织查询" —— **这个设计正好绕开了这个坑。**

**② 沙盒 vs 线上**：线上是真向量库 + rerank，沙盒是确定性词法。
处理办法**不是把它藏起来**，而是让沙盒实现**同一份契约** ——
会返回空、会返回过期的、会返回只沾边的。按「沙盒不要比真实世界友好」的原则，
把不完美如实建模，而不是给一个干净的召回。

**③ 英文查询占不到单字切分的便宜**（实测 0.000）。当前语料以中文为主，暂不处理。

# R 部分 · Runtime 侧 RAG（原 12 号，2026-08-17 建，2026-08-19 并入）

> **契约由 runtime 定义，沙盒去满足它**（`09 §1-③`）—— 建它之前这条纪律是反的：
> 阈值/语义全是训练侧的 `corpus.py` 单方面定的。这一版的第一产出是**契约**，代码只是载体。
> 分层沿用设计 §12：结构化（安全线/benchmark）**永不进检索**（精确 key 查询）；
> 半结构化 + 非结构化走「SQL 过滤 + 词法打分」。

## R1 · ★★★ 契约：三种状态，不是两种

```
ok           查到了            hits 非空
no_match     查了，确实没有     语义 =「没有政策限制这件事」⇒ 可带 caveat 继续或转人工
unavailable  查不了            语义 =「不知道有没有限制」  ⇒ 绝对不能继续
```

现象一模一样（都是"没拿到东西"），语义正好相反 —— 合并成一个信号，
**一次故障看起来就是"没有限制" ⇒ agent 放行**（压测场景④要抓的灾难）。
与「超时的两种形态」同形（`09 §2`）；区别是超时那两种真实世界里就分不开（靠幂等键），
而这两种**我们完全分得开** —— 分得开却不分是自己制造致命歧义。

返回结构 `RetrievalResult(status, hits, query, latency_ms, error)`，三条硬约束（测试守着）：
① **`unavailable` 不许降级成 `no_match`**（安全边界，不是实现细节）；
② **不许"总是返回 top-k"**（阈值是真的，否则「检索为空不编答案」构造上永远触发不了）；
③ **`expired`/`superseded_by` 是 SQL 算出来的，不是检索出来的** ——
   取代关系从新条款反查（沿用 §1），**即使检索是模糊的，"哪一版现行"也是精确的**：
   把最贵的那件事从模糊侧挪到了精确侧，「过期检出率」验收因此不依赖检索质量。

接降级网关：`retrieval_empty`（查不到）与 `retrieval_unavailable`（查不了）**两个触发器**都开审批单，
但 `trigger_reason` 必须不同 —— 人对这两种情况要做的判断完全不同。

## R2 · 打分复用沙盒函数，但阈值必须重标（0.35 → 0.53）

PG 默认全文不懂中文；装 `zhparser` = 引入「版本变了结果就变」的依赖（沙盒刻意避免的）。
⇒ SQL 管过滤（租户/platform/region/生效期/取代），Python 直接 `import` 沙盒的
`overlap_score` —— **复用同一个函数让"契约一致"是逐字一致而不是近似一致**。
成立范围：语料 10²–10³ 条线性扫描（实测 3ms）；> 10⁴ 条或 P95 > 100ms 才换倒排做候选集。

★★★ **阈值不能沿用 0.35 —— 当天被推翻的预测**（原猜想：函数一样阈值也一样）。
实测语料只有 4 条就出问题：「量子计算加速广告投放」撞上博彩条款得 0.400 ≥ 0.35。
**机制不是规模，是候选集变了**：沙盒每条 case 只带 1–2 篇构造上不撞；runtime 全库参与打分，
单字切分的 CJK 太容易撞 ⇒ **相同打分函数 + 不同候选集 = 操作点必然不同**。
重标（`scripts/calibrate_runtime_retrieval.py`，评测集进版本管理）：
应命中族内最低 0.667 / 应留空最高 0.400 ⇒ `RUNTIME_MATCH_THRESHOLD = 0.53`。
⚠️ 语料一变必须重跑该脚本；真实查询要等 M10。
**教训：共用的是函数，不是参数**（同 M8「共用的是函数，不是策略」）。

## R3 · 向量什么时候上 —— 门槛写死，不是"以后再说"

不上的理由是实测的（§3-③ 没有分离带），但真正的理由是**一条真实用户查询都没有**。

```
前提   M10 影子模式攒够 ≥200 条真实查询
判据   真实查询 × 真实语料，量词法检索的漏召回率
门槛   >10% ⇒ 上向量（只上非结构化层）；≤10% ⇒ 不上，结论写回本文
```

已知会漏在哪：词汇失配（「每天预算最多能加多少」vs 条款原文几乎无共同词）——
这类问法占多少**只能量，不能猜**。

## R4 · 沙盒欠的两样（v13 已补，过程教训留档）

| 欠什么 | 为什么沙盒造不出来 | 不补的后果 |
|---|---|---|
| ① 检索不可用 | 沙盒是纯函数，永远不会挂 | 模型学不会「查不了时不能放行」 |
| ② 似是而非的误召回 | 每 case 只 1–2 篇，构造上不撞 | 没见过「召回了相关但不对的条款」——真语料上的常态 |

②是「沙盒比真实世界友好」的新形态：**沙盒把干扰藏起来了 —— 语料少不是简化实现，是改变任务难度**。
落地成两个新模板 `policy_outage`(POLU)/`policy_misread`(POLM) 各 60 条 + `retrieval_unavailable_cap`(0.15,
两层自动闭合) —— **不是给 policy_drill 加档**，因为 `axes.py` 写死 `% 3`，扩档会重排存量 90 条 POL
（增量重建的坑）。实测 v12→v13：存量 1550 条逐字节未变、EVAL 254→278 老 id 丢失 0。
⚠️ 新档 EVAL 配额一开始只有 4 条（尺子比要量的东西粗，M8 §6-② 同坑），进 `OUTCOME_EVAL_QUOTA` 后 4→12。
⚠️ 顺序也被推翻过一次：原计划「先 M8 验收再动沙盒」——但两项验收是绝对判据不需要基线，
且 `unavailable` 是刚定的契约，在 v12 上训练 = 训出从没见过「查不了」的策略（学了个错的）。

## R5 · 别再重新讨论的（R 部分）

- **不用向量库**（R3 门槛没满足之前）；**不装中文分词扩展**（R2）。
- **runtime 阈值和沙盒阈值本来就该不同**（R2 实测），要统一的是函数不是参数。
- **结构化数据永不进检索**（把安全线塞进向量库是灾难）。
- **取代关系从新条款反查**，不回改旧条款。
- **`unavailable` 永不降级成 `no_match`** —— 安全边界。
