# Syncopate · 16 — M7-b：v13 上的第二次 RL（2026-08-17）

> M7 第一跑的结论是「没测出差异」，根因量出来是**位移太小**。
> 这一跑只想回答一件事：**把 lr 提上去，能不能推动模型。**
> 答案是：**能推一点，但在 fully_async 下会先撞上另一堵墙。**

---

## 0 · 三十秒读懂

```
起点   Qwen3-4B + SFT(v13, e1) 合并模型      数据 v13（EVAL 343 / SFT 503 / RL 824）
配置   fully_async · DDP · 动态分池开 · 110 步（RL train 659 / batch 6 = 一遍）

lr 3e-5   ESS/N 从 0.85 一路跌到 0.26，**第 75 步跌破 0.3 触发停机**，无 ckpt
lr 1e-5   ESS/N 全程 0.34–0.91，**110 步跑完**，5 个 ckpt
          位移 ‖ΔW_eff‖/‖W_base‖ = **0.0487%**
          配对差值 **+0.020**，而配对 MDE 也正好是 **0.020** ⇒ **仍是「没测出差异」**
```

★★★ **这一跑的真正产出不是模型，是一条被夹住的区间**：

> **lr 大到能推动模型时，异步的 ESS 就塌了；lr 小到 ESS 健康时，模型推不动。**

---

## 1 · 三个数据点把 lr 夹住了

| | lr | 步数 | ESS/N | 位移 | 结局 |
|---|---|---|---|---|---|
| M7 第一跑 | 1e-6 | 100 | 0.74–0.88 | 0.0093%※ | 没测出差异 |
| **M7-b** | **1e-5** | **110** | **0.34–0.91** | **0.0487%** | **仍没测出差异**（+0.020 = MDE） |
| M7-b 首跑 | 3e-5 | 75 | **跌破 0.3** | — | **TIS 破裂，停机** |

※ M7 那个数用的是**另一种口径**（`‖Δθ_trainable‖/‖θ_trainable‖`，LoRA 的 B 零初始化）
⇒ 和这里的 `‖ΔW_eff‖/‖W_base‖` **不可直接比**。见 `14-sft-health-metrics.md`。

**参照**：SFT 一遍（lr 1e-4 × 210 步）的位移是 **0.4985%** —— 比 RL 这一跑大 10 倍。

### ★ 这正好是 §00 研究问题里的 H2

`ESS/N ≈ exp(−T·σ²(k))`，而 σ 随策略每步移动量增大。
**lr 直接调的就是"每步移动多少"** ⇒ 提 lr 同时做两件事：推动模型 **和** 压低 ESS。
⇒ 这两件事在 fully_async 下**是同一个旋钮**，这就是那条等值线。

⚠️ 而它**在同步 colocate 下不存在**（k=0，σ 只剩实现失配）——
所以「异步能不能吃更大的 lr」本身就是一个可以做的对照实验（见 §4）。

## 2 · 逐模板：方向是对的，幅度不够

```
涨得最多  SCALE +0.061 · CONF +0.045 · CLAR +0.031 · FAIL +0.020
退得最多  REJ −0.047 · POLM −0.036 · BUD −0.032 · POLU −0.025
逐题      赢 146 / 平 71 / 输 126
```

⚠️ **v13 新增的两档（POLU/POLM）双双小幅退步** —— 它们在 SFT 之后已经很高
（0.980 / 0.967），属于"接近饱和的题被 RL 动了一下反而掉"，和 M7 那次
FRESH 掉得最多是同一个形状：**RL 会动到本来做得好的题**。

★ 护栏侧最刺眼的一条：**`unauthorized_write_cap` 91 → 128（+37）**。
位移只有 0.0487% 就多出 37 次越权写 —— 和 M7 那次「0.0093% 的位移下
`false_claim_cap` 掉 19%、同时长出两类新违规」完全一致：
**模型对 RL 方向极其敏感，而 reward 只决定方向不决定距离。**

✅ **`retrieval_unavailable_cap` 在训练中真的被打中过（末步命中率 4%）** ——
v13 那个新档在 RL 里是活的，不是摆设。

## 3 · 动态分池：第一次真的接上了

```
(FullyAsyncRollouter pid=…) [verl-patch] worker 进程：动态分池 sampler 已装
(FullyAsyncRollouter pid=…) [pool] 动态分池启用：659 条 case
```

★ 判据是**那个进程**打出来的 —— `FullyAsyncRollouter` 正是此前 driver 侧补丁够不着的
Ray actor。修法：把 `install_sampler_patch()` 装进 `verl_patches.setup_worker()`，
走已有的 `_defer_until_imported`（钩子里只许做纯 Python 的事）。

离线用真实评测数据验过：有梯度题占抽样 **79.1%**（题库占 63.7%）、
饱和题降到 **13.5%**（占 23.4%）、**65/65 条饱和题都被复检过**（中位第 41 步）——
地板没把回归检测关掉。

## 4 · 下一跑该做什么（按优先级）

1. **★ 同步 colocate 下跑同样的 lr 3e-5。**
   如果 colocate 能吃下 3e-5 而 fully_async 不能，**那就是异步的代价第一次被量出来** ——
   而且是这个项目研究问题的正面答案。成本一跑。
2. **缩短同步周期 / 调大 `--latency-scale`。** 这一跑 `partial_ratio` 仍是 **0**
   （轨迹 ~500 token vs 同步周期 4 步），漂移这条线还是空的。
3. **lr 2e-5 补一个中间点**，把等值线画出来（现在只有 1e-5 通过 / 3e-5 破裂两点）。
4. **步数换 lr**：位移 ≈ lr × 步数。1e-5 × 330 步（三遍）位移约 0.15%，
   ESS 未必塌 —— 用时间换位移，比硬提 lr 安全。

## 5 · 这一跑踩的坑（全部有修）

| 坑 | 现象 | 修法 |
|---|---|---|
| **nsys 包住长跑** | 中间文件 30 分钟涨到 **74 GB**，且 `nsys stop` **会杀掉目标进程** ⇒ 首跑报废、产出是个 0 字节报告 | nsys 只包 ≤10 步的专门跑；长跑用 `torch.profiler`。记在 `08 §4.0.1` |
| **`save_freq` 判断的是 `param_version` 不是 global_step** | 每 4 步 +1 ⇒ `save-freq 25` 要到第 ~100 步才第一次存；中途停机 = **一个 ckpt 都没有** | 改用 `--save-freq 5`（≈每 20 步），并挂自动瘦身（8.5 GB → 252 MB） |
| **评测的基座默认成裸模型** | RL 的 LoRA 是在 **SFT 合并模型**上训的，贴到裸基座 ⇒ 分数全线暴跌（CLAR 0.844→**0.000**），看着像"RL 把模型训坏了" | `eval_parallel.sh` 的 `MODEL` 改成**必填**，给错宁可报错 |
| `pgrep -f` 自匹配 | 第 6 次。守卫脚本按模式 kill 打到了自己 | 改用 PID 文件 |
| 守卫匹配错进程名 | `launch_rl` 会 exec 成 `main_ppo_pool` ⇒ 守卫立刻退出，形同虚设 | 匹配 `train[.]main_ppo_pool` |
| 在 shell 脚本运行中改它 | bash 边读边执行，字节偏移一变当场语法错 | 改完再跑 |

★ 其中前三个都是**同一个形状**：**一个默认值/判据看起来正常，实际指向了另一件事**，
而且都不报错。
