## 1 · 为什么现在建（最硬的理由不是压测）

压测场景④「RAG 不可用」没有被测对象、§19 的「检索 P95 < 200ms」量不了、
`retrieval_empty` 触发器没有生产者 —— 这三条一次关掉，但它们都不是最重要的。

最重要的是这条纪律**现在是反的**：

> 「沙盒是 runtime 的子集，**且契约由 runtime 定义**」（`09 §1-③`）

契约实际上是 `corpus.py`（沙盒）定的：阈值 0.35、`no_match` 的语义、`top_k=3`、
取代关系从新条款反查 —— **全是训练侧单方面定的，runtime 那边什么都没有**。
每多拖一天，沙盒就多攒一些 runtime 未必兑现得了的契约决定。

⇒ **这一版的第一产出不是代码，是契约**（§3）。代码只是让契约有个物理载体。

## 2 · 三层怎么分（§12：RAG 必须是混合的，不是纯向量）

| 层 | 内容 | 怎么查 | 这一版 |
|---|---|---|---|
| **结构化** | 安全线 · benchmark · 权限矩阵 · 素材标签 | **精确 key 查询，零召回误差** | 已有（`ingested.json`），本版不动 |
| **半结构化** | 平台广告政策 · 广告法 · 内部 SOP | **SQL 字段过滤 + 词法打分** | ✅ 本版建 |

ROAS 线』可能召回 PROD_B 的」。所以结构化那层永远不进检索，这一版继续保持。

## 3 · ★★★ 契约：三种状态，不是两种

这是本文档最重要的一节。**runtime 定义它，沙盒去满足它。**

```
ok           查到了            hits 非空
no_match     查了，确实没有     hits 为空 —— 语义是「**没有政策限制这件事**」
unavailable  查不了            hits 为空 —— 语义是「**我们不知道有没有限制**」
```

### 3.1 为什么必须把后两种分开

```
no_match      语料里确实没有对应条款   ⇒ 可以带 caveat 继续，或转人工
unavailable   PG 挂了 / 检索超时       ⇒ **绝对不能继续**
```

**现象一模一样（都是"没拿到东西"），语义正好相反。**
合并成一个信号的话，**一次故障看起来就是"没有政策限制" ⇒ agent 放行** ——
而那正是压测场景④要抓的那个灾难。

★ **这和「超时的两种形态」是同一个形状**（`09 §2`）：

```
超时    没发出去（重试安全） vs 到了但回包丢了（重试=重复扣款）  —— 靠幂等键分辨
检索    查不到（没有限制）   vs 查不了（不知道有没有限制）        —— 靠状态码分辨
```

⚠️ 区别在于：超时那两种**在真实世界里就是分不开的**，所以错误文本必须逐字相同；
而检索这两种**我们完全分得开**（一个是查询返回 0 行，一个是连接失败）——
**分得开却不分，是自己制造了一个致命的歧义。**

### 3.2 返回结构

```python
@dataclass(frozen=True)
class RetrievalResult:
    status: RetrievalStatus        # ok | no_match | unavailable
    hits: list[dict]               # unavailable 与 no_match 时**必为空**
    query: str
    latency_ms: int                # §19 的「检索 P95 < 200ms」量的就是它
    error: str | None = None       # 只有 unavailable 时非空
```

**三条硬约束**（都由测试守着）：

1. **`unavailable` 不许降级成 `no_match`。** 服务出问题时"假装没查到"是最坏的默认值。
2. **不许"总是返回 top-k"。** 阈值是真的，低于它就是没查到 ——
   否则「检索为空时不编答案」这项验收在构造上永远触发不了（同 doc 10 §3-② 淘汰 BQ25 的理由）。
3. **`expired` / `superseded_by` 是算出来的，不是查出来的**（§4）。

### 3.3 接到降级网关上

`DecisionContext` 加第八个信号，gateway 加第七个触发器：

```
retrieval_empty_tools        已有  ⇒ 触发器 retrieval_empty        「查不到」
retrieval_unavailable_tools  🆕    ⇒ 触发器 retrieval_unavailable  「查不了」
```

两者都开审批单 —— **因为网关本来就是"不要继续，交给人"的那个机制**。
但 `trigger_reason` 必须不同：人看到"检索为空"和"检索挂了"要做的判断完全不同。

## 4 · 过期与取代：SQL 算的，不是检索问题

```sql
expired       := valid_to IS NOT NULL AND valid_to < :now
superseded_by := (SELECT clause_id FROM policy_clauses WHERE supersedes = c.clause_id)
```

★ **取代关系从新条款反查**（新版本声明 `supersedes=<旧 id>`），不在旧条款上写
`superseded_by` —— 语料是增量追加的，写旧条款等于每加一版都要回改历史，
而那正是"版本"这个概念要避免的。**这条沿用沙盒的既有决定，不改。**

★★ **这意味着：即使检索是模糊的，"哪一版现行"也是精确的。**
§14 的「过期检出率」那项验收因此**不依赖检索质量** ——
检索只负责"找到这一族条款"，"哪一版有效"是确定性计算。
**把最贵的那件事从模糊侧挪到了精确侧。**

## 5 · 打分：为什么不用 PG 全文，而是复用沙盒那个函数

**PG 的默认全文配置不懂中文** —— 没有分词器，一整段 CJK 会被当成一个 token。
要让它能用得装 `zhparser` / `pg_jieba`，**而那等于引入一个"版本变了检索结果就变"的依赖** ——
正是沙盒侧刻意避免的东西（`corpus.py`：「不想引入分词器依赖」）。

⇒ **这一版的分工**：

```
SQL   做它擅长的：作用域/租户过滤 · platform/region 过滤 · 生效期 · 取代关系
Python 做打分：直接 import 沙盒的 overlap_score 和 MATCH_THRESHOLD
```

★★ **复用同一个函数不是图省事，是让"契约一致"变成逐字一致而不是近似一致。**
两边各写一份打分逻辑，迟早会漂移，而漂移了没有任何东西会响。

⚠️ **这个选择的成立范围**：语料 10²–10³ 条时，线性扫描 < 10ms（实测 3ms），纯赚。
**什么时候换成倒排/全文做候选集生成**：语料 > 10⁴ 条，或检索 P95 > 100ms
（= §19 门槛 200ms 的一半）。

### 5.1 ★★★ 阈值不能沿用沙盒的 0.35 —— 一个当天就被推翻的预测

**原猜想**（写在本文档第一版）：打分函数一样、阈值也一样，
要改的触发条件是「语料 > 10⁴ 条」或「P95 > 100ms」——**都是规模/性能维度**。

**实测**：语料**只有 4 条**的时候就出问题了，而且**和规模、延迟都无关**：

```
查询「量子计算加速广告投放」   ← 语料里显然没有的东西
撞上 POL_SEA_GAMBLING（东南亚博彩条款）  得分 0.400 ≥ 0.35  ⇒ 被当成命中
共享的字：投 / 放 / 广 / 告
```

**推翻后**：真正的机制不是规模，是**候选集变了**。

```
沙盒     每条 case 自带 1–2 篇、手写、构造上不会互撞          ⇒ 0.35 够用
runtime  整个语料库一起参与打分                              ⇒ 单字切分的 CJK 太容易撞
```

⇒ **相同的打分函数 + 不同的候选集 = 操作点必然不同。** 这不是调参，是结构性的：
误召回概率随语料条数**单调上升**，而阈值标定的那 17 条查询是在"每次只看 1–2 篇"下做的。

**重新标定**（`scripts/calibrate_runtime_retrieval.py`，可重跑、评测集进版本管理）：

```
应命中 族内最低  0.667        ← 版本对（V1/V2）算同一族：两个都该召回，
应留空 最高      0.400          "哪一版现行"由 §4 精确算，不归检索管
⇒ 可用区间 (0.400, 0.667]    取中点  RUNTIME_MATCH_THRESHOLD = 0.53
```

⚠️ **4 条语料 + 11 条我自己写的查询，远不够定案**（同 `corpus.py` 当年那句自白）。
真实查询要等 M10。**语料一变就要重跑那个脚本** —— 所以它是脚本不是注释里的传说
（doc 10 §6-③ 记着"选型可复述但不可复现"那笔债，这里不重蹈）。

**教训**：**"两边共用同一个函数"保证的是契约一致，不保证操作点一致。**
共用的是**函数**，不是**参数** —— 同 M8 那条「共用的是函数，不是策略」。

## 6 · 向量什么时候上 —— 门槛先写死

**不上的理由是实测的，不是偏好**（doc 10 §3-③）：`Qwen3-0.6B` mean-pooling
任意两段文本余弦都落在 0.6–0.9，**相关与不相关之间没有分离带**。
换真检索模型（bge/e5）大概率可用，代价是联网依赖 + 版本会改变检索结果。

**但真正的理由是：我们手上一条真实用户查询都没有。**
现在建向量库是在优化一个量不了的东西 —— 正是"用推理代替测量"。

⇒ **门槛**：

```
前提   M10 影子模式跑起来，攒够 ≥ 200 条真实用户查询
判据   用真实查询 × 真实语料，量词法检索的**漏召回率**
门槛   漏召回 > 10%  ⇒ 上向量，且**只上非结构化那一层**
       漏召回 ≤ 10%  ⇒ 不上，把这条结论写回本文档
```

★ 已知它会漏在哪：**词汇失配**（「每天预算最多能加多少」vs
「单日预算上调不得超过前一日的 20%」表层几乎无共同词）。所以真实查询里
这类问法占多少，直接决定要不要上 —— **这个比例只能量，不能猜。**

## 7 · 沙盒那半边：要做，但**不是现在**

契约里新增的 `unavailable`，沙盒目前**造不出来** —— 它是纯函数，永远不会不可用。
按「契约由 runtime 定义」+「沙盒不要比真实世界友好」，沙盒必须补上这个局面，
否则**模型永远学不会"查不了的时候不能放行"**。

⚠️ **但它必须排在 M8 验收之后**：动沙盒 = 动数据版本（v12 → v13）。
而 M8 的两项验收还没在模型上量过、基线也还没重出。先动沙盒就会重演
「增量重建把基线搞没了」那一次。

```
2026-08-17 上午  runtime 侧（本文档 §3–§5）
2026-08-17 下午  ✅ **沙盒两样都补完了，v13 已生成**（见下）
```

### 7.1 ✅ 已兑现（顺序被推翻了一次，记在这里）

**原计划**：先跑 M8 验收，再动沙盒。**理由是"保住基线"。**
**被推翻**：M8 的两项验收是**绝对判据（趋近 0），根本不需要基线模型**；
而这台机器上没有任何 SFT 产物，反正要重训。
⇒ 先训 v12 再改沙盒 = **白烧一个完整的 SFT + 评测周期**。

★ 更要紧的是我当时没想到的一条：`unavailable` 是**刚给 runtime 定下的契约**，
在 v12 上训练 = 训出一个从没见过"查不了"的策略 —— 按纪律那属于「学了个错的」。

**动手前先量了一件事**（怕加干扰文档会把沙盒推进 runtime 上那个误召回区间）：
现有干扰最高 0.286、阈值 0.35，**余量 0.064，够用** ⇒ 不用重标定沙盒阈值。
⚠️ 顺带发现沙盒的 `empty` 档**本来就放了干扰条款** —— 所以问题从来不是
"要不要加干扰"，是"加哪一种"。

### 7.2 落地成了两个**新模板**，不是给 policy_drill 加两档

⚠️ 因为 `axes.py` 里所有轴都是 index 推导 + **写死的 `% 3`**：
`RAG_STATES` 从 3 扩到 5 就要改成 `% 5` ⇒ **存量 90 条 POL 的档位全部重排**
⇒ 语料变、gold 变、历史基线全废。那正是「增量重建顺手改掉不相关部分」那个坑。

```
policy_outage  (POLU) 60 条  检索不可用：政策**存在**但够不着（server_error + every:true）
policy_misread (POLM) 60 条  似是而非：召回了东西，但它答非所问
新 cap  retrieval_unavailable_cap (0.15)  两层自动闭合，存量恒不命中
```

**实测（v12 → v13）**：

```
存量 1550 条 case      逐字节未变 0 处改动 · 0 处丢失      ← 构造保证，不是事后 diff
冻结 EVAL              254 → 278，老 id 丢失 0
新模板进桶              EVAL 12/12 · SFT 12/12 · RL 36/36
```

★ **中途按 M8 的教训改了一次配额**：新档在 EVAL 里一开始只拿到 **4 条**
（每格 2 × 两个 entry_mode）—— 和 M8 §6-② 栽的是同一个坑「尺子比要量的东西粗」。
加进 `OUTCOME_EVAL_QUOTA` 之后 4 → 12。

**沙盒欠的是两样，不是一样**（第二样是建 runtime 的过程中才发现的）：

| 欠什么 | 为什么沙盒现在造不出来 | 不补的后果 |
|---|---|---|
| **① 检索不可用** | 沙盒是纯函数，永远不会挂 | 模型学不会「查不了的时候不能放行」 |
| **② 似是而非的误召回** | 每条 case 只有 1–2 篇手写语料，**构造上不会撞** | 模型没见过「召回了一条相关但不对的条款」，而这在真语料上是常态（§5.1 实测 0.400 的那次） |

★ ②尤其值得记：它是**"沙盒比真实世界友好"的一个新形态** ——
以前担心的是沙盒把失败藏起来，这次是沙盒**把干扰藏起来了**。
语料少不是简化实现，是**改变了任务难度**。

★ 这是那条纪律**第一次朝正确方向起作用**：runtime 先定契约，沙盒后满足。
以前是反的（M8 定完沙盒才发现 runtime 什么都没有）。

## 8 · 别再重新讨论的

- **不用向量库**（§6 的门槛没满足之前）；**不装中文分词扩展**（§5）。
- **runtime 阈值和沙盒阈值本来就该不同**（§5.1 实测），别"统一"它们 —— 要统一的是函数，不是参数。
- **结构化数据永不进检索**（安全线塞进向量库是灾难，§2）。
- **取代关系从新条款反查**，不回改旧条款（§4）。
- **`unavailable` 永不降级成 `no_match`**（§3.1）—— 这条是安全边界，不是实现细节。
