## 0. 先建立地图：一次 RL 训练到底在做什么

### 0.1 一个循环，四个动作

抛开所有术语，LLM 的强化学习后训练就是这样一个循环：

```
   ┌──────────────────────────────────────────────────────┐
   │                                                      │
   ▼                                                      │
① 出题                                                    │
   给模型一批 prompt（数学题 / 代码题 / 一个待完成的任务）      │
   │                                                      │
   ▼                                                      │
② 生成（rollout）                                          │
   模型自己写出答案。可能是一次性写完（单轮），                  │
   也可能是"想一步→调工具→看结果→再想"（多轮 agentic）          │
   │                                                      │
   ▼                                                      │
③ 打分（reward）                                           │
   跑单元测试 / 对答案 / 让另一个模型评判 / 环境返回成败          │
   │                                                      │
   ▼                                                      │
④ 更新权重（train）                                         │
   用 PPO / GRPO 之类的算法算梯度，改模型参数                   │
   │                                                      │
   └──── ⑤ 把新权重塞回生成器，再来一轮 ────────────────────────┘
```

这个循环有一个和普通训练**完全不同**的地方：**训练数据是模型自己现场产生的**。

普通的监督训练，数据在硬盘上躺着，你只需要一个训练引擎。而 RL 训练里，你同时需要：

- 一个**训练引擎**跑第 ④ 步（算梯度、更新参数）
- 一个**推理引擎**跑第 ② 步（高速生成）
- 一个**编排层**协调这两者：谁用哪张卡、什么时候切换、权重怎么从训练引擎传到推理引擎

**RL 框架 = 这三样东西的组装方式 + 循环逻辑。** 所有框架的差异都可以还原到这句话。

### 0.2 为什么这件事很难

有三个反直觉的难点，理解了它们，你就理解了这个领域全部工程复杂度的来源。

**难点一：训练和推理是两套完全不同的软件，但要装同一个模型。**

训练引擎（Megatron、FSDP）为了算梯度，把模型按某种方式切到多张卡上；推理引擎（vLLM、SGLang）为了快速生成，按另一种方式切。两边的权重排布（sharding layout）不一样。每训练一步，你都要把训练侧的权重**重新排布**后送到推理侧——这个动作叫 **weight sync（权重同步）**，是 RL infra 最核心的工程难题之一。

普通推理服务一辈子只加载一次权重；RL 里每几十秒就要换一次。**推理引擎在 RL 中不是"服务"，而是一个高频可变对象。**

**难点二：生成的耗时是长尾分布。**

一批 512 条 prompt，有的模型 200 token 就写完了，有的要写 8000 token。同步训练必须等最慢的那条写完才能进入训练阶段——于是绝大多数 GPU 在那儿干等。这个"气泡"（bubble）通常吃掉 30%~60% 的算力。所有框架的"异步"设计，都是在解这一个问题。

**难点三：RL 的 bug 不会报错。**

代码跑得好好的，loss 在下降，但模型就是不变强，或者训了 500 步突然崩掉。原因可能是权重同步漏了一层、推理引擎和训练引擎算出来的概率对不上、或者用了过期数据却没改目标函数。**这类 bug 只能靠指标发现，不能靠 traceback 发现**——这也是为什么 slime 这种"数据流显式可见"的设计有额外价值。

### 0.3 三个部件的分工

| 部件 | 干什么 | 代表 |
|---|---|---|
| **训练引擎** | 把模型切到多卡上，前向、反向、更新参数 | Megatron-Core、PyTorch FSDP、DeepSpeed、TorchTitan |
| **推理引擎** | 高吞吐地生成 token，管 KV cache | vLLM、SGLang、TensorRT-LLM |
| **编排层** | 分配 GPU、启动进程、传数据、容错 | Ray、SLURM、Monarch、accelerate |

后面第 3、4、5 章会分别把这三个部件讲透。先看决策树。

## 1. 决策树：怎么选

### 1.1 选训练引擎

训练引擎的分水岭只有一条：**你的模型能不能靠"每张卡放一份完整模型"的方式训起来。**

```
你要训多大的模型？
│
├─ ≤ 8B 稠密模型，卡够（8×80G 以上）
│   → PyTorch FSDP2
│     理由：和 HuggingFace 权重格式一模一样，不用转换；
│           改代码最简单；权重重排布（resharding）最便宜，
│           所以每步同步权重到推理引擎的开销最小。
│
├─ 8B ~ 70B 稠密模型
│   ├─ 你想快速做算法实验，不在乎最后 20% 的吞吐
│   │   → PyTorch FSDP2（配 sequence parallel / Ulysses 处理长序列）
│   └─ 你要压榨吞吐、或上下文超长（32K+）
│       → Megatron-Core（用它的 TP + CP）
│
├─ MoE 模型（Qwen3-30B-A3B、DeepSeek-V3、GLM 系列……）
│   → Megatron-Core，没有第二个选择
│     理由：MoE 必须要专家并行（EP），只有 Megatron-Core 这条线做得成熟。
│     ⚠️ 额外注意：MoE 的 RL 有一个专属大坑，见 §6.7 Miles 的 R3。
│
└─ 100B+ / 需要流水线并行（PP）
    → Megatron-Core
      代价：权重格式和 HuggingFace 不同构，存取都要转换
            （这就是 Megatron-Bridge 存在的理由，见 §3.5）
```

**一句话总结**：`FSDP2 = 好用但天花板低`，`Megatron-Core = 难用但没有天花板`。中间地带靠你对"开发速度 vs 吞吐"的偏好来定。

### 1.2 选推理 / rollout 引擎

注意，这里的判据**和你部署线上服务时完全不同**。线上服务比的是吞吐和延迟；RL 里比的是别的东西。

```
你的 rollout 长什么样？
│
├─ 单轮生成，一问一答（数学题、代码题）
│   → vLLM 或 SGLang 都行，差别不大
│     倾向 vLLM：生态更大、文档更全、遇到问题好搜
│
├─ 多轮 / agentic（调工具、跑沙箱、和环境交互）
│   → SGLang 明显更优
│     理由：多轮对话每一轮都要重发前面全部历史，
│           SGLang 的 RadixAttention 前缀缓存命中率高得多（见 §4.3），
│           省下的是实打实的 prefill 算力。
│
├─ 你要做"动态采样 / 过采样 / 中途丢弃"
│   （比如：一个 prompt 采 16 条，发现前 8 条都对了，剩下的没必要采完）
│   → 必须 SGLang
│     理由：需要 abort-in-flight，即"把正在生成的请求中途掐掉"的能力。
│           vLLM 这块成熟得晚。
│
├─ 你要做全异步 RL（生成和训练同时跑）
│   → 必须 SGLang
│     理由：全异步需要 interruptible decoding（可打断解码，见 §4.3），
│           AReaL 和 slime 都因此绑死 SGLang。
│
└─ 你追求极限吞吐，且 rollout 逻辑很固定
    → 可以看 TensorRT-LLM（verl 0.7 起支持）
      但 RL 场景实际用的人很少，因为权重热更新这条路上坑更多。
```

**一句话总结**：`RL 选推理引擎，看的不是"生成多快"，而是"能不能被随时打断、能不能被随时换权重"。`

### 1.3 选编排层

大多数情况下这一项不是你选的，是框架帮你选好的。但你要知道它意味着什么：

```
你的集群长什么样？
│
├─ 一台机器 / 少量卡，自己跑实验
│   → accelerate + torchrun（TRL 走这条）
│     最简单，但只能做同构的、静态的任务分配
│
├─ 多机集群，需要给不同角色（actor / rollout / reward）分不同的卡
│   → Ray（verl、NeMo-RL、ROLL、slime、Miles 全用它）
│     Ray 提供 placement group：声明"我要 4 张卡给训练、4 张给生成"
│     它还提供 actor 模型，让你像调函数一样调远程进程
│
├─ 你在有 SLURM 的 HPC 集群上
│   → SLURM 直接调度（AReaL 早期走这条）
│     更贴近传统超算的运维习惯
│
└─ 你想要真正的容错 + 交互式调试
    → Monarch（TorchForge 走这条）
      能从 Jupyter notebook 里驱动整个集群，
      单进程崩了能恢复，不用整个 job 重来
```

### 1.4 选框架（主决策树）

现在把上面三条合起来。这是这份文档里最该记住的一张图。

```
你的首要目标是什么？
│
├─ ① 我要学 / 做研究 / 写论文 / 面试要讲得出来
│   │
│   ├─ 想接触最主流、遇到问题最容易搜到答案
│   │   → verl
│   │     生态最大，新算法（GRPO/DAPO/GSPO/……）第一时间有官方 recipe。
│   │     代价：抽象层厚，魔改要先读懂它的 controller 架构。
│   │
│   └─ 想把整个系统读完、真正搞懂 RL infra 是怎么回事
│       → slime
│         代码量小到能通读，没有中间抽象层，
│         Megatron 和 SGLang 的参数直接透传。
│
├─ ② 我要训一个真正的前沿模型（MoE、100B+）
│   │
│   ├─ 走开源社区路线
│   │   → slime（GLM 全系列的实际训练框架）
│   │     或 Miles（slime 的企业向下游，MoE 专项优化最狠）
│   │
│   └─ 走 NVIDIA 官方全家桶，要企业级支持和版本一致性
│       → NeMo-RL
│
├─ ③ 我的瓶颈是 GPU 利用率（生成太慢，训练卡在那儿等）
│   │
│   ├─ 任务是 RLVR（数学、代码这类可自动验证的）
│   │   → AReaL
│   │     全异步 + staleness 感知的目标函数，系统和算法一起解。
│   │
│   └─ 任务是 agentic（环境交互慢、有的环境会挂）
│       → ROLL
│         环境级异步 + 冗余环境副本，专治"环境比模型还慢"。
│
├─ ④ 我要做 agentic RL，且已经有一个线上跑着的 agent
│   → AReaL 2.0
│     不用重写 agent，把 LLM 调用的 base_url 指过去就能训。
│     详见第 7 章，这是目前最值得关注的方向。
│
├─ ⑤ 我只是想快速试试 GRPO / DPO，模型不大
│   → TRL
│     和 transformers / peft 无缝，一个 Trainer 类就跑起来了。
│     天花板在 ZeRO-3，别指望训 MoE。
│
└─ ⑥ 我想赌未来的架构，接受生态还浅
    → TorchForge
      PyTorch 官方出品，RL 代码写得像伪代码，容错是一等公民。
```

### 1.5 一张表看完对应关系

| 框架 | 训练后端 | rollout 后端 | 编排 | 抽象厚度 |
|---|---|---|---|---|
| `verl` | FSDP / FSDP2 / Megatron / VeOmni | vLLM / SGLang / TensorRT-LLM | Ray | 厚 |
| `NeMo-RL` | DTensor / Megatron-Core | vLLM / SGLang | Ray | 中 |
| `TRL` | DeepSpeed ZeRO / accelerate | vLLM | accelerate | 薄（但功能也少） |
| `ROLL` | Megatron-Core / DeepSpeed | vLLM / SGLang | Ray | 中厚 |
| `AReaL` | Megatron-Core | SGLang | SLURM / 自研 | 中 |
| `slime` | Megatron-LM | 只有 SGLang | Ray | 极薄 |
| `Miles` | Megatron-LM | 只有 SGLang | Ray | 极薄 |
| `TorchForge` | TorchTitan | vLLM | Monarch | 薄（新范式） |

"抽象厚度"的含义：**厚 = 换后端容易、魔改内部难；薄 = 换后端不可能、魔改内部容易。** 这是一个必然的取舍，没有免费的午餐。

## 2. 人格速写：八个框架的第一印象

这一章不讲技术，只给你直觉。把每个框架当成一个"人"来认识。

### verl —— 那个什么都支持的巨型系统

想象一个大型企业的 ERP 系统：**任何模块都可以插拔替换**，训练引擎换四种、推理引擎换三种，配置文件几百行。它的设计哲学是"我定义接口，你们都来适配"。

**优点**：生态最大。新算法出来第一时间有人在 verl 上实现；遇到问题一搜全是答案；简历上写它别人都认识。
**缺点**：抽象层厚。你想改一个底层行为，得先搞懂它的 controller / worker / DataProto 三层结构。它为了同时支持四种训练后端，很多地方只能取"最小公分母"。

**一句话**：`最主流、最可插拔、最难魔改。`

### slime —— 那个只做胶水的极简主义者

它的世界观和 verl 恰好相反：**我不做抽象，我只做胶水。** Megatron 的参数原样透传，SGLang 的参数加个前缀原样透传。上游有新优化，你直接就能用，不用等 slime 包一层。

它只支持 Megatron + SGLang 这一条路径，而且是**故意**的——理由是"支持多个推理引擎，就只能把它们压成最小公分母，反而用不了 SGLang 的独门能力"。

**它的分量**：GLM-4.5 一直到 GLM-5.2，整个系列的 RL 训练都是它跑的。这不是 demo，是量产线。

**一句话**：`最透明、最好读，但你只能走它规定的那一条路。`

### Miles —— slime 的"企业加强版"

由 RadixArk（SGLang 团队成立的公司）做的，和 slime 同一条技术路线（SGLang + Megatron + Ray），但专攻**大规模 MoE 训练里的正确性问题**。它解决的问题非常具体也非常致命，见 §6.7。

**一句话**：`slime 的下游硬核版，MoE RL 绕不开。`

### NeMo-RL —— NVIDIA 的正规军

英伟达自己的第一方 RL 框架，用来训他们的 Nemotron 系列。最大的价值不是某个功能，而是**整条链路是同一批人维护的**：CUDA、Megatron-Core、Transformer Engine、容器镜像、RL 框架，版本永远对得上。

有意思的血缘：它的前身 NeMo-Aligner 是最早的 LLM RL 库之一，verl、SkyRL、ROLL 都受它启发——这话是 NVIDIA 自己在 README 里写的。

**一句话**：`企业级、版本不打架，但你得接受整套 NV 生态。`

### TRL —— 不在同一个赛道的标准库

它其实**不是**一个"大规模 RL 系统"，而是 HuggingFace 生态里的 post-training 标准库。SFT、DPO、GRPO、KTO 一套统一 API，和 transformers / peft 无缝对接。

它的定位是：让你**十行代码跑起来一个 GRPO**。天花板也很明确——没有 Megatron，没有 5D 并行，上限就在 DeepSpeed ZeRO-3。

**一句话**：`入门最快，规模上不去，但它从来也没打算上去。`

### ROLL —— 那个把调度做到极致的

阿里出品。它的独特世界观是：**rollout 阶段的每一条样本，都应该被单独调度。** 别的框架按 batch 管理生成，它按单条请求管理——可以动态增加、可以中途取消。

而且它把"环境"和"打分"当成**独立的一等公民模块**（environment worker / reward worker），这在 agentic 场景很关键：环境可能很慢、可能会挂、可能是个真实的浏览器或数据库。

**一句话**：`调度粒度最细，最懂"环境比模型还麻烦"这件事。`

### AReaL —— 那个把异步做到底、还顺手解决了算法问题的

蚂蚁 + 清华 IIIS 出品。它的核心主张是：**生成和训练根本不该互相等待。** 生成器一直生成，训练器攒够一批就更新，谁也不等谁。

但它比别家多做了一件关键的事：**它承认全异步会让算法失效，并给出了算法侧的解法。** 这一点后面详讲，因为大多数框架只把异步当调度问题，AReaL 把它当成"系统+算法"的联合问题。

2026 年 7 月的 AReaL 2.0 更进一步，走向了"线上服务即训练"，这是第 7 章的主题。

**一句话**：`最激进的异步派，而且是唯一把异步的算法代价量化清楚的。`

### TorchForge —— PyTorch 官方的新范式

Meta / PyTorch 团队出品，建在 Monarch（新的分布式编程框架）之上。它的野心不是"再做一个 RL 框架"，而是**换一种写分布式 RL 的方式**：让你用 `async/await` 写 RL 逻辑，像写单机伪代码一样，分布式的复杂度全部藏在下面。

**一句话**：`最干净的新范式，最浅的生态，赌未来的选择。`

## 3. 训练引擎详解

### 3.1 先搞懂一件事：为什么模型要"切开"

一张 H100 有 80GB 显存。训练一个 7B 模型需要多少？

用 bf16 训练、Adam 优化器，粗算一下：

$$
\text{显存} \approx \underbrace{2P}_{\text{权重}} + \underbrace{2P}_{\text{梯度}} + \underbrace{12P}_{\text{Adam 状态(fp32 权重+m+v)}} = 16P
$$

其中 $P$ 是参数量。7B 模型就是 $16 \times 7\text{B} = 112\text{GB}$，**一张卡装不下**。再加上激活值（activation），还要更多。

所以必须"切开"。**怎么切**，就是所有训练引擎的分歧所在。一共有五种切法：

| 切法 | 全称 | 切什么 | 大白话 |
|---|---|---|---|
| **DP** | Data Parallel | 切数据 | 每张卡放一份完整模型，各自算不同的数据，最后把梯度加起来 |
| **TP** | Tensor Parallel | 切矩阵 | 一个大矩阵乘法拆成几块，几张卡各算一块，算完拼起来 |
| **PP** | Pipeline Parallel | 切层 | 第 1~10 层放卡 A，第 11~20 层放卡 B，像流水线一样传递 |
| **EP** | Expert Parallel | 切专家 | MoE 专用：不同的"专家"放在不同卡上 |
| **CP** | Context Parallel | 切序列 | 一条超长文本，前一半给卡 A、后一半给卡 B（注意力要跨卡通信） |

**关键直觉**：这五种切法的**通信代价差别巨大**。

- TP 通信最频繁（每一层都要 all-reduce），所以 TP 组必须放在同一台机器内，走 NVLink。跨机做 TP 会慢到不可接受。
- DP 通信最少（一步只同步一次梯度），可以跨机。
- PP 通信量小但会产生"气泡"（流水线开头和结尾有卡在闲着）。

真实的大规模训练是这几种的组合，叫 **5D 并行**，比如 `TP=8, PP=4, DP=16, EP=8`。**能不能玩这套组合，就是训练引擎的核心分水岭。**

### 3.2 DeepSpeed ZeRO —— 最早的"聪明的 DP"

微软出品。它的洞察是：既然 DP 里每张卡都存了一份**一模一样的**优化器状态和梯度，那不如切开分别存，用到的时候再临时拼回来。

| 阶段 | 切什么 | 省多少 |
|---|---|---|
| ZeRO-1 | 切优化器状态 | 省 4x |
| ZeRO-2 | + 切梯度 | 省 8x |
| ZeRO-3 | + 切权重 | 省 N 倍（N=卡数） |

**优点**：改动极小，一个配置文件就能开。
**缺点**：本质还是 DP，没有 TP/PP/EP，所以撑不起 MoE 和超长上下文。ZeRO-3 因为每层前向都要临时把权重收集回来（all-gather），通信开销大。

**现状**：在 RL 领域基本退居二线，只有 TRL 和早期的 ROLL 还在主用。

### 3.3 PyTorch FSDP / FSDP2 —— ZeRO-3 的官方亲儿子

FSDP（Fully Sharded Data Parallel）是 PyTorch 官方版的 ZeRO-3，思路一样：权重、梯度、优化器状态全切开，前向时临时聚合。

**FSDP2 是重写版**，底层换成了 **DTensor**（分布式张量）。

> **什么是 DTensor？** 大白话：一个"知道自己被切成了几块、每块在哪张卡上"的张量。你对它做的操作，PyTorch 自动帮你处理通信。有了这层抽象，重新排布（resharding）变成了一个标准操作，而不是每个框架自己手写一套。

**为什么 RL 特别喜欢 FSDP2**：

1. **权重格式和 HuggingFace 同构。** 不用做格式转换，存下来的 checkpoint 直接能上传 HF。
2. **resharding 便宜。** RL 每步都要把训练侧权重重排后送给推理引擎，DTensor 让这件事有标准做法。
3. **可组合。** 能和 LoRA、序列并行等特性叠加使用。

**天花板**：没有原生的 TP/PP/EP。虽然可以配合 Ulysses 之类的序列并行方案处理长文本，但训 MoE 或 100B+ 就吃力了。

### 3.4 Megatron-Core —— 没有天花板，但门槛高

NVIDIA 出品，就是 2019 年那篇张量并行论文的工程化产物。**它是唯一一个五种并行全都做得成熟的库。**

要区分三个名字（这是最容易搞混的地方）：

| 名字 | 是什么 |
|---|---|
| `Megatron-LM` | 参考实现，一个能直接跑的训练脚本仓库 |
| `Megatron-Core` | 从中抽出来的**库**，别人真正依赖的是它 |
| `Megatron-Bridge` | 2025 年后新增，做 HuggingFace ↔ Megatron-Core 的双向权重转换 + PyTorch 原生训练循环 |

**它的代价，具体是什么**：

1. **权重格式和 HuggingFace 完全不同构。** Megatron 内部按 TP/PP 切好的格式存，HF 是另一套。存取都要转换。这就是 Megatron-Bridge 存在的全部理由——而且它做的是**并行感知的逐参数转换**，不需要把整个模型在单卡上加载一遍。
2. **参数体系陡峭。** 几百个 flag，很多需要理解底层才能配对。
3. **RL 里的额外麻烦**：训练侧是 Megatron 的切法，推理侧是 vLLM/SGLang 的切法，每步同步权重都要做一次跨格式重排。这是 slime、Miles、AReaL 花了大量工程量的地方。

### 3.5 TorchTitan —— PyTorch 官方对标 Megatron 的答案

PyTorch 团队做的大规模训练平台，DTensor 原生，把 TP/PP/DP/CP 用 PyTorch 原生 API 表达出来。定位是"Megatron-Core 的官方替代"，但成熟度和生态还差一截。TorchForge 用它做训练后端。

### 3.6 VeOmni —— 字节的全模态训练框架

字节出品，面向多模态/全模态训练。verl 0.7 起把它加成了第四种训练后端。目前用的人还少，但如果你要做 VLM / Omni 的 RL，值得关注。

### 3.7 训练引擎横向对比

| | DeepSpeed ZeRO | FSDP2 | Megatron-Core | TorchTitan |
|---|---|---|---|---|
| 5D 并行 | ❌ 只有 DP 变体 | ⚠️ 主要 DP，需外挂 SP | ✅ 全套 | ✅ 大部分 |
| MoE (EP) | ⚠️ 有但不成熟 | ❌ | ✅ 最成熟 | ⚠️ 发展中 |
| HF 权重同构 | ✅ | ✅ | ❌ 需转换 | ⚠️ |
| resharding 成本 | 中 | 低（DTensor） | 高 | 低（DTensor） |
| 上手难度 | 低 | 低 | 高 | 中 |
| RL 里的地位 | 退场中 | 中小规模主力 | 大规模唯一解 | 新兴 |

**选择口诀**：`能用 FSDP2 就别碰 Megatron；MoE 和 100B+ 就别想 FSDP2。`

## 4. 推理 / rollout 引擎详解

### 4.1 先搞懂 LLM 推理的两个阶段

生成一段文本，机器内部分成两个性质完全不同的阶段：

**Prefill（预填充）**：把你输入的 prompt 一次性读进去，算出每个 token 的中间状态。这一步是**计算密集**的——1000 个 token 可以并行算，GPU 吃满。

**Decode（解码）**：一个一个往外吐 token。每吐一个都要读一遍全部模型权重，但只算一个 token 的量。这一步是**访存密集**的——GPU 算力大量闲置，瓶颈在显存带宽。

中间那些算好的状态存在 **KV cache** 里，避免每生成一个新 token 都要把前面重算一遍。KV cache 会随着序列变长而线性增长，是显存的主要消耗者之一。

理解这两个阶段，后面所有优化的动机就都清楚了。

### 4.2 vLLM —— 生态最大的默认选择

**核心技术 PagedAttention**：借用操作系统虚拟内存分页的思路来管 KV cache。

> **大白话**：以前给每个请求预留一整块连续显存，就像给每个人分一整间房，人少的时候浪费严重。PagedAttention 把显存切成固定大小的"页"，谁需要就分几页，用完还回去。显存利用率从 20~40% 提到 90%+，同时能服务的请求数翻好几倍。

**RL 场景要知道的一个特性 —— sleep mode**：当训练和生成**共用同一批 GPU**（叫 colocate，见 §5.3）时，训练的时候需要把 vLLM 的显存腾出来。sleep mode 就是让 vLLM 临时"睡觉"，释放 KV cache 和权重占的显存，训练完再唤醒。

**优点**：文档最全、社区最大、遇到问题好搜。
**在 RL 里的短板**：中途取消请求（abort）、可打断解码这类 RL 专属能力，成熟得比 SGLang 晚。

### 4.3 SGLang —— RL 圈的实际标准

由 LMSYS（做 Chatbot Arena 那批人）出品。

**核心技术 RadixAttention**：把 KV cache 按**前缀树（radix tree）**组织，自动复用相同前缀的计算结果。

> **为什么这对 agentic 特别重要**：多轮对话的第 5 轮，要把前 4 轮的全部内容重新发一遍。如果每次都重新 prefill，算力全浪费在重复内容上。RadixAttention 发现"这段前缀我算过"，直接复用。一个 agent 循环里同一个 2000 token 的 system prompt 反复出现，命中率能到 90%+。

**RL 专属的三个关键能力**（这也是 AReaL 和 slime 绑死它的原因）：

**① abort-in-flight（飞行中取消）**
> **大白话**：一条正在生成的请求，允许你中途喊停，立刻释放它占的显存和算力。
> **为什么需要**：做动态采样时，一个 prompt 采 16 条答案，如果前 8 条都答对了，剩下 8 条继续生成就是浪费。或者：训练侧已经攒够数据要更新权重了，正在生成的这些用旧权重的请求可以直接丢掉。

**② interruptible decoding（可打断解码）**
> **大白话**：比 abort 更精细——不是"丢掉"，而是"暂停并保留现场"。一条生成到一半的序列，可以在权重更新的瞬间被打断，**然后用新权重继续往下写**。
> **为什么需要**：全异步 RL 的核心难题是"生成到一半，权重变了怎么办"。选择丢掉太浪费（一条 8000 token 的推理链可能已经生成了 6000）；选择等它写完，又回到了同步的老问题。可打断解码给出第三条路：接着写。
> **⚠️ 但这里有个算法陷阱**：一条轨迹的前半段是旧权重写的、后半段是新权重写的，那么在算重要性采样比率（importance ratio）时，"这条数据是哪个策略产生的"这个问题就没有唯一答案了。AReaL 的论文正是证明了：不改目标函数直接这么干，模型会掉点。见 §6.5。

**③ 权重热更新接口**
SGLang 团队专门为 RL 场景做了自定义权重更新的支持——这不是普通推理服务需要的功能，是 RL 框架推着做出来的。

**其他值得知道的**：
- **P/D 分离（Prefill/Decode Disaggregation）**：把 prefill 和 decode 拆到不同的 GPU 组上跑。因为这两个阶段一个吃算力、一个吃带宽，混在一起互相干扰。
- **sgl-router**：一个前缀感知的路由器，把请求路由到"已经缓存了这段前缀"的那个实例上。如果路由随机，前缀缓存的收益就没了。

### 4.4 TensorRT-LLM —— 吞吐最高，RL 里最少见

NVIDIA 出品。**先说一个容易过时的认知**：它早期的模式是"把模型编译成一个针对具体 GPU 型号固化的 engine"，改配置就要重编译。现在它已经转成 **PyTorch-native 架构**，可以直接跑 HF 模型不必编译 engine，定位反而更接近 vLLM 了。

verl 0.7 起支持它作为 rollout 后端。但在 RL 场景实际用的人少——权重热更新这条路上的坑更多，而 RL 里权重是每几十秒就要换一次的。

### 4.5 HF Transformers 的 generate —— 只用来 debug

慢，但代码最简单、行为最可预期。所有框架都保留它，用途是：当你怀疑推理引擎和训练引擎算出来的概率对不上时，用它当 ground truth 对照。

### 4.6 RL 里评价推理引擎的三个真正的维度

这一节是本章的重点。**线上服务和 RL 对推理引擎的要求几乎是两套标准。**

| | 线上服务关心 | RL 关心 |
|---|---|---|
| 权重 | 加载一次，永不改变 | 每几十秒换一次，换的成本决定训练效率 |
| 请求 | 尽量都完成 | 经常需要主动丢弃 / 打断 |
| 数值 | 只要输出合理就行 | 必须和训练引擎算的概率对得上，否则梯度是错的 |

**维度一：权重同步怎么做**

训练侧算出新权重后，怎么送到推理侧？几种做法，效率差一个数量级：

| 方式 | 原理 | 代价 |
|---|---|---|
| 存 checkpoint 再加载 | 写硬盘、推理引擎重新读 | 最慢，几分钟级 |
| NCCL broadcast | 走 GPU 间通信直接广播 | 主流做法，秒级 |
| CUDA IPC zero-copy | 同一台机器上，直接共享显存指针，**完全不拷贝** | 最快，但只能同机 |
| RDMA（TorchStore） | 跨机的直接内存访问 | TorchForge 的路子 |

Miles 实现了 zero-copy CUDA IPC 权重同步，这是它的性能优势来源之一。

**维度二：能不能被打断**

见 §4.3 的 abort 和 interruptible decoding。这决定了你能不能做动态采样和全异步。

**维度三：训练-推理数值一致性（train-inference mismatch）**

这是一个很多人不知道、但**极其关键**的问题。

> **问题是什么**：同一个模型、同一段输入，vLLM 算出来的 token 概率，和 Megatron 前向算出来的，**不完全相等**。原因是两边用了不同的 kernel 实现、不同的算子融合方式、不同的批处理策略，浮点误差累积不同。
>
> **为什么致命**：PPO/GRPO 的核心是重要性采样比率
> $$r_t = \frac{\pi_\theta(a_t|s_t)}{\pi_{\text{old}}(a_t|s_t)}$$
> 分母来自推理引擎（生成时记录的概率），分子来自训练引擎（重新前向算的概率）。如果两个引擎本身就算不出同一个数，那么即使权重完全没变，$r_t$ 也不等于 1。这个偏差会被当成"策略变化了"，直接污染梯度。
>
> **各家的解法**：
> - TRL：默认开启 **Truncated Importance Sampling (TIS)**，对这个比率做截断修正。
> - verl：提供 rollout importance sampling，全异步模式下重算 rollout 的 log prob。
> - Miles：更根本的做法——**端到端统一 FP8 精度流**，让训练和推理用同一套数值路径，从源头消除 mismatch。

**这一条是 2025~2026 年 RL infra 最核心的议题之一。** 算法名字（GRPO / DAPO / GSPO）是最容易抄的部分；这三个维度才是框架之间真正的工程差距。

## 5. 编排层详解

### 5.1 编排层到底在管什么

一次 RL 训练里，同时有好几种角色的进程：

- **Actor**（被训练的模型，训练侧）
- **Rollout**（生成用的推理引擎）
- **Reference model**（算 KL 惩罚用的冻结模型）
- **Critic / Reward model**（打分模型，某些算法需要）
- **Environment worker**（跑沙箱、执行工具调用）

编排层要回答四个问题：
1. 这些角色各自占几张卡、占哪几张？
2. 进程怎么起来、怎么互相发消息？
3. 大块数据（几 GB 的权重、几万条轨迹）怎么传？
4. 某个进程崩了怎么办？

### 5.2 单控制器 vs 多控制器（最重要的概念）

这是理解 verl 架构的钥匙。

**多控制器（SPMD, Single Program Multiple Data）**：传统分布式训练的做法。你写一份代码，用 `torchrun` 起 8 个一模一样的进程，每个进程执行同样的逻辑，靠 `rank` 编号区分自己该干哪一份活。

> **大白话**：八个工人拿到同一份说明书，各自看自己的工号决定做哪一块。
> **优点**：高效，没有中心节点瓶颈。
> **缺点**：写复杂逻辑很痛苦。"先让 rollout 生成，再让 reward 打分，再让 actor 训练"这种流程，在 SPMD 里要靠一堆 barrier 和条件判断拼出来。

**单控制器（Single Controller）**：一个中心进程掌管全局流程，像写单机脚本一样调度所有远程 worker。

> **大白话**：一个工头拿着流程图，挨个指挥"你现在生成、你现在打分、你现在训练"。
> **优点**：RL 的复杂流程写起来非常自然，就是一段普通的 Python。
> **缺点**：中心节点可能成瓶颈。

**verl 的 HybridFlow 就是把两者结合**：上层用单控制器写 RL 流程（生成→打分→训练），每个 worker 组内部还是 SPMD 高效执行。这个设计是它论文的核心贡献，也是它能自由更换后端的根本原因——因为流程逻辑和计算实现被彻底分开了。

ROLL 也采用单控制器架构。TorchForge 则是把单控制器做到了极致：整个 RL 循环写成 `async/await` 的普通 Python。

### 5.3 放置策略：colocate vs 分离

**colocate（共置）**：训练和生成**共用同一批 GPU**，轮流使用。

```
时间轴 ────────────────────────────────────────►
GPU 0-7:  [生成 rollout] → [训练更新] → [生成 rollout] → ...
          ↑ vLLM 占显存      ↑ vLLM sleep，Megatron 占显存
```
- 优点：卡少的时候唯一可行的方案，不浪费资源
- 缺点：切换时要反复腾挪显存（offload / sleep），有额外开销；而且两边必须**串行**，气泡消不掉

**分离（disaggregated）**：训练和生成各占一批卡，同时运行。

```
GPU 0-3:  [持续生成 生成 生成 生成 ...]
GPU 4-7:  [训练][训练][训练][训练]...
```
- 优点：可以真正做异步，两边同时满负荷
- 缺点：卡要更多；权重要跨节点传；两边负载配比不对就有一边闲着

**你上一轮踩的坑就在这里**：一旦分离，rollout 那批卡上不只有 vLLM，还有权重同步用的缓冲区，显存预算要重新算。

### 5.4 三档同步性

| 档位 | 做法 | 数据新鲜度 | GPU 利用率 |
|---|---|---|---|
| **同步（on-policy）** | 生成完一整批 → 训练 → 再生成 | 完全新鲜 | 低（等最慢的那条） |
| **one-step-off** | 生成第 N+1 批的同时，训练第 N 批 | 落后一步 | 中高 |
| **全异步（fully async）** | 生成器一直生成，训练器攒够就更新 | 落后不定，需要限制 | 最高 |

> **staleness（陈旧度）是什么**：一条训练数据，是用几步之前的权重生成的。同步 RL 的 staleness = 0。全异步下，如果不加限制，可能出现"用 20 步前的权重生成的数据，拿来更新现在的模型"——这在数学上已经不是原来那个算法了。

**关键认知**：异步不是免费的午餐。它把一个**系统问题**（GPU 闲置）转化成了一个**算法问题**（off-policy 偏差）。AReaL 的核心贡献就是把这个转化的代价量化清楚，并给出了算法侧的补偿。

### 5.5 各编排层的特性

| | accelerate + torchrun | Ray | SLURM | Monarch |
|---|---|---|---|---|
| 出品 | HuggingFace / PyTorch | Anyscale | HPC 传统 | Meta / PyTorch |
| 编程模型 | SPMD | Actor（远程对象） | 批作业提交 | Actor mesh + 单控制器 |
| 异构角色分配 | ❌ 困难 | ✅ placement group | ⚠️ 靠脚本拼 | ✅ |
| 大块数据传输 | NCCL | Ray object store（有序列化开销） | 自己解决 | RDMA 直传 |
| 容错 | ❌ 一个挂全挂 | ⚠️ 部分 | 重新排队 | ✅ 一等公民 |
| 交互式调试 | ❌ | ⚠️ | ❌ | ✅ 能从 notebook 驱动集群 |
| 谁在用 | TRL | verl / NeMo-RL / ROLL / slime / Miles | AReaL | TorchForge |

**Ray 为什么成了事实标准**：它的 placement group 让你能声明式地说"我要 4 张卡放训练、4 张放生成，且必须在同一个节点上"，而 Actor 模型让远程进程能像本地对象一样被调用。这两点恰好是 RL 的刚需。

**Ray 的代价**：数据在 Ray object store 里传递有序列化/反序列化开销，几 GB 的张量走这条路不划算——所以框架们通常绕开 Ray 传大块权重，改走 NCCL 或 CUDA IPC。

## 6. 框架逐个详解

每个框架按同一个模板讲：**它的世界观 → 独门武器 → 适合谁 → 代价**。

### 6.1 verl（字节 Seed）

**世界观**：RL 算法是一张多阶段、多模型的**数据流图**。框架的职责是把这张图的"流程"和"计算"彻底分开，这样任何计算引擎都能插进来。

**独门武器：Hybrid-Controller 架构**

高层是单控制器：一个 `RLTrainer` 进程管全局计算图，负责调度生成、触发打分、分发训练任务。底层每个 worker 组内部是标准 SPMD 分布式训练。这个设计的直接后果就是**后端矩阵最全**——训练侧 FSDP / FSDP2 / Megatron / VeOmni，生成侧 vLLM / SGLang / TensorRT-LLM，随便组合。

**其他值得知道的**：
- 规模上到 671B + 专家并行，是开源框架里验证过的最大规模之一
- `AgentLoop` 抽象：多轮 / 工具调用的 rollout 逻辑从早期的 ChatScheduler 迁移到了这里
- v0.7（2026 年初）引入 Model Engine 和 rollout server 抽象，把全异步从 recipe 转正

**适合谁**：想要生态和通用性的人；做算法研究需要频繁换 baseline 的人；简历需要一个"别人都认识"的框架的人。

**代价**：抽象层厚。为了同时支持四种训练后端，很多地方只能取最小公分母。你要改底层行为，得先读懂它的三层架构。slime 明确说"不做 lowest-common-denominator 抽象"，针对的就是这一点。

### 6.2 slime（清华 THUDM / 智谱）

**世界观**：**不做抽象，只做胶水。** 抽象是有成本的——一旦你在 Megatron 和 SGLang 之上包一层，上游的新优化你就用不了，必须等胶水层跟进。

**独门武器一：参数直通**

Megatron 的参数原样透传，SGLang 的参数加 `--sglang-` 前缀原样透传。上游有新功能，你今天就能用。

**独门武器二：故意只绑一个 rollout 后端**

这不是能力不足，是刻意选择。理由：支持多个推理引擎，就只能把它们压成最小公分母，反而用不上 SGLang 独有的路由、缓存、P/D 分离和权重同步行为。

**独门武器三：为"RL bug 不会报错"这件事做的设计**

保持数据流显式可见，支持 **rollout-only 和 train-only 分离调试**——你可以只跑生成这一半，或只跑训练这一半，单独验证。把可复现性、容错、trace、profiling 和 CI 当成一等工程问题维护。

> **为什么这很重要**：前面 §0.2 说过，RL 的 bug 不会抛异常，只会让指标慢慢变差。能把系统劈成两半单独验证，是定位这类问题的唯一实用手段。

**分量**：GLM-4.5、4.6、4.7、5、5.1、5.2 全系列的 RL 训练框架。这是量产线，不是 demo。

**适合谁**：想真正读懂 RL infra 的人（代码量小到能通读）；确定走 Megatron + SGLang 这条路的团队。

**代价**：换不了后端。而且和 SGLang / Megatron 的具体 commit 强绑定，官方 Docker 镜像把版本 pin 死了——好处是环境不会打架，坏处是升级要跟着它的节奏。

### 6.3 NeMo-RL（NVIDIA）

**世界观**：RL 框架不该是孤立的一层，应该和整条 NV 软件栈（CUDA、Megatron-Core、Transformer Engine、容器）一起演进。

**独门武器一：第一方一致性**

CUDA、驱动、Megatron-Core、TE、NGC 容器、RL 框架，全是同一批人维护，版本永远对得上。这听起来平淡，但任何被 CUDA / PyTorch / vLLM 三方版本冲突折磨过的人都知道它值多少钱。

**独门武器二：双训练后端 + LoRA 全覆盖**

DTensor 和 Megatron-Core 两条路都支持，且**两条路都支持 LoRA SFT 和 LoRA GRPO**。这意味着你可以先用 DTensor 快速验证，再切到 Megatron 上规模，代码不用重写。

**独门武器三：内建 on-policy distillation**

学生模型生成 on-policy 序列，用 KL 对齐更大的 teacher 的 logits，以比 RL 更低的成本逼近大模型质量。这是一个独立于 RL 的后训练方法，NeMo-RL 把它做成了一等公民。

**血缘**：它是 NeMo-Aligner 的重构版，而 NeMo-Aligner 是最早的 LLM RL 库之一——verl、SkyRL、ROLL 都受它启发（NVIDIA 自己在 README 里承认的）。所以你会发现这些框架的很多概念是同源的。

**配套**：NVIDIA 还配了 NeMo Gym（环境和 reward 的配套件），把 agentic RL 需要的环境抽象也补上了。

**适合谁**：企业环境；想要一套官方支持、不折腾版本的团队；要训 Nemotron 系列或用 NV 官方 recipe 的人。

**代价**：你得接受整套 NV 生态和它的节奏。

### 6.4 TRL（HuggingFace）

**世界观**：post-training 应该像 `model.fit()` 一样简单。

**独门武器一：统一 API**

SFT / DPO / GRPO / KTO / RLOO 一套 Trainer 接口，和 transformers、peft、accelerate 无缝。十行代码起一个 GRPO。

**独门武器二：默认开启 Truncated Importance Sampling**

这点很多人不知道：TRL 对 vLLM 生成**默认开启** TIS 来纠正训练框架和推理框架之间的数值 mismatch（就是 §4.6 讲的那个问题）。别的框架大多要你自己意识到并手动配。对新手来说，这是一个"默认就对"的重要保护。

**独门武器三：vLLM 的两种模式做得很清楚**
- `colocate`：vLLM 跑在 trainer 进程内，共享 GPU 显存，不用另起服务
- `server`：vLLM 独占若干张卡，通过 HTTP 通信

**近期动向**：加了 `AsyncGRPOTrainer`；GRPOTrainer 支持**逐样本选择环境**、环境自带 reward，可以在一个 run 里混多个沙箱任务套件（对接 Harbor / OpenEnv）。也就是说它也在往 agentic 走了。

**适合谁**：入门；单卡到单机八卡；模型 ≤ 8B；只是想验证一个算法想法。

**代价**：天花板是 DeepSpeed ZeRO-3。没有 Megatron，没有 5D 并行，别指望训 MoE 或 100B+。

### 6.5 AReaL（蚂蚁 + 清华 IIIS）

**世界观**：生成和训练不该互相等待。而且——**光解决系统问题不够，异步带来的算法问题必须一起解**。

**独门武器一：全异步 + 可打断解码**

生成器持续不断地生成，训练器攒够一批就更新，谁也不等谁。配合 §4.3 讲的 interruptible decoding，一条生成到一半的序列可以在权重更新时被打断，然后用新权重继续。

**独门武器二（真正的差异点）：decoupled PPO objective**

这是 AReaL 最该被记住的贡献。它的论文做了一个关键消融：

> 在有 staleness 的情况下，**朴素 PPO 追不上同步 RL 的效果**——即使 staleness 很小也会掉点。原因是 clipping 的中心锚错了：PPO 的裁剪是围绕"产生这条数据的那个策略"做的，但异步下这个策略是模糊的（前半段旧权重、后半段新权重）。
>
> 引入 **decoupled PPO objective**（把"行为策略"和"裁剪锚点"解耦）后，稳定性才拉回来。而且即使有了这个目标函数，**无界的 staleness 依然会掉点**——必须设一个上界。
>
> 最终结果：同样 GPU 数下 **2.77× 加速**，且最终精度持平或更好。

**为什么这条特别值得你注意**：大多数框架把异步当纯调度问题（"我把气泡填上了，快了 2 倍"）。AReaL 是唯一一个明确说清楚"异步会让算法失效，代价是多少，怎么补"的。如果你要做异步 RL 的研究，这篇消融是绕不开的起点。

**独门武器三：AReaL 2.0 的 agent 微服务架构** —— 见第 7 章，单独讲。

**适合谁**：GPU 利用率是主要瓶颈的场景；做异步 RL 研究的人；有线上 agent 想直接训的人。

**代价**：训练后端只有 Megatron-Core，rollout 只有 SGLang，灵活性低。

### 6.6 ROLL（阿里）

**世界观**：rollout 阶段的每一条样本都应该被单独调度；环境和打分应该是独立的一等公民。

**独门武器一：sample 级的 Rollout Scheduler**

别的框架按 batch 管理生成，ROLL 按**单条样本**管理请求生命周期——可以根据当前资源和生成进度**动态增加或中止**请求。

> **为什么这有用**：GRPO 需要对同一个 prompt 采 N 条答案来算组内相对优势。如果 16 条里前 8 条方差已经足够了，后 8 条就可以砍掉，算力省下来去跑新 prompt。batch 级调度做不到这种精细控制。

**独门武器二：环境级异步 + 冗余环境副本**

这两个是 agentic RL 专属的机制：
- **环境级异步 rollout**：GPU 不必等环境返回。agent 调一个工具可能要等 3 秒（跑单元测试、访问数据库），这 3 秒 GPU 不该闲着。
- **冗余环境 rollout（redundant environment rollout）**：同一个任务开多个环境副本，谁先返回用谁。真实环境会超时、会挂、会被限流，冗余是对抗长尾的标准手段。

效果：RLVR 任务快 2.24×，agentic 任务快 2.72×。

**独门武器三：StepWise 和 TrajectoryWise 双范式**

ROLL 同时支持 TrajectoryWise（StarPO，整条轨迹一个奖励）和 StepWise（GiGPO，每一步一个奖励）两种训练范式。

> **这个区别很重要**：一个 agent 做了 20 步最后失败了，你是给这 20 步全部打负分（TrajectoryWise），还是要找出到底哪一步走错了（StepWise）？后者就是**步级信用分配**问题，是长程 agentic RL 最核心的难题之一。ROLL 是把它做进框架的少数派。

**适合谁**：agentic RL；环境异构或不可靠的场景；多任务混合训练（它支持按 domain 配 batch 比例）。

**代价**：抽象比 slime 厚，比 verl 生态小。

### 6.7 Miles（RadixArk）

RadixArk 是 SGLang 团队成立的公司。Miles 是 slime 的企业向下游，同样是 SGLang + Megatron-LM + Ray。

**独门武器：Rollout Routing Replay（R3）**

这是一个**只有做 MoE RL 才会撞上、但撞上就是灾难**的问题：

> **问题**：MoE 模型每个 token 都要经过一个 router，决定送给哪几个专家。生成的时候（推理引擎里）路由做了一组决策；训练重新前向的时候（训练引擎里）router 又算一遍——**这两次的结果可能不一样**。
>
> 原因是推理和训练的 kernel 实现不同、批处理方式不同、数值精度不同，router 的 logits 差一点点，argmax 就可能选到不同的专家。
>
> **后果**：你以为你在对"生成这条数据的那个模型"算梯度，实际上你算的是"另一个专家组合"的梯度。重要性采样比率彻底失效，策略更新被污染。这是 §4.6 那个 mismatch 问题在 MoE 上的**放大版**——稠密模型只是数值有偏差，MoE 是**走了完全不同的计算路径**。
>
> **R3 的解法**：把 rollout 时的路由决策**记录下来，在训练时重放**，强制两边走同一条路径。

**其他落地的东西**：端到端统一 FP8 精度流、INT4 QAT 闭环、zero-copy CUDA IPC 权重同步、TIS/MIS off-policy 修正、投机解码式的 RL。

**架构上的一个好设计**：它直接接进 Megatron 的参数解析、模型构建和分布式 checkpoint 格式，而不是把 Megatron 包成黑盒。新模型架构通过**插件式的 spec 文件**加入，不用长期维护一个 Megatron fork。

**适合谁**：做 MoE 的大规模 RL；追求极限性能和数值正确性的团队。

**代价**：比 slime 更新、社区更小。

### 6.8 TorchForge（Meta / PyTorch）

**世界观**：研究者不应该写分布式系统代码。RL 逻辑应该像伪代码一样自然。

**它建在四个东西上**：
- **Monarch**：新的单控制器分布式编程框架，提供 actor mesh、RDMA 数据传输、容错
- **TorchTitan**：训练后端
- **vLLM**：生成后端
- **TorchStore**：一个分布式的、内存中的 PyTorch 张量键值存储，专门为**权重同步**设计，能自动做 DTensor 重排布

**独门武器一：容错是一等公民**

Monarch 声称在 16K GPU 的作业上，进程恢复 90 秒、机器恢复 2.5 分钟。传统 SPMD 训练是"一个进程挂了，整个 job 重来"。

**独门武器二：交互式调试**

能从 Jupyter notebook 驱动整个 GPU 集群，工作区同步、分布式断点。这在调试 RL 这种"跑半小时才看得出不对"的任务上，价值很大。

**独门武器三：TorchStore 解权重同步**

把 §4.6 讲的权重同步问题抽象成一个 KV store：训练侧 put，推理侧 get，中间的 DTensor 重排布自动完成。

**适合谁**：赌 PyTorch 官方路线的人；对容错和调试体验有强需求的人。

**代价**：最新，生态最浅，踩坑的时候可能没人踩过。

## 7. 专题：AReaL 2.0 的「agent 微服务」意味着什么

这一章单独讲，因为它可能是这份文档里**最值得你花时间的部分**。

### 7.1 先看清楚传统做法有多别扭

假设你已经有一个跑在线上的 agent——比如一个客服 agent，或者一个代码助手。它有自己的一套代码：planning 逻辑、工具调用、沙箱、记忆模块。这套东西叫 **agent harness**（agent 骨架）。

现在你想用 RL 让它变强。传统流程是这样的：

```
线上的 agent（真实用户在用）
    │
    │  ❌ 完全不相通
    │
    ▼
你另外搭一套训练环境：
    ① 在 RL 框架里重新实现一遍 agent 的逻辑
       （框架的多轮 rollout 接口是它自己定义的，你得适配）
    ② 造一批模拟任务和模拟环境
    ③ 训完，把新权重导出
    ④ 部署上线
    ⑤ 观察线上效果，发现和离线测的不一样
    ⑥ 回到 ①，改模拟环境，再来一遍
```

这个流程有四个硬伤：

1. **实现两遍**。线上一套 agent 逻辑，训练框架里再写一套。两套必然会漂移，而且漂移了你还不知道。
2. **环境是假的**。你精心构造的模拟环境，和真实用户提出的千奇百怪的请求，分布永远对不上。模型在模拟环境里刷到 95 分，上线掉到 70 分是常态。
3. **数据是造的**。你得自己想 prompt、自己造任务。而线上每天有海量真实交互流过，全部浪费了。
4. **循环周期以周计**。训练→导出→部署→观察→改环境，一轮下来一两周。

### 7.2 AReaL 2.0 做了什么

它的做法是把整个关系**倒过来**：

> **不要把 RL 当成一条离线的、和线上部署脱节的后训练流水线；而是把 rollout 和 training 用的那些 GPU worker，包装成可以插进任何在线 agent 服务的微服务组件。**

具体形态：

```
    你现有的 agent 服务（planning / 工具 / 沙箱 / 记忆 全部不动）
                        │
                        │  只改一行：base_url 指向 AReaL 的 gateway
                        ▼
    ┌───────────────── Gateway ─────────────────┐
    │                    │                      │
    │                 Router                    │
    │                    │                      │
    │              Data Proxy                   │
    │                    │                      │
    │        ┌───────────┴───────────┐          │
    │        ▼                       ▼          │
    │  Agent-compute worker      轨迹记录        │
    │  （原来的 rollout worker）      │          │
    │        │                       ▼          │
    │        │                  在线 RL 训练循环  │
    │        │                       │          │
    │        └───── 权重更新 ◄────────┘          │
    └───────────────────────────────────────────┘
```

对 agent 服务来说，它调用的还是一个**普通的 OpenAI 兼容 API**。它不知道后面接的不是推理服务，而是一个"边服务、边记录、边训练"的系统。

官方给的例子直白到有点粗暴：训练你自己的 agent，只需要把 `base_url` 和 `api_key` 换成 AReaL 的 RL 服务——不改任何代码，任何 agentic runtime 都能用。

### 7.3 为什么这件事的潜力很大

我按"从直接到深远"排列。

#### ① 训练数据从"造"变成"捡"

这是最直接的收益。你的 agent 每天服务 10 万次请求，每一次都是一条**真实分布下的轨迹**：真实用户的意图、真实的工具返回、真实的失败模式。传统做法这些全部丢掉，现在它们直接变成训练数据。

**类比**：以前是自己出模拟题练习，现在是把真实考卷收上来当训练集。

#### ② 环境问题被彻底绕过

agentic RL 最贵的部分从来不是训练，是**环境**。你要搭沙箱、要 mock API、要造数据库、要模拟网络故障——而且搭出来的还是假的。

这个架构下，**生产系统本身就是环境**。你不用模拟浏览器，用户的真实浏览器就是环境；你不用 mock 数据库，真实数据库就是环境。这一下省掉了 agentic RL 项目里可能 60% 的工程量。

#### ③ 分布对齐问题消失了

离线训练最大的隐疾是 **train-serving 分布不一致**：训练时见到的任务分布，和线上真实分布不一样。你在离线环境上的所有指标提升，都可能在线上打折甚至反转。

在线 RL 直接消除了这个 gap——训练分布**就是**服务分布，定义上没有偏差。

#### ④ 从"训练一次"变成"持续进化"

传统模型是一个**静态快照**：训完就冻结，直到下一次训练。这个架构下，模型可以持续从最新的交互中学习。用户的使用方式变了、工具的 API 改了、出现了新型任务——模型能跟着变，而不是等下一次训练周期。

这就是所谓的 **data flywheel（数据飞轮）**：用得越多 → 轨迹越多 → 模型越强 → 用得更多。之前这个飞轮只有大厂用人工标注 + 定期重训才转得起来，而且转一圈以月计。现在原则上可以转得快得多。

#### ⑤ agent harness 和 RL 框架解耦了

这一点从架构审美上讲最漂亮，长期影响也最大。

以前 RL 框架要支持 agentic，就得自己定义一套多轮 rollout 接口（verl 的 AgentLoop、ROLL 的 environment worker……），然后每个 agent 框架去适配。结果是 **N 个 agent 框架 × M 个 RL 框架 = N×M 的适配工作量**。

现在的契约变成了「OpenAI 兼容的 HTTP API」——一个**所有人都已经实现了**的标准。任何 agent 框架（LangGraph、自研 harness、Claude Code 式的命令行 agent）都自动可训，不需要为 RL 做任何适配。

**N×M 变成了 N+M。** 这是所有成功的解耦（比如 LSP 之于编辑器和语言、MCP 之于模型和工具）的共同特征。

#### ⑥ 多租户 / 多 agent 共享一个 RL 后端

既然接口是 HTTP，那么多个不同的 agent 服务可以共享同一套 RL 基础设施。一个团队维护 RL 后端，各业务线把 base_url 指过来，各自训各自的策略（或共享一个基座）。这在企业内部是很现实的形态。

#### ⑦ 反过来看：它让"评测"和"训练"合一

一个容易被忽略的推论：如果线上流量能进训练循环，那它同样能进**评测**循环。你可以对同一批真实请求做 A/B——一部分走旧权重、一部分走新权重，直接在真实分布上比较。评测不再是一个离线的、和训练脱节的环节。

### 7.4 但它难在哪：三个真问题

我不希望你只看到潜力。这条路有三个硬障碍，而且都不好解。

#### 障碍一：reward 从哪来（最大的）

线上真实轨迹**没有标准答案**。数学题可以对答案，代码可以跑单测，但"用户问了个客服问题，agent 回答了"——这条轨迹是好是坏？

可用的信号都很弱：
- 用户有没有追问 / 有没有骂人（隐式反馈，噪声极大）
- 用户有没有点赞（覆盖率极低，通常 <1%）
- 任务有没有完成（很多任务根本没有明确的完成信号）
- 用另一个模型当裁判（引入裁判模型的偏差，且贵）

**这是整条路线的真正瓶颈。** 系统架构再优雅，reward 不可靠，学出来的东西就不可靠——甚至可能学到"讨好用户"而不是"把事情做对"。

#### 障碍二：在线学习的经典陷阱

一旦模型从自己的输出中学习，就形成了**反馈回路**，几个经典风险全部激活：

- **分布漂移 / 模式坍缩**：模型倾向于产生它擅长的那类回答，这类回答又变成训练数据，进一步强化这个倾向。多轮之后行为空间越来越窄。
- **灾难性遗忘**：为了适应最近的流量，把之前的能力忘掉了。
- **被污染 / 被攻击**：如果有人故意用特定模式刷你的服务，理论上可以影响你的模型。
- **不可复现**：线上流量不可重放，某一天模型变差了，你很难回溯到底是哪批数据造成的。

传统离线训练至少有"数据集是固定的、实验可复现"这个安全垫。在线 RL 把它拆掉了。

#### 障碍三：工程上的新要求

这个架构对 infra 提出了传统 RL 没有的要求：

- **每条请求要打权重版本标记**。否则你不知道这条轨迹是哪个策略产生的，重要性采样比率就没法算——直接回到 §4.6 和 §5.4 讲的 staleness 问题，只不过现在 staleness 是由**真实流量的到达时间**决定的，你控制不了。
- **轨迹存储和回放**。真实交互要完整记录（包括工具调用和返回），量很大。
- **服务质量不能降**。这是生产系统，你不能因为在训练就让用户等。权重更新的瞬间不能有可感知的延迟尖峰。
- **隐私和合规**。真实用户数据进训练循环，这在很多场景下是硬性的法务问题。

### 7.5 这对你意味着什么

你在做的那个训练侧 runtime 项目，本质上问的是同一个问题：**训练系统和服务系统的边界应该划在哪里。**

传统答案是"划得很清楚"：训练是训练，服务是服务，中间用 checkpoint 文件连接。AReaL 2.0 的答案是"不划"：同一批 GPU worker，既是服务的推理后端，又是训练的 rollout 来源。

这个视角有两个具体的可迁移之处：

1. **接口选择决定了生态**。它选择"OpenAI 兼容 HTTP"而不是"我自己定义一套 rollout 接口"，这个选择本身就是它最大的杠杆——因为这个接口所有人都已经实现了。你设计任何 runtime 时都该问：我的契约是不是别人已经在用的东西？
2. **权重版本要成为一等公民**。一旦训练和服务混在一起，"这次调用用的是哪个版本的权重"就必须是系统里可查询、可传播的一等信息，而不是一个隐含状态。这一条在你的 runtime 设计里可以直接用上。

如果要深挖，建议按这个顺序读：先读 AReaL 原始论文（理解全异步 + decoupled PPO 的算法基础），再读 AReaL 2.0 的架构描述（理解微服务化怎么做的），最后自己想清楚 reward 那一环在你的场景里怎么解——因为那才是决定这条路走不走得通的地方。

## 8. 术语速查表

| 术语 | 大白话 |
|---|---|
| **rollout** | 模型生成答案的过程（RL 里"采样"的意思） |
| **on-policy / off-policy** | 训练用的数据是不是当前这个模型产生的。是=on-policy，不是=off-policy |
| **staleness（陈旧度）** | 一条数据是用几步之前的权重生成的 |
| **weight sync（权重同步）** | 把训练侧的新权重送到推理引擎 |
| **resharding（重排布）** | 权重在不同的并行切法之间转换排布 |
| **colocate（共置）** | 训练和生成共用同一批 GPU，轮流使用 |
| **disaggregated（分离）** | 训练和生成各占一批 GPU，同时运行 |
| **KV cache** | 生成时缓存的中间状态，避免重复计算 |
| **prefill / decode** | 读入 prompt 的阶段 / 逐个吐 token 的阶段 |
| **PagedAttention** | vLLM 的显存管理法，像操作系统分页一样管 KV cache |
| **RadixAttention** | SGLang 的前缀缓存，自动复用相同开头的计算结果 |
| **abort-in-flight** | 把正在生成的请求中途掐掉，立刻释放资源 |
| **interruptible decoding** | 生成到一半可以被打断，换新权重后接着写 |
| **P/D 分离** | prefill 和 decode 拆到不同 GPU 组上跑 |
| **sleep mode** | 让 vLLM 临时释放显存，把卡让给训练 |
| **train-inference mismatch** | 训练引擎和推理引擎算出的概率不完全一致 |
| **TIS / MIS** | 截断式重要性采样，用来修正上面那个 mismatch |
| **R3 (Rollout Routing Replay)** | MoE 专用：把生成时的专家路由决策重放到训练时 |
| **DP / TP / PP / EP / CP** | 切数据 / 切矩阵 / 切层 / 切专家 / 切序列 |
| **ZeRO** | DeepSpeed 的显存优化，把优化器状态和梯度切开存 |
| **FSDP** | PyTorch 官方版的 ZeRO-3 |
| **DTensor** | 知道自己被切到哪些卡上的分布式张量 |
| **SPMD / 多控制器** | 起 N 个一样的进程，各自看编号干活 |
| **单控制器** | 一个中心进程指挥所有远程 worker |
| **placement group** | Ray 里声明"我要几张卡、放在哪"的机制 |
| **agent harness** | agent 的骨架代码：planning、工具调用、记忆等 |
| **MFU** | 模型算力利用率，实际 FLOPs / 理论峰值 FLOPs |
| **RLVR** | 有可验证奖励的 RL（数学、代码这类能自动判对错的） |
| **GRPO** | 对同一 prompt 采 N 条答案，用组内相对好坏当优势，省掉 critic 模型 |

## 9. 学习路径建议

**第一阶段：跑通一个最小闭环（1~2 周）**

用 `TRL` 在单机上跑一个 GRPO，模型选 0.5B~1.5B，任务选 GSM8K 这类有标准答案的。目标不是效果，是**看清楚循环的四个动作**。重点观察：日志里的 reward 曲线、KL 值、生成长度的变化。

**第二阶段：理解 infra 的复杂度来自哪里（2~4 周）**

用 `verl` 跑同一个任务，对比它比 TRL 多做了什么。重点读三处代码：
1. 单控制器怎么调度 worker（`single_controller/`）
2. 权重同步怎么实现的（`workers/rollout/` 里的 update_weights）
3. colocate 模式下显存怎么腾挪的

**第三阶段：读一个能读完的系统（2~3 周）**

读 `slime` 的源码。它小到能通读，而且没有中间抽象层，所以你看到的就是"Megatron 和 SGLang 真实的接口长什么样"。读完你对 RL infra 的理解会上一个台阶。

**第四阶段：按方向深挖**

- 关心**异步和算法**：读 AReaL 论文的消融实验部分
- 关心 **agentic 和步级奖励**：读 ROLL 的 GiGPO 实现
- 关心 **MoE 和数值正确性**：读 Miles 的 R3
- 关心**架构未来**：读 AReaL 2.0 和 TorchForge

**一个建议**：不要试图同时学四个框架。选一个主力（verl 或 slime），把它读透，其他的只读"别家没有的那一点"对应的那一块代码。框架之间 80% 的东西是同源的——毕竟它们大多受 NeMo-Aligner 启发。
