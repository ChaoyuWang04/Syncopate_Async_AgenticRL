## 1 · 问题与预测

**问题**：`old_log_prob` 为什么是 `ref` 的 1.95×？两者都是纯前向。

**★ 预测（写死于 `scripts/infra/bench_cpu_snapshot.py` 文件头）**：
- **H1**：全量快照（~8 GB、数百张量、非 pinned）单趟 **2–8 s**
- **H2**：平均每步搬运 **9–25 s** ⇒ 能解释 **37 s** 缺口的大部分
- **H3**：只存 `requires_grad=True`（LoRA）⇒ **省 50× 以上**，单趟 <0.2 s


## 3 · 方法

读码定位调用序列（`fully_async_trainer.py:465` `_compute_old_log_prob`）：

```
local_trigger_step == 1 :  save_model_to_cpu(1)                        → 1 趟 D2H
local_trigger_step >= 2 :  save_model_to_cpu(cur)                      → 1 趟 D2H
                           restore_model_from_cpu(1)   ← 换成 π_old    → 1 趟 H2D
                           <前向：算 old_log_prob>
                           restore_model_from_cpu(cur) ← 换回当前      → 1 趟 H2D
                           clear_cpu_model(cur)
```

⇒ `--sync-every 4` 下：3/4 的步走「重步」（1 save + 2 restore），1/4 走「轻步」（1 save）。

分别计时「全量」与「仅 `requires_grad=True`」两种实现，按上述序列加权换算每步成本。

## 4 · 数据

### 4.1 参数构成

```
全部参数       902 个张量   8.309 GB
可训练(LoRA)   504 个张量   0.264 GB   ← 占 3.18%
```

### 4.2 单趟耗时

| 操作 | 全量 (s) | 仅 LoRA (s) | 加速 |
|---|---|---|---|
| `save_model_to_cpu` (D2H) | **3.579** | 0.037 | **96.1×** |
| `restore_model_from_cpu` (H2D) | 0.506 | 0.030 | 16.6× |

★ **D2H 比 H2D 慢 7 倍**——非 pinned 内存 + 902 次逐张量小拷贝的典型形状。

### 4.3 按实际调用序列换算

| | 全量 | 仅 LoRA |
|---|---|---|
| 重步（3/4 步：save + 2×restore） | 4.59 s | 0.098 s |
| 轻步（1/4 步：只 save） | 3.58 s | 0.037 s |
| **★ 平均每步** | **4.34 s** | **0.083 s** |
| **可省** | — | **4.25 s/步** |

### 4.4 与 M7 实测缺口对账

```
old_log_prob  19.1 s/步        （日志 76.3 s ÷ 4，见 §6 口径更正）
ref            9.8 s/步        （日志 39.2 s ÷ 4）
缺口           9.3 s/步
其中快照搬运   4.34 s/步  =  47%
剩余未解释     ~5.0 s/步  ← 待查（entropy？LoRA adapter 前向开销？）
```

## 5 · 结论

1. **`old_log_prob` 贵在「不是一次前向」**：它要把整个模型换成 v1 参数、算完再换回来。
2. **搬的东西 96.8% 是不该搬的**：基座冻结、跨版本逐字节相同，
   `ddp_save_to_cpu` 却把 902 个张量全拷了。
3. **修法很小**：在 `verl_patches.ddp_save_to_cpu` / `ddp_load_from_cpu` 里加
   `if p.requires_grad` 过滤 ⇒ **4.34 → 0.083 s/步，省 74.1 s 的 5.7%**。
   ⚠️ 正确性依据：基座 `requires_grad=False`，优化器从不更新它 ⇒ v1 与当前版本的基座**必然相同**。
   **但要有测试钉死这条**（对拍：全量恢复 vs 仅 LoRA 恢复，逐参数 allclose）。
4. ★ **这笔钱比 E11 大**：E11 全套自写 kernel 才 4.3%，这里改一个 `if` 就有 5.7%。
   ⇒ 又一次印证 ostinato §14.1：**「一行开关/一个过滤器」的收益经常大于手写算子。**
5. ⚠️ 缺口还剩 ~5 s/步（53%）未解释 ⇒ 挂 E01 用 nsys 查。

## 6 · ⛔ 推翻了什么

> **原猜想（H2）**：搬运能解释 `old_log_prob` 与 `ref` 之间 **37 s** 的缺口。
>
> **实测**：搬运只有 **4.34 s/步**。
>
> **推翻后**：**H2 的分母本身就是错的。** 37 s 不是「每步」的缺口——
> 核实日志后发现 **每条 timing 行覆盖恰好 4 个 global step**
> （`training/global_step` 序列 3, 7, 11, …, 147，相邻差全为 4，共 37 行 = 148 步）。
> ⇒ 真实缺口是 **9.3 s/步**，搬运占 **47%**，H2 的方向对、量级错。
>
> **教训**：**报绝对时间之前，先确认那条日志行覆盖的是几个步。**
> 之前 E11/E12 里所有「XX s/步」的说法都受此影响（**百分比不受影响**，
> 因为它们是同一窗口内的比值）。已在 E12 §4.4 与本报告加口径注记。

## 7 · 踩的坑

| 症状 | 根因 | 修法 |
|---|---|---|
| 一开始以为缺口是 37 s | 把「4 步之和」当成「每步」 | 用 `training/global_step` 的差分核对窗口 |
| `.sum().backward()` 撞 `assert dlogprobs.is_contiguous()` | `.sum()` 的梯度是 expand 出来的、非连续 | 传显式 `torch.ones_like(...).contiguous()` |

## 7.5 ✅ 改动已落地（2026-08-14）

`syncopate/train/verl_patches.py` 的 `ddp_save_to_cpu` 加了一行 `if param.requires_grad`：

```python
state = {
    name: (param.detach().to("cpu", copy=True), None)
    for name, param in model.named_parameters()
    if param.requires_grad          # ← E13
}
```

`ddp_load_from_cpu` **无需改动**——它本来就是「存的时候没有就跳过」的语义
（`if name not in cpu_sharded_state: continue`），冻结基座自然不被触碰。

三条新测试（`tests/train/test_verl_patches.py`，全部通过，连同原有 4 条共 7 条）：

| 测试 | 钉死什么 |
|---|---|
| `test_snapshot_only_stores_trainable_params` | 冻结基座不进快照 |
| `test_restore_recovers_trainable_and_leaves_frozen_untouched` | 可训练参数能恢复 **且** 冻结基座**逐字节不动** |
| `test_full_finetune_model_still_saves_everything` | **前提失效时自动退回全量**——全参微调下不能漏存 |

★ 第三条是关键：这个优化依赖「基座确实冻结」。若哪天改成全参微调，
`requires_grad` 全为 True ⇒ 本函数自动退回全量拷贝，**语义仍然正确，只是不再省**。
⇒ **不是靠注释提醒后人，是靠测试守住。**

## 7.6 ✅✅ 真实训练验证（2026-08-14，`logs/e12b_synctiming.log`）

时间戳核对：`verl_patches.py` 改于 11:17:15，trainer worker 起于 11:18:27
⇒ **这一跑带着修法**（差 72 秒，运气好的两用一跑）。

**★ 最干净的证据是「同跑内 `old_log_prob` 对 `ref` 的比值」**
——两者都是同一批数据上的纯前向，条件完全一致，不受数据组成/预热影响：

| | old_log_prob | ref | 比值 |
|---|---|---|---|
| M7（**无**修法） | 76.3 s | 39.2 s | **1.95×** |
| 本跑（**有**修法） | 33.21 s | 34.61 s | **0.96×** |

⇒ **那个 1.95× 的缺口整个消失了**，old_log_prob 甚至略快于 ref。
⇒ §5-5 里「缺口还剩 ~5 s/步未解释」这句**也随之作废**——修完之后没有缺口了。

### ★★★ 最稳健的证据：**同跑内 `old_log_prob / ref` 的比值**

两者都是同一批数据上的纯前向，**不受预热、数据组成、序列长度影响**——
把它当"自带对照组的比值"看，是这次能拿到的最干净的指标：

| | 样本数 | 全部取值 | **中位** |
|---|---|---|---|
| M7（**无**修法） | 37 | 全部落在 **1.75 – 2.11**（极稳） | **1.941** |
| e12b（**有**修法） | 3 | 0.96 / 1.10 / 1.07 | **1.069** |

⇒ **`old_log_prob` 相对 `ref` 的「超额开销」从 0.94×ref 降到 0.07×ref，
消掉了约 93%。** 换算成绝对值：
```
M7   old_log_prob 19.21  −  ref 9.87  =  超额 9.34 s/步
e12b old_log_prob 10.77  −  ref 9.95  =  超额 0.82 s/步
⇒ 省下 ≈ 8.5 s/步（占 74.6 s 的 11.4%）
```

### 跨跑绝对值（剔除首条预热后，每 global step）

| 项 | M7 无修法（36 条） | e12b 有修法（**仅 2 条**） | 比值 |
|---|---|---|---|
| **old_log_prob** | **19.21 s** | **10.77 s** | **0.56×** ← 目标项 |
| ref | 9.87 s | 9.95 s | 1.01× |
| adv | 2.42 s | 2.29 s | 0.94× |
| update_actor | 24.70 s | 28.04 s | **1.14×** ⚠️ |
| step | 74.63 s | 71.27 s | 0.95× |

⚠️⚠️ **端到端只能说 −5%，不能说 −11%**：e12b 稳态只有 **2 条**，
`update_actor` 恰好高了 14%（与本改动无关，纯样本噪声），把收益吃掉大半。
⇒ **目标项的收益（8.5 s/步）证据充分；端到端数字需要长跑复核。**

### ⛔⛔ 我在这一节里连续报错了两次，记下来

| 时点 | 我报的 | 实际 | 错因 |
|---|---|---|---|
| 拿到**第 1 条** timing 行 | step **−33%** | — | n=1 的跨跑对比 |
| 拿到 **3 条**（含预热） | step **−13%**、"归因干净" | — | **均值里混了预热步**（M7 首条 71.3 vs 稳态 ~98，e12b 首条 72.1） |
| 剔除预热后 | **step −5%**，目标项 −44%，`update_actor` 反而 +14%（n=2 噪声） | ✓ | — |

★ **教训（三条，都便宜但都真踩了）**：
1. **跨跑比绝对值之前，先剔除预热步**——首步能低 30%，足以把结论带偏。
2. **样本量要报出来。** 「e12b 有修法」听起来和「M7 无修法」对等，
   实际是 **2 条 vs 36 条**。⇒ **写比值表时把 n 写在表头里。**
3. **优先找"自带对照组"的指标。** `old_log_prob/ref` 这个比值在同一跑内、
   同一批数据上取，天然免疫上面两个坑——**它给出的结论从第一次到最后一次没变过。**

★ 实测省得比微基准预测的**更多**（预测 4.34 s/步，比值法反推 ≈ 10.8 s/步）。
推测原因：真实场景是 **3 个 rank 各搬 8.3 GB**，且 `ddp_load_from_cpu` 结尾有
`dist.barrier()` ⇒ **最慢的那个 rank 决定整体**，而单卡微基准量不到这一层。
⇒ **单卡微基准会系统性低估多卡下的搬运成本**，记一笔。

## 7.7 ⛔ 一个「递增趋势」，查完发现不存在

**原观察**（e12b 三条 timing 行）：`update_actor` 72.1 → 99.9 → 124.4（+73%），
`step` 199.4 → 265.7 → 304.5（+53%）⇒ 一度写下「步耗时在跑内递增，原因未知」。

**复核（拿 M7 的 37 条查）**：

```
update_actor 与步序号的相关系数   0.080     ← 基本无关
step         与步序号的相关系数   0.018
四个区间的 update_actor 均值      96.9 / 99.4 / 97.9 / 97.9   ← 完全平
但 M7 首条 71.3，末条 99.6
```

⇒ **没有递增趋势。** e12b 看到的是 **预热（72）→ 稳态（~100）+ 一个偏高点（124）**，
在只有 3 个点时长得像趋势。**M7 的首条 71.3 和 e12b 的首条 72.1 几乎一样**——
这本身就是"首条是预热"的铁证。

★ **教训**：**3 个点画不出趋势，但足以骗到自己。**
判断趋势的正确做法是**去已有的长序列里算相关系数**，而不是盯着短序列的形状。
⇒ 这次复核花了 2 分钟，避免了去查一个不存在的现象。
