## 1 · ESS 到底量什么（先钉概念，否则判据无从谈起）

### 1.1 一句话与一个比方

RL 要用**现在这版策略**的梯度，但轨迹是**派出去的那版策略**生成的。
重要性采样（IS）用一个权重把差别补回来：

```
w = 现在的策略认为这条轨迹的概率 ÷ 生成它时的策略认为的概率
```

**ESS 回答：这一批加权样本，相当于几条「一人一票」的样本？**

```
ESS/N = (mean w)² / mean(w²) = 1 / (1 + CV²)

权重都一样        → ESS/N = 1.0    48 条就是 48 条
一条占了 90% 权重 → ESS/N ≈ 0.02   48 条只值 1 条
```

比方：你派 48 个人出去打分，但他们是「上一版的你」派出去的。你得按「他的口味跟现在的我有多近」
给每张票加权。**ESS 就是「加权之后，这堆票相当于几个人一人一票」。**

### 1.2 我们的实数 `[实测 logs/rl_v13e1.log，27 个指标周期]`

一次优化器更新用 **6 条 prompt × 8 次采样 = 48 条序列**（`rollout_dumps/*.jsonl` 每文件 48 行，逐文件核过）。

| | N | ESS/N | **绝对有效条数** |
|---|---|---|---|
| lr 1e-5，步 3 | 48 | 0.912 | **44** |
| lr 1e-5，步 107 | 48 | 0.348 | **17** |
| lr 3e-5，停机那一刻 | 48 | 0.278 | **13** |

### 1.3 ★ 它塌在**低侧**，不是高侧 `[实测]`

```
                     步3      →   步107（lr 1e-5）
低于 0.5 的序列占比    5.6%   →   56.8%      ★ 主要在这一侧
高于 2.0 的序列占比    0.7%   →   12.0%
权重均值              0.99   →    0.65      整体下沉，不是对称变宽
```

与 E20 §3.5 的「67.2% 被压到下界」是同一件事（那是 lr 3e-5 的更极端版本）。

### 1.4 ★★ 必须分清：**方差** vs **偏差**

| | 是什么 | ESS 低会怎样 | 我们的实况 |
|---|---|---|---|
| **方差** | 梯度算得准不准 | 变吵。有效 17 条 vs 44 条 ⇒ 噪声 ×1.6 | 🟡 主要是这个 |
| **偏差** | 梯度指的方向对不对 | **只有被 `C=2.0` 截断的那部分才产生偏差** | 12%（1e-5）/ 67%（3e-5 末段） |

**IS 只要权重是对的，不管多不平衡，它都是无偏的。** 低 ESS 让梯度更吵，**不会让它指错方向**。
真正「安静地失效」（研究问题 H3）的是**截断**：一堆序列被压到同一个界上，
IS 修正退化成常数缩放 —— 那才是估计量坏掉。

⇒ **判「TIS 还能不能用」该看 `fraction_high/low`（被截断的比例），不是看 ESS。**

### 1.5 ⚠️ verl 报出来的 ESS 是**截断后**的口径 `[实测源码]`

`verl/trainer/ppo/rollout_corr_helper.py:751-757`：

```python
weights_for_ess = rollout_is_weights.clamp(min=0.0, max=rollout_is_threshold)   # ← clamp 到 [0, 2.0]
metrics["rollout_is_eff_sample_size"] = 1.0 / masked_mean(normalized.square())
```

⇒ **高侧尾巴被砍掉 ⇒ 报出来的 ESS 系统性偏高**，而且 `fraction_high` 从 0.7% 涨到 12%
⇒ **越到后期越乐观**。与 E20 §3.5「观测到的 0.270 是截断在硬撑」一致，这里补代码出处。

## 2 · 0.3 这条线合不合理？—— 三条独立的理由说不合理

### ① 它是个**比例**，而比例隐含了一个 batch 大小的假设

```
上游语境：batch ~1024 条，ESS/N=0.3  ⇒  有效 307 条  → 完全够用
我们：    batch    48 条，ESS/N=0.3  ⇒  有效  14 条  → 快没了
```

**同一个比例，含义差 20 倍。** 决定梯度质量的是 **`N × ESS/N`（绝对有效条数）**，不是比例。

⇒ 这正是本项目反复记录的形状：**判据写满了、真的在跑、真的报了个数 ——
只是它量的不是我们以为的那件事**（`.claude/memory/blank-thresholds-are-not-passes.md` ③④）。

### ② ★★ 我们把上游的「换聚合方式」读成了「停机」

`23-research-question.md §7` 里我们自己抄下来的原文：

> verl 文档：*若 ESS < 0.3, **consider switching to geometric aggregation***

上游的意思是：**ESS 掉到 0.3，说明当前聚合方式不适合你的工作点了，换一个。**
而 `06-rl-run-protocol.md §2` 写成了 **「立即停：ESS/N < 0.3」**。

**「换个估计量」变成了「停止训练」。** 更讽刺的是——「什么时候该从 sequence 换成 token」
**正是这个项目的研究问题本身（H3）**。我们把研究问题的答案，当成了训练的刹车。
⇒ **E20-a 的结果正是这句话的实证**：换掉估计量，ESS 直接回到 1.000，一分吞吐都没付。

### ③ 它拦下来的那一跑，其它指标全是正常的 `[实测 lr3e5 日志 18 个周期]`

```
ESS      第31步起在 0.26–0.41 之间震荡 40 步 —— 是平台，不是滑坡
grad_norm    0.0004–0.0126     和 1e-5 同量级
pg_clipfrac  0.0011–0.0029     PPO 剪裁几乎从没触发
entropy      0.055–0.086       没塌
reward       0.45–0.59         没崩
```

⚠️ **但这不等于「3e-5 是安全的」**：E20 §3.5 已说明那 40 步的"平稳"是**截断把方差摁住**的结果，
代价是 67% 的样本几乎没有梯度（`grad_norm` 反而变小就是证据）。
⇒ **正确读法：它不是崩了，是废了。** 停机线拦对了"有问题"，**但归错了因、给错了处方**
（处方应是"换估计量"，不是"降 lr"）。

### 2.4 建议的新停止条件（替换 `06 §2`）

```
🔴 停机 · 梯度质量没了
   N × ESS/N < 24 条序列               ← 绝对条数，不是比例

🔴 停机 · 估计量真的失效了（= H3）
   fraction_low + fraction_high > 40%   ← 4 成样本被压到界上 ⇒ IS 退化成常数缩放
                                          （lr3e-5 末段实测 67%，早就该报警）

🟡 不停机，改配置（这才是上游那句话的原意）
   ESS/N < 0.3  ⇒  换聚合口径：--rollout-is token（E20-a 已证有效）

保留：决策位熵 < 0.05 / grad_norm 跳两个数量级 / reward 涨但 cap 不降（连续 3 步）
```

⚠️ 24 与 40% 都是**按当前 batch 反填的工程值，不是推导出来的** —— 按纪律写明：**这是拍的**，
第一次跑完用实测反填。

## 3 · 把「学不动」拆成可定价的算术

```
净位移 ≈ lr × 更新次数 × 效率（各步方向不互相抵消的比例）
```

`[实测]`：

| | lr | 更新次数 | 位移 `‖ΔW_eff‖/‖W_base‖` | 反解「效率」 |
|---|---|---|---|---|
| **SFT v13**（参照系） | 1e-4 | 210 | **0.4985%** | 0.24 |
| **RL m7b（lr 1e-5）** | 1e-5 | **110** | **0.0487%** | 0.44 |  ⛔(21)

⇒ **缺口 ≈ 10× 来自 lr、1.9× 来自更新次数，效率反而是 RL 略高。**

★★ **这给 E20 §3.6 一个定量排序**：「一个 epoch 只更新 109 次」是**对的观察**，
但拿「正常 LoRA 几千次」当参照会高估它的份量 —— **正确的参照系是我们自己的 SFT：210 次。
1.9× 的差距，排在 10× 的 lr 后面。**

⚠️ `[推断，未验证]` 上表「效率」用 `lr × 次数` 当上界反解，而这条经验规则是在**旧口径**
（`‖Δθ_trainable‖/‖θ_trainable‖`）下得到的；新口径 `ΔW_eff=(α/r)·B@A` 在 B 从零长起来的早期
**近似二次而非线性** ⇒ 上界不严格。**引用「效率 0.44」必须带这句。**

## 4 · ★★★ 位移是**输入**，不是产出 —— 这一节是本文最想让 infra 读到的

### 4.1 我写下的一个预测，被 E20-a 当天推翻了（按纪律不删）

> **原猜想（本文初稿）**：token 级 IS 会把被压到下界的 67% 样本救回来 ⇒ 有效 batch ×3.3
> ⇒ **位移会跟着起来（预测 ≥0.3%）**。
> **实测 `[E20 §3.7]`**：ESS 0.449 → **1.000**、`grad_norm` 趋势反转，
> 而**位移 0.1071% → 0.1101%（+2.8%），几乎没动**。
> **推翻后**：⇓ 见 §4.2。**教训**：我把"梯度变好"和"走得更远"当成了同一件事。

### 4.2 机制：AdamW 下**每步位移 ≈ lr，与梯度大小/质量无关**

这条本项目早就写下来过（`.claude/memory/rl-step-size-is-lr-times-steps`）：

```
AdamW 的更新量 = lr · m̂ / (√v̂ + ε)     ← 梯度被自己的二阶矩除掉了
⇒ 梯度大 10 倍，步长几乎不变
⇒ **位移 ≈ lr × 更新次数**，估计量修不修都一样
```

⇒ ✅ **所以 E20-a「位移没变」完全在意料之中，它绝不是"没起作用"的证据。**
   估计量买到的是**方向质量**（每一步走得对不对），不是**距离**（走了多远）。

### 4.3 ⇒ 由此得到两条对下一批实验的硬约束

**约束一：`位移起得来` 不能当成功判据。**
E20 §4.1 的指标表把位移列成「目标：起得来」。但位移是我们**设定**的量：
`lr 3e-5 → 1e-4` 加 `mini_batch 6→2`，位移**必然**涨约 10 倍 —— 那是算术，不是证据。
⇒ **下一批（E20-e/f/g）如果只报位移涨了，等于什么都没证明。**
⇒ 这就是本项目 README §4 那条纪律（**只报吞吐不报精度不算完成**）在正确性线上的同一句话。

**约束二：判定 E20-a 有没有用，只有一把尺子 —— 任务级配对，而且要看三个计数。**

```bash
# token 级那一臂的收尾 ckpt
python -m syncopate.train.eval_local --adapter <token臂 ckpt> ...
python -m syncopate.train.compare    _audit/v13_sft_e1.json _audit/<新审计>.json
```

⚠️⚠️ **不要只看均值。** `16 §2.5` 已经吃过一次亏：M7-b 均值 +0.020（= MDE，读作"没测出"），  ⛔(21)
**逐题拆开是 85 涨 / 70 跌 / 188 没动** —— 模型动得很厉害，只是净额相抵。  ⛔(21)

⇒ ★ **判定 E20-a 的正确判据**：在**位移相同**（0.107% vs 0.110%）的两臂上比
「显著变好 / 显著变差 / 没动」三个计数。

```
若 token 臂的「变差」明显少于序列臂  ⇒ 估计量修好了，同样的位移走在了更对的方向上 ✅
若三个计数没差别                    ⇒ 方向噪声的主因不在 IS，要回去看优势/奖励信号（E20 §6-5）
```

**这是同位移下的对照，比任何"位移涨了多少"都干净。**

### 4.4 顺带：`ppo_mini_batch_size 6→2` 现在可以做了，但要带两个监控

我初稿写的「不要先减 mini_batch」，**理由是它会喂大序列级 IS 的问题** ——
**E20-a 修好之后这条理由消失了**（token 级 ESS = 1.000，余量很大）。
⇒ 改成：**可以做，但同时盯两件事**：

```
① pg_clipfrac      现在 0.001（几乎不触发）⇒ 批内后段变离策略后它应该开始动。
                   若仍恒为 0 ⇒ clip 根本没在工作，"多更新几次"是在无保护地重复用同一批数据
② 每次更新只剩 2 组（16 条序列），而**零方差组占 10.4%** `[实测]`  ⛔(21)
                   ⇒ 约 10% 的更新可能几乎没有信号。建议中间点 `mini_batch=3`（每步 2 次更新、24 条）
```

## 6 · ★ 主线侧同时要修的六处（**不在 E20 范围内**，但和它互相放大）

### 6.1 🔴 轨迹变长同时在**两条线上**造成伤害 —— 主线与 infra 的交汇点


## 7 · ⚠️ 三处口径更正（会污染引用，请优先改）

### 7.1 🔴 「更新次数」被 param_version 顶替了，差 4 倍 `[实测，逐文件数过]`

```
checkpoints/grpo/m7b_v13e1/rollout_dumps/      110 个文件 × 48 行  ⇒ 110 次优化器更新
checkpoints/grpo/b16_ref_on_60/rollout_dumps/   52 个文件          ⇒  52 次
checkpoints/grpo/b16_ref_off_60/rollout_dumps/  60 个文件          ⇒  60 次
```

而 **E20 §1 / §3.7 的表写的是「13 次 / 15 次更新」**，那是 **timing 行数 = param_version 数**
（`52/4=13`、`60/4=15`，`sync_every=4`）。**E20 内部是矛盾的**：
§3.6 算出「110 步 ⇒ 109 次更新」（**这条对**），§1 却按 13 记。

**交叉验证**（这也是判定 52/60 才对的依据）：

```
每次更新的位移   m7b(lr 1e-5)  0.0487% / 110 = 0.00044%  ⛔(21)
                B16 (lr 3e-5)  0.102%  /  52 = 0.00196%   ⇒ 比值 4.4 ≈ lr 比值 3   ✅
若按 13 次记     0.102% / 13   = 0.00785%                 ⇒ 比值 18×              ❌
```

⇒ **要改**：`E20 §1`、`E20 §3.7`、`E17 §5.1` 的分母。
⚠️ **E17 §5.1 的 A/B 结论不受影响**（两臂同一个错分母，比值不变），但那两个绝对值
（0.00783% / 0.00790%）要各除以 4。

★ 教训（可进记忆）：**同一份日志里有三个都叫 step 的计数器** ——
`training/global_step`（跳 `sync_every`）· ckpt 目录名（= `param_version`）· dump 文件数（= 真正的更新次数）。
**引用「步数」之前先说清是哪一个。**

### 7.2 🟠 `位移 ≈ lr × 步数` 的成立口径

它是在**旧口径** `‖Δθ_trainable‖/‖θ_trainable‖` 下得到的；现在通用的是 `‖ΔW_eff‖/‖W_base‖`，
而 `ΔW_eff=(α/r)·B@A` 在 B 从零长起来的早期**近似二次**。
⇒ 拿 `lr × 次数` 当上界反解「效率」（§3）**不严格**，引用必须带这句。

### 7.3 🟠 「ESS」这个词在三处指不同的东西

```
verl 自报 rollout_is_eff_sample_size     ← **截断后**的口径（§1.5），最乐观
1/(1+chi2_seq)   = 0.015                 ← 真正的序列级 ESS   [E20 §3.5]
1/(1+chi2_token) = 0.939                 ← token 级
```

⇒ **写「ESS」必须写明是哪一个** —— 三者在同一时刻相差 60 倍。
