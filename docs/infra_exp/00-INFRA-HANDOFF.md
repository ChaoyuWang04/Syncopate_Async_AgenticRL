## 4 · ⚠️ 两个已知的坑（下次开跑必撞）

1. **`--weight-sync-bucket-mb` 默认 2048 会 OOM**（⇒ 队列 B2 就是治它的）。
   CheckpointEngine 会在**目标卡上**分配一个 bucket 大小的暂存区（`nccl_checkpoint_engine.py:142`），
   而实际只推 132 MB。⇒ **`gpu_util` 不是安全阀**，解法是**调小 bucket**（短跑传 512）。
   ⚠️ 它对**所有模式**生效，colocate 同样会撞。
2. **`--save-freq 999` 挡不住收尾那次保存。** 每个短跑结束都落 **27 GB** ckpt。
   曾差点把 61 GB 的 MoE 下载挤爆。⇒ **计时/探针类短跑，跑完就删 `checkpoints/grpo/<exp>/global_step_*`**
   （`dispatched.jsonl` 和 `rollout_dumps` 要留）。

### 🔴🔴 第 0 优先级 · 正确性：**模型学不动**（[`E20`](E20-rl-not-learning.md)）

**症状**：跑完一整遍数据集（109 次更新）之后能力几乎没变化；`lr=3e-5` 会让 ESS 崩、只有 `1e-5` 能用。

**已诊断出两个独立原因**：

| | 原因 | 证据 |
|---|---|---|
| ① | **序列级 IS 在长序列上指数崩塌** | 同一批数据：`chi2_seq=64.19`（ESS 0.015）vs `chi2_token=0.065`（ESS 0.939），**差 989×**；67% 的序列被截到下界；`grad_norm` 反而变小 |
| ② | **一个 epoch 只更新 109 次** | `ppo_mini_batch_size = train_batch_size = 6`、`ppo_epochs=1` ⇒ 每 fit step 只更新 1 次。正常 LoRA 是几千次 |

| 序 | 任务 | 状态 | 说明 |
|---|---|---|---|
| **1** | **E20-d · colocate + lr=3e-5** | 🔴 待跑（~30 min） | ★ **最便宜的决定性诊断**：colocate 下陈旧度 = 0，只换 `--mode`，不动算法。ESS 还塌 ⇒ 主因不是陈旧度 |
| **2** | **E20-a · token 级 IS** | 🟡 **正在跑**（batch8） | `--rollout-is token`，lr 3e-5，60 步 |
| **3** | **E20-b · 陈旧度对照** | 🟡 正在跑（batch8 第三跑 `sync_every=1`） | |
| **4** | **E20-e · 增加更新次数** | 🔴 待跑 | `ppo_mini_batch_size 6→2`（109→327 次）。⚠️ **必须在 2 之后**：批内走得更远会让序列级 IS 崩得更快 |
| **5** | **E20-f · 提 lr** | 🔴 待跑 | 2/4 都做完之后才有意义。判据是位移起得来且 ESS 不塌 |
| 6 | **B21 · 重测 B10/B19 的代价** | 🔴 待跑 | 它们的 ESS 是在 `lr=1e-6`（模型不动）下量的，**系统性低估陈旧度代价** ⇒ 现有结论不可用 |
