## 1 · 现在的问题（每条都有代码出处，不是推测）

用大白话说：一单进来要过五道关，每道关都有"人为等待"——

```
① 没有门铃，全靠打转问。
   worker 领单：每 0.2 秒查一次数据库"有新单吗"（worker.py poll_interval=0.2）
   用户看进度：每条 SSE 流每 0.25 秒查一次"有新事件吗"（api.py:398）
   ⇒ 每个环节平白多等 0~250ms；一单五六个环节，固定税约 0.5~1 秒；
     96 个用户在线时，光"看进度"就是每秒近 400 次无效查询砸向数据库。

② 传菜口只有 10 个。
   worker 与 API 的连接池都是默认 max_size=10（db.py:41），而 worker 开 512 个并发槽。
   每一步的每一笔读写（领单/写事件/记账/查幂等）都要先排队借这 10 条连接之一
   ⇒ 延迟随并发线性上涨的头号嫌疑。

③ 两只手干所有活。
   API 是一个 Python 进程、worker 也是一个进程（GIL：同一时刻各只有一只手）。
   96 路 SSE 推送 + JSON 序列化 + 全部编排逻辑挤在两颗核上，四张 GPU 在旁边看戏。

④ 记账挡在路中间。
   每走一步都同步写完事件/审计/用量/幂等才走下一步。这些账是产品卖点不能砍，
   但"记完账才干活"让账本排队时间全进了用户延迟。

⑤ （测量欠账）以上四条的**份额**还没量过——E32 只证明了"总量在调度层"。
```

已知的好底子（不用修）：领单用 `FOR UPDATE SKIP LOCKED`（并发安全的正规写法）；
SSE 断线补发从数据库按 `Last-Event-ID` 重放（**不依赖进程内存 ⇒ 多进程化天然安全**）。

## 4 · 分步施工（★ 每步末尾的门槛数字不达标，不许进下一步）

### S0 · 装表分账（半天–1 天）——先测量后动手，本线铁律

给一单旅程的每一站装计时，把 e2e 拆成：

```
t_queue   下单 → 被领走          （查 run_events 的 created/started 时间差即得，零改码）
t_llm     模型调用总时长          （decider 侧计时，挂在 usage 记录旁）
t_tool    工具执行总时长          （worker 已有 tool 计时口径）
t_db      借连接的等待 + 读写时长  （db.py 包一层计时器，按调用方分桶）
t_sse     事件落库 → 客户端收到   （b4_goodput 客户端侧：收到时间 − 事件 created_at）
t_rest    余数                   （解释不了的部分，必须显式打出来）
```

产物：C = 8 / 64 / 96 三档各一张分账表 + goodput 阶梯噪声地板（C=64/96 各重跑 ×3）。

**门槛（过了才许开刀）**：
- ① 分账覆盖率 ≥ **90%**（六项加总 ÷ e2e；解释不了 10% 以上 = 表装错了，先修表）
- ② 同档重跑 ×2 各站份额漂移 < **5 个百分点**（表自己得是稳的）
- ③ 三档对比能指出**随并发涨得最快的那一站**（这就是第一刀的靶子；若与 P1 不符，先改预测记档再动刀）

### S1 · 门铃替轮询（~1 天）

用 PostgreSQL 自带的 LISTEN/NOTIFY：新单落库时数据库主动喊 worker，新事件落库时
主动推给 SSE 流。**轮询不删，改成 2 秒一次的兜底**（门铃坏了得有慢铃，且兜底被触发
时必须打一行判据日志——"机制在但没接上"的防线）。
⚠️ 已知坑预告：NOTIFY 在事务提交时才发（恰好保证一致性，是特性不是坑）；
asyncpg 的 listener 连接断了要重建，重建逻辑必须有专项测试。

**门槛**：
- ① 全量 pytest **365+ passed / 0 skipped**；四红线专项全绿（断线补发、幂等逐条）
- ② C=8 的 I01 P95 改善 ≥ **300ms**（固定税兑现；对照 S0 噪声地板读）
- ③ 数据库每秒查询数（进度轮询类）下降 ≥ **80%**（S0 装的 t_db 计数器直接读）
- ④ 拔掉门铃（kill listener 连接）后系统靠兜底继续工作，且兜底判据行出现

### S2 · 连接池扩容与分池（~半天）

10 → 按 S0 实测份额定容（预估 worker 执行池 64+ / API 读池 32+ / SSE 池 32+，
三池分开，刷进度的不许挤占干活的）。同时确认 PG `max_connections` 余量。

**门槛**：
- ① C=96 下 t_db 里的**借连接等待**份额降到 < **5%**（S0 同表口径复测）
- ② PG 连接占用峰值 ≤ max_connections 的 **70%**（留余量，不许贴顶）
- ③ 全量 pytest + 四红线专项全绿

### S3 · 多进程（~半天–1 天）

API 起 4 个 uvicorn worker；runtime worker 起 4 个进程（按 NUMA 各绑一颗，拓扑
表沿用 b4_serve_4x 实测的 CPU 亲和）。前置检查：SSE 补发走 DB 重放已确认跨进程
安全；再排查一遍有没有进程内缓存被隐式共享的假设（成本累计、限流计数）。

**门槛**：
- ① goodput 阶梯 **C=96 全绿**（膝点实际推过 96；达不到 = 归因写进 §6 再议）
- ② 高并发时 API/worker 任一进程 CPU < **80% 单核**（单手饱和消除的直接读数）
- ③ 四红线专项全绿 + kill 掉 4 个 worker 进程中的 1 个，在飞任务 **0 丢失**（lease 机制专项）

### S4 · 记账挪出关键路径（**条件步**：仅当 S0 显示账本同步写份额 > 10% 才做）

事件写入改组提交/批量落盘；**幂等标记与审批门保持同步不动**（这两样是"绝不
重复执行/绝不越权花钱"的根，异步化=打破承诺）。

**门槛**：
- ① 断线补发专项连跑 ×3 全绿 · kill -9 恢复 3/3 · 对账脚本（请求数 vs 事件数）零缺行
- ② C=192 的 I01 P95 ≤ **5s**
- （若 S0 显示份额 < 10%：本步跳过，在 §5 记"预测 P3 命中，主动不做"）

### S5 · 终验与收尾（~半天）

- goodput 阶梯 8→384 完整重跑（与 E32 的 before 同尺同表）
- **终极门槛（预注册）：goodput@SLO ≥ 256 并发**；卡在中间值就如实记账 + 逐站归因
  （分账表会直接指出剩余大头在谁家）
- loadtest 服务面全表复跑：不低于 21/22，四红线全绿
- 回填：本报告 §0 · NARRATIVE〔B-5〕格 · 11 §5 追加 after² · MAINLINE 删行 · 01 删行
