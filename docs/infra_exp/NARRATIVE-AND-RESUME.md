## 0 · 两条硬规矩

### 0.1 只写完成态

> **这里写的是「所有实验做完之后」的样子，不是「现在做到哪」。**
> **还没测出来的数字一律留 `〔 〕`，后面标由哪个实验填。**

**为什么只留一个版本**：进度会变、且**一定会走到完成态**；同时维护「现在能写的」和「做完能写的」两份，
前者会不断被改、后者永远没人看，最后两份都不准。⇒ **进度归 TRACK-A/B，这份只描述终点。**

### 0.2 ★★★ 每个问题必须写成「问题 → 根因 → 解法 → 指标怎么变」四段

**没有第四段的，不算解决，只算测量。**

这条规矩是被一个真实的错误逼出来的：占空比 31% 这个结论一度被当成「产出」讲，
但它其实只是**测量 + 归因**——**三个成因一条都还没消掉**（见 P5）。
⇒ **归因做完会有一种「已经解决了」的错觉。四段式就是防这个的：第四段空着，问题就还在。**

# 第一部分 · Track B（框架/异步线）

> 一条主线：**通用 RL 框架的默认假设，在 agentic 负载上逐条失效。我们逐条量、逐条改。**
> 业务背景：手游买量投放的多轮工具调用 agent，轨迹长短天然不齐（1–8 轮），
> 长链路任务又慢又关键；硬件是 4×消费级显卡，无 NVLink、无 P2P，卡间经主机内存中转。

## 1 · 遇到的问题，和怎么解决的

### P1 · 同批轨迹长短不齐，同步训练时快的都在干等 ✅ 已解决

| | |
|---|---|
| **怎么发现** | 实测同批**最慢/平均 = 1.37–2.75×**（多轮工具往返导致），而同步模式有 barrier，**必须等最慢那条** |
| **根因** | 通用框架假设「rollout 时长大致齐整，barrier 的代价可接受」——**单轮数学题成立，多轮 agent 不成立** |
| **解法** | 上全异步（3 卡训练 + 1 卡生成），让训练和采样重叠；配 decoupled PPO + 陈旧度上限 + 可打断 rollout 保证可训 |
| **★ 指标** | **每步 117.8 → 74.1 秒（1.59×）**，同机同配置对照 |

★ **这里有个容易被跳过的动作**：手上原本有个 32.6 秒的老基线，看着漂亮，
**但那次用的是另一套算法（bypass vs decoupled），跟现在不可比**，所以专门补了同机分母。
⇒ **加速比必须有同机分母，否则就是在自己骗自己。**

⇒ **三种摆法的完整对照**（除摆法外配置全同）：
```
colocate       1 卡    117.8 s/步    1.00×
one_step_off   3+1     〔B3〕        〔B3〕
fully_async    3+1      74.1 s/步    1.59×
```

### P2 · 异步 RL 的"权重同步"两个月里根本没在同步 ✅ 已定位、已自己修好、已验证

| | |
|---|---|
| **怎么发现** | 排查清单上一条红了一天的前提：「推给推理引擎的，到底是不是当前训练的权重？」——**我们验过它的耗时，从没验过它的内容**。判据一写就炸：推出去的那一层权重，**与磁盘上起点模型逐位相同** |
| **根因** | 框架在"训推分离"这条路上**只调了一次取参数、且用的是默认参数**，而那个默认值的含义是「推理端还没有基座，先推基座」——**设计上该跟着推一次 adapter，代码里只写了第一步**。⇒ 每次同步推 **8,414 MiB 冻结基座**，LoRA 一个字节没推 ⇒ **生成数据的策略永远停在起点** |
| **为什么两个月没被发现** | 它不报错、指标全正常，而且**制造了一整套自洽的错误解释**：一个指标单调涨 36×、有效样本数随位移下降、陈旧度旋钮不敏感 —— 全都"看起来像陈旧度"，我们据此追了两个月 |
| **解法** | 上游把这个组合关成 `not planned`，且框架自带的替代开关（合并进基座）实测**毁掉 adapter 一半的作用**（bf16 存不下 0.05% 量级的增量）。⇒ **自己补上那段没接上的管子**：两端能力本来都在，缺的只是把「这是 adapter」这个标记传下去 |
| **★ 指标** | 生成端权重 **从不更新 → 每次同步都更新**（引擎里 adapter 从 `[]` 变成 `[123]`）· 同步载荷 **8,414 → 252 MiB（33×）** · `param_sync` **6.25 → 0.974 s（6.4×）** · 任务分 **首次通过冻结评测：+0.101（t=9.3）** |

★ **这个案例最值钱的不是修好了，是它展示了一类失败**：*机制在、判据在、指标正常，而两个东西悄悄不相等*。
⇒ **教训：验过"送到了"不等于验过"送对了"。判据要写成「送过去的那一份 == 手上的那一份」，
而不是「送成功了 / 耗时多少 / 没报错」。**

### P2b · 而且"同步的代价"本身也不在传输上 ✅ 已实测

| | |
|---|---|
| **怎么发现** | 把同步频率从每 4 步降到每 16 步，整体快 **11.4%**。但 `param_sync` 只占一步 **0.2–0.7%** —— **差 23 倍，钱不可能在那儿** |
| **根因** | 拆开一步的构成：省下的 3.62 s 里 **3.47 s（96%）在 `gen`（训练端等样本）**，`param_sync` 只占 4%，三次前向纹丝不动。⇒ **每次同步都要打断生成，被打断后样本队列要重新填满，训练端就得干等** |
| **★ 指标** | `gen` 占一步 **11.1%（每 4 步同步）→ 0.2%（每 16 步）**；由此**否掉了一整条优化方向**（优化权重同步最多值 0.7%，而"少打断一次"值 3.5 s） |

★ **教训：一个优化方向在动手之前，先用"它最多能省多少"卡一下上限。**
⇒ 我们差点去优化一个占比 0.7% 的东西。

### P3 · 每步把整个模型存一遍，只为取其中 3% ✅ 已解决

| | |
|---|---|
| **怎么发现** | 查 P2 途中顺手看到：算法每步要做一次"存档"（把模型换成旧版本参数算一遍、算完换回来），实测 **4.34 秒/步** |
| **根因** | 数了一下——**存了 902 个张量、8.309 GB，而真正会变的只有 3.18%**。剩下 96.8% 是**冻结的基座**，与上一版**逐字节相同**，存了纯属白存 |
| **解法** | 一行 `if param.requires_grad`；配 3 条测试，其中一条专门钉「全参微调时自动退回全量」 |
| **★ 指标** | 该动作 **4.34 → 0.083 秒/步**（52×），**端到端节省 5.7%**；`old_log_prob/ref` 比值 **1.941 → 1.069** |

★ **这笔钱比整套自写算子的预期收益（4.3%）还大，而改动是一个 `if`。**
★ **前提失效要靠测试守，不是靠注释提醒后人。**

### P4 · 传输缓冲区按 4 GB 定长分配，而实际载荷小两个数量级 ⇒ 分卡模式偶发 OOM ✅ 已修（默认值改了）

| | |
|---|---|
| **怎么发现** | 两跑死在同一个地方：生成卡上 vLLM 占 24.65 GB + 同步组件 4.71 GB，**剩 1.99 GB 要分配 2.00 GB，差 0.01 GB** |
| **根因** | 缓冲区默认 2048 MB **双缓冲 = 4 GB**，且**每个 worker 各一份**，其中一份就住在被 vLLM 占满的生成卡上——**而修好之后实际只推 252 MB**（当时以为是 132 MB，实际推的是 8.4 GB 冻结基座，见 P2） |
| **解法** | 让缓冲区匹配真实传输量（2048 → 512 MB）〔**B2**〕 |
| **★ 指标** | 分卡模式的偶发 OOM **消除**；若耗时同步按比例下降，则坐实"广播整个定长 buffer"的猜想〔**B2**〕 |

⛔ **一条要更正的旧结论**：`gpu_util 0.75` 曾被记成"安全值"。
**实测它只是运气好擦过去，第 4 次同步照样 OOM。真正的解法不是压 gpu_util，是让缓冲区匹配真实数据量。**

### P5 · ★★ 整机占空比只有 31%，生成卡 82.5% 在待机 🔴 已归因，**成因一条都还没消掉**

| | |
|---|---|
| **怎么发现** | 轮询四张卡的利用率，154 个采样点、覆盖一个完整周期：**训练卡空闲 54–57%、生成卡空闲 82.5% 且功耗只有 47.7 W**（这张卡满载能到 450 W，它基本在待机）。⇒ **整机平均 31%**<br>★ **这个数和 P1 的 1.59× 互相印证**——一个从空间维度量、一个从时间维度量，指向同一件事 |
| **根因** | **四条，逐条对上实验**（★ 这张表最重要的是最后一列）：<br>① 权重同步 59.8 s / 4 步 ⇒ 占步 18.8% —— 由 **P2/B1** 打<br>② 陈旧度阈值节流，攒够就停下等训练 ⇒ **量级未知** —— 由 **B10** 打（**此前是空白**）<br>③ 训练侧三次前向串行 ⇒ 占步 **72%** —— 由 **P3(已落) + E11 切片** 打<br>④ **配比本身**：生成只占一步耗时的 **6.3%**，却独占一整张卡 ⇒ 3+1 是当初拍的，从没测过 —— 由 **B11** 打（**此前连成因都没列**） |
| **解法** | **不是单点优化，是四条并行**：B1（同步）+ B10（把写死的阈值变成一条可解释的权衡曲线）+ B11（重新配比/放置）+ 已落地的 P3 |
| **★ 指标** | **整机占空比 31% → 〔W〕%**（由上述四项共同填）；**每步 74.1 → 〔Z〕秒** |

⇒ ★★ **这一条是整个 Track B 最大的一块，也是最容易被自己骗过去的一块**：
**归因做完会有一种「已经解决了」的错觉。**
成因列表必须标上「谁在打」——**空着的格子才显形**（②④ 就是这样被找出来的）。

### P6 · 异步可能系统性丢掉长任务（这是正确性问题，不是吞吐问题）🟡 仪器已修正，测量待做

| | |
|---|---|
| **怎么发现** | 异步下短任务先回、长任务可能被切断，**而长链路正是 agent 的核心能力**。按轮数**逐桶**比"发出去的"和"训练到的"（不比均值，均值会把问题藏起来）⇒ **零差：7200 对 7200，14 个桶全同** |
| **★ 根因** | **零差是假的——仪器装错了位置。** 记录点在"轨迹跑完并算完分之后"，所以它记的是「**跑完了**」不是「**发出去了**」⇒ 我们量的是「完成 → 训练」，**而漂移发生在「发出 → 完成」那一段：半路被杀的轨迹根本走不到那行代码，在账上从来就不存在** |
| **解法** | ① 观测点移到 case 真正被交给 agent loop 那一刻（带版本号），与完成端配对；<br>② **主动把系统推到触发条件上**（收紧陈旧度 / 调小同步周期 / 用更长轨迹）——**要测出漂移，得先让它发生**；<br>③ 量出来之后，用**动态分池的采样权重**对系统性欠采样的样本做补偿 |
| **★ 指标** | 长轨迹存活率〔**B4**〕、下发与训练到的长度分布差〔**B4**〕、漂移与轨迹长度的相关性〔**B4**〕；补偿后残余漂移〔**B6**〕 |

⇒ **这个零差是"什么都没发生"的零差，不是"发生了但被修好"的零差。**
⇒ ★ **教训：设计观测点之前先问一句——我要量的那个差，物理上发生在哪两点之间？**
⇒ **顺序钉死：先量出漂移，再用分池补。别反过来。**
⇒ ★ 这一格是 **AReaL 两篇论文连着列为 future work、都没做的那一格**。

## 2 · 收束：一句题眼

一路上三次撞到同一个形状：
- 为了取 **3%** 的参数，存了整个模型（P3）；
- 为了用 **4%** 的 token，给全部 token 算了分（Track A P2）；
- 为**不分片**的机器，走了一条为**分片**设计的路径（P2 查因途中）。

> **「机制本身是对的，但它假设的运行条件和我们的不一样。」**
>
> 通用框架的默认值是在 **NVLink + 稠密监督 + 单轮任务**的假设下调出来的。
> **我们的活儿三条都不满足，所以要逐条量、逐条改。**

## 3 · ⚠️ 讲这个故事时的三条措辞纪律

| # | 纪律 | 为什么 |
|---|---|---|
| **①** | **decoupled PPO / 陈旧度上限 / 可打断 rollout 一律写成「在 agentic 负载上复现并验证」** | 它们是 AReaL 已发表的做法（arXiv 2505.24298），在框架里只是三个配置项。**暗示自研，读过论文的人一问就穿。**<br>真正属于我们的是四件：① 长度漂移的定量测量（论文明说是 future work）② 分池 × 异步的补偿组合 ③ 权重同步的根因 ④ 消费级无 P2P 拓扑上的这条曲线 |
| **②** | **「31%」必须和它的 after 一起出现** | 单独拿出来是**测量结果不是成果**。⇒ 见 §0.2 |
| **③** | **结论要带成立范围** | 例：「零漂移」只在轨迹时长 ≪ 同步周期时成立；「模型内部并行是净亏损」的量级随互联换代而变。**范围丢了，结论就变成错误陈述** |

核心工作：

## 5 · 遇到的问题，和怎么解决的

### P1 · 长轨迹训不了——而"能走完长链路"正是业务能力本身 ✅ 已解决

| | |
|---|---|
| **怎么发现** | 训练直接 OOM：**T=12288 / 16384 跑不起来，bs=2 就吃掉 25.54 GB** |
| **根因** | 显存的大头是那张"打分表"——模型每读到一个位置都要给词表 **151936** 个词各打一个分，`[16384 × 151936]` bf16 = **4.98 GB**，前向一份反向一份约 10 GB，**是全模型最大的瞬态张量**。<br>★ 再往下问一层：**这张表有多少是有用的？** 去数真实数据——**SFT 每条 5402 token 只有 204 个参与学习（3.8–4.9%），RL 侧 4.17%**（1755 条轨迹：prompt 88.3% / 工具返回 7.6% / 模型自己说的 4.2%）。**两个阶段同一量级 ⇒ 这是这类负载的结构性特征，不是偶然**。⇒ **那张巨表 96% 生下来就注定被丢掉** |
| **解法** | 稀疏投影：先只算到 hidden，按监督 mask **挑出真正需要的那几行**再做投影。**数学上完全等价，不是近似**——被丢弃位置的梯度本来就恒为 0；4 条与朴素实现的对拍测试守着 |
| **★ 指标** | 峰值显存 **16.94 → 10.40 GB（−39%）**；**T=12288/16384 与 bs=4 从 OOM 变为可训**（序列长度上限翻倍以上） |

★ 通用框架**没有这个问题**：它们跑单轮数学/代码，response 占 50%+。**负载画像决定该优化什么。**
★ **附带一条反直觉发现**：**bs=1 反而最快**（4400 token 已喂饱 170 个 SM）
⇒ **省下来的显存该换更长的序列，不是更大的 batch。**

### P2 · RL 侧同样在算白算的东西——但先量了分母，然后主动降级 🟡 落地待做

| | |
|---|---|
| **怎么发现** | RL 侧密度同样只有 **4.17%**，直觉上该照搬 P1 的做法、甚至自己写个融合算子 |
| **★ 根因（这里是关键）** | **先量分母**：微基准显示 **lm_head 在整个前向里只占 4.28%**。⇒ 哪怕把 95.8% 的浪费全省掉，**端到端也只快 4.3%**；而最笨的做法（按 mask 切片再喂现成算子）**就有 4.0%** |
| **解法** | **不自己写算子**，落地那个最笨的切片方案，并与框架内置融合算子 / Liger / 朴素实现同台跑分 |
| **★ 指标** | RL 侧峰值显存与耗时〔**A4**〕；三方跑分结果与归因〔**A4**〕 |

⇒ ★ **教训：「浪费掉的比例」和「能拿回来的收益」，中间隔着一个分母。**
96% 白算 ≠ 能快 96%，因为这件事本身只占全局的 4%。

⇒ 同一个实验还有一次自我更正：原预测密度 10–20%，**实测 4.17%，错了 2.5–5 倍**。
错因是拿配置里的 `max_response_length=1536` 当实际值，而实测 response 中位只有 **422**。
★ **估算里出现配置项的数字，先问一句「实际值是多少」。**

### P3 · 把模型切开分给多张卡，反而更慢 ✅ 已解决

| | |
|---|---|
| **怎么发现** | 按主流做法把模型切开分片，实测比单卡更慢 —— 每算一层都要把参数从别的卡拼回来 |
| **根因** | 这台机器四张卡之间**没有直连**（P2P 被驱动关掉，GeForce 从 4090 起都这样），数据要绕主机内存（约 NVLink 的 1/35）。分片意味着每算一层都要把参数从别的卡拼过来——**付的是数据量的代价** |
| **解法** | 改成数据并行（每卡一整份模型，每步只同步 LoRA，实测 **252 MB**） |
| **★ 指标** | 改数据并行后每步 **〔A6 填〕**，扩展比 **〔A6 填〕** |

| **★ 指标** | 同 3 卡、只改分片策略、取稳态：DDP `update_actor` **7.97 s** · ZeRO-2 **3.42×** · ZeRO-3 **6.02×** |

⇒ ⚠️ **但这条后来被自己推翻了一半，见 P7** —— 「6 倍」里的大部分不是分片的代价，
是一个**四个字节的对齐问题**。⇒ 讲这段时**必须连 P7 一起讲**，否则给出的是一个错误的结论。

### P7 · ★★ 「多给一张卡，分片反而快 4 倍」—— 根因是 **4 个字节** ✅ 已查实

| | |
|---|---|
| **怎么发现** | P3 量到 3 卡分片慢 **6.02×**，而按卡间带宽推算只该慢 4 秒、实测慢 40 秒 —— **量级对不上，说明模型是错的** |
| **一路排除** | 不是带宽（换机器带宽 ×4，惩罚纹丝不动）→ 不是通信次数（固定 4 GB，切 576 次比切 1 次还快 0.7×）→ 不是拓扑（同 3 卡上另外三个集合通信全正常）→ 也不是「NCCL 选错协议」（实测 3 卡与 4 卡的算法/协议选择**完全相同**） |
| **根因** | **16 字节向量化访存的对齐悬崖**：NCCL 的 Simple 协议 kernel 按 16 字节打包搬运，**每 rank 分块字节数只要不能被 16 整除，就整段退化成标量路径**。常见张量是 2 的幂次 —— **÷3 破坏对齐，÷4 天然保持** ⇒ 这才是「3 卡受诅咒」的真相 |
| **决定性实验** | 固定一切、只挪几个字节：`%16==0` 时 **13.2 GB/s**，**+4 字节**（`%16==4`）掉到 **1.1 GB/s** —— 差 **12×**；而 `%128` 完全不相干 |
| **真实路径验证** | 真实 ZeRO-3 训练里 all_gather 的 **335.5 GB 中 99.9% 的字节**落在错位分块上（主体每 rank 67,287,212 B，`%16=12`，**只差 4 个字节**）；同一次跑里 broadcast（不按 rank 切分）**0% 错位**，构成天然对照组 |
| **★ 指标** | 应急手段（切协议）：3 卡 ZeRO-3 `update_actor` **47.94 → 14.40 s（3.33×）**，同尺子复现 **3.23×**。治本手段（补齐分片）：每 rank 补 **4 字节**，代价 6e-8，收益按微基准最多 **12×**〔A16 验真实尺寸〕 |

⇒ ★ **这一条最能说明这条线的方法**：停在「NCCL 选错了协议」会得到一个**看起来完整、
实际是错的**根因，而且它导出错误的建议（换协议，代价是 all_reduce −30%）。
**多问一句「那它为什么选错」**，才碰到真正的地板 —— 而正解是补 4 个字节，没有任何取舍。
⇒ 责任落在三层的缝里（NCCL kernel 整段退化 / 成本模型看不见对齐这一维 / FSDP 只保证整除
不保证字节对齐），**最该修的是 NCCL** —— 唯一不需要跨层协商的那个〔A15 已成稿，待提〕。
