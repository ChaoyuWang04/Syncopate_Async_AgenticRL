## 0 · ★★★ 这份文档的唯一版本原则

# 第一部分 · Track B（框架/异步线）

## 1 · 故事怎么讲（完整时间线）

> **这个叙事的力量在于：每一步都是被数据逼出来的，没有一步是拍脑袋。**
> 十二段，可长可短——15 秒版讲 ①⑤⑫，3 分钟版全讲。

### ① 起点不是「我想做异步」，是「多卡没起作用」

上四张卡、按主流做法把模型切开分片，结果**三张卡每步 1182 秒，一张卡 198 秒——多给三张卡反而慢 6 倍**。
查下去发现这台机器卡间没有直连（P2P 被驱动关掉，GeForce 从 4090 起都这样），只有 **6.4 GB/s**，
是数据中心 NVLink 的 **1/140**。

⇒ **第一个认知：搬运比计算贵得多。并行不该发生在模型内部，该发生在外部。**（E02 / E00）

### ② 改成「三张卡训练 + 一张卡生成」的异步摆法，跑通了，然后量了一下——只快 1.59 倍

这里有个容易被跳过的动作：手上原本有个 32.6 秒的老基线，看着很漂亮，
**但那次开的算法不同（bypass vs decoupled），跟现在根本不可比**。所以专门补了同机同配置的对照。

⇒ **加速比必须有同机分母，否则就是在自己骗自己。**（E08 §4.6）

### ③ 换个维度交叉验证：整机占空比只有 31%

轮询四张卡的利用率，154 个采样点、覆盖一个完整周期：
**生成卡 82.5% 的时间在闲着、功耗只有 47.7 W——这张卡满载能到 450 W，它基本在待机。**

⇒ **时间维度（只快 1.59×）和空间维度（只用 31%）互相印证，指向同一件事。**（E08 §4.5.1）

### ④ 顺着找：一步的时间拆开，权重同步占 18.8%

而我们只有 **132 MB** 的 LoRA 要传，6.4 GB/s 上理论 **0.02 秒**。实测 **55.8 秒**——**差 2500 倍。**

### ⑤ ★ 故事的核心：四步查因

```
两点反解    首次推 8 GB / 稳态推 132 MB，数据量差 60× 而耗时只差 1.85×
            两个方程解两个未知数 → 传输 0.8 s，固定开销 55.0 s = 98.6%
            ★ 这一步零 GPU 成本，纯用已有日志
微基准称重  把怀疑的操作单独拎出来量：分配 buffer 2.6 ms、清缓存 12.2 ms → 全部排除
分步计时    插探针跑一次：编排 8 步里 5 步合计 0.038 s（0.06%），99.94% 在第 5 步
A/B 排除    怀疑是"取参数"路径 → 关掉那个开关，只变这一个变量 → 60.13 vs 61.44，没动
            ★ 但关掉后走的是完全不同的取参数路径，两条路都是 60 秒
            ⇒ 成本根本不在"取参数"，一次砍掉一整条分支
```

⇒ 这个过程里**推翻了我自己提出的 4 个看起来很合理的假设**。
⇒ **教训：A/B 的负结果能一次排除一整片可能性，比"再读一遍代码找可疑处"有效得多——
读码只能生成假设，不能排除假设。**（E12 §4.5）

### ⑥ 定位到最后一层，然后改

把第 5 步再切成「训练侧取参数+发」和「生成侧收+装进 vLLM」两半，
根因是〔**B1**〕；改法是〔**B1**〕，**权重同步 55.8 → 〔X〕秒，占步耗时 18.8% → 〔Y〕%**。

顺带一刀：默认缓冲区是 2048 MB **双缓冲 = 4 GB**，其中一份住在已被 vLLM 占了 24.65 GB 的生成卡上，
**剩 1.99 GB 要分配 2.00 GB，差 0.01 GB 就 OOM**——而实际只推 132 MB。
调小到 512 MB 后〔**B2**：是否按比例降耗时〕，**同时消除了分卡模式下的偶发 OOM**。

⇒ ★ **这里要说清楚一件事**：「`gpu_util 0.75` 是安全值」这个旧结论是错的，
**0.75 只是运气好擦过去。解法不是压 gpu_util，是让缓冲区匹配真实传输量。**

### ⑦ 查因途中顺手发现另一笔账

算法每步要做一次"存档"（把模型换成旧版本参数算一遍、算完换回来），实测 **4.34 秒/步**。
数了一下：**存了 902 个张量、8.309 GB，而其中真正会变的只有 3.18%**——
剩下 96.8% 是冻结的基座，存了和上一版**逐字节相同**。

**改动是一行 `if param.requires_grad`：每步 4.34 → 0.083 秒，端到端省 5.7%。**

⇒ **这笔钱比整套自写 kernel 的预期收益（4.3%）还大，而改动是一个 `if`。**
⇒ 配 3 条测试，其中一条专门钉「全参微调时自动退回全量」——
**前提失效要靠测试守，不是靠注释提醒后人。**（E13）

### ⑧ 三种摆法放到同一把尺子上

除了摆法本身，其余配置全部一致（同样的算法、同样的打包、同样的步数）：

```
colocate       1 卡    117.8 s/步      1.00×
one_step_off   3+1     〔B3〕          〔B3〕
fully_async    3+1      74.1 s/步      1.59×
```

⇒ **这三行是"异步到底值多少"的完整回答**，也是所有加速比的分母。

### ⑨ ★ 正确性那一侧：最能体现工程判断的一段

异步理论上会丢长任务——短的先跑完、长的被切断，**而长链路正是 agent 的核心能力**。
于是按轮数**逐桶**比"发出去的"和"训练到的"（不是比均值，均值会把问题藏起来），
**结果零差：7200 对 7200，14 个桶全同。**

**但我去看了记录点的位置，发现它在"轨迹跑完并算完分之后"**——
所以它记的是"**跑完了**"不是"**发出去了**"；我量的是「完成 → 训练」，
**而漂移发生在「发出 → 完成」那一段：半路被杀的轨迹根本走不到那行代码，在我的账上从来就不存在。**

⇒ **这个零差是"什么都没发生"的零差，不是"发生了但被修好"的零差。**
⇒ **教训：设计观测点之前先问一句——我要量的那个差，物理上发生在哪两点之间？**（E08 §6）

### ⑩ 把仪器装到对的地方，再把系统推到会出问题的地方

观测点移到 case 真正被交给 agent loop 的那一刻（带 `param_version`），与完成端配对；
同时**主动把系统推到触发条件上**（收紧陈旧度上限 / 调小同步周期 / 用更长的轨迹）——
**要测出漂移，得先让它发生。**

结果：长轨迹存活率〔**B4**〕、下发与训练到的长度分布差〔**B4**〕、
以及漂移与轨迹长度的相关性〔**B4**〕。

⇒ ★ **这一格是 AReaL 论文明确列为 future work、两篇连着都没做的那一格。**

### ⑪ 量出来之后，用采样权重去补偿

我们手上有一个现成的杠杆：按 reward 方差给 case 加权的动态分池。
一旦量出「哪类 case 系统性没被训到」，就能用采样权重补回去〔**B6**〕。

⇒ **顺序钉死：先量出漂移，再用分池补。别反过来。**
⇒ **「量出漂移 + 用采样权重补偿」这个组合，AReaL 没做，框架里也没有。**

配套一把统一的尺子：**ESS / TIS / 逐 token logprob 差**，
用来同时度量量化、路由抖动、陈旧度三种失配〔**B7**〕；
并把我们的陈旧度阈值折算成论文里的 η，回答**「我们在他们那条消融曲线的哪个位置」**〔**B7**〕。

### ⑫ 收束：题眼

所有优化最后都过同一道任务级尺子：冻结 EVAL 128×8 配对比较（自报 MDE ≈ 0.05）
+ 能力构成 + 决策位熵〔**B5**〕。**只报吞吐不报任务精度的优化不算完成。**

最终结果：**每步 74.1 → 〔Z〕秒，整机占空比 31% → 〔W〕%，任务精度无显著差异。**

而一路上三次撞到同一个形状：
- 为了取 **3%** 的参数，存了整个模型（E13）；
- 为了用 **4%** 的 token，给全部 token 算了分（E11）；
- 为**不分片**的机器，走了一条为**分片**设计的路径（E12）。

> **「机制本身是对的，但它假设的运行条件和我们的不一样。」**
>
> 通用框架的默认值是在 **NVLink + 稠密监督 + 单轮任务**的假设下调出来的。
> **我们的活儿三条都不满足，所以要逐条量、逐条改。**

# 第二部分 · Track A（软硬结合线）

## 4 · 故事怎么讲（完整时间线）

### ① 起点是一次 OOM，不是「我想写算子」

业务上 agent 的价值在于**自己走完长链路**（多轮工具调用、自己纠错），而长链路意味着长序列。
**实测：T=12288 / 16384 直接 OOM，bs=2 就吃掉 25.54 GB。**
⇒ **长轨迹被显存判了死刑，而它正是业务能力本身。**

### ② 去看显存花在哪：最大的瞬态张量是那张「打分表」

模型每读到一个位置，都要给词表里 **151936** 个词各打一个分。
`[16384 × 151936]` 的 bf16 张量 = **4.98 GB**，前向一份、反向再一份 ⇒ 约 10 GB。
**它是全模型最大的瞬态张量，也是 OOM 的元凶。**

### ③ 问一个别人没问的问题：这张表有多少是有用的？

去数真实数据：
```
SFT   每条 5402 token，只有 204 个进 loss   ⇒  3.8–4.9%
RL    1755 条真实轨迹                       ⇒  4.17%
      （prompt 88.3% / 工具返回 7.6% / 模型自己说的 4.2%）
```
⇒ **两个阶段同一量级 ⇒ 这不是某个阶段的偶然，是这类负载的结构性特征。**
⇒ **那张巨表 96% 生下来就注定被丢掉。**

★ 而通用 RL 框架**没有这个问题**：它们跑单轮数学/代码，response 占 50%+。
**负载画像决定该优化什么。**

### ④ 于是做稀疏投影

**做法**：先只算到 hidden，按监督 mask **挑出真正需要的那几行**，只对它们做投影。
**数学上完全等价，不是近似**——被丢弃位置的梯度本来就恒为 0。**4 条与朴素实现的对拍测试守着。**

```
SFT 侧   峰值显存      16.94 → 10.40 GB   (−39%)
         T=12288/16384  OOM → 可训
         bs=4           OOM → 可训
RL  侧   〔A4〕
```

★ **附带一条反直觉发现**：**bs=1 反而最快**（4400 token 已经喂饱 170 个 SM）
⇒ **省下来的显存该换更长的序列，不是更大的 batch。**

### ⑤ ★ RL 侧照做之前先量分母 —— 然后主动降级

微基准结果：**lm_head 在整个前向里只占 4.28%。**
所以哪怕把 95.8% 的浪费全省掉，**端到端也只快 4.3%**；
而最笨的做法（按 mask 切片再喂现成 kernel）**就有 4.0%**。

⇒ **不自己写 kernel，落地那个最笨的切片方案**〔**A4**〕，并与框架内置融合算子 / Liger / 朴素实现同台跑分〔**A4**〕。
⇒ ★ **教训：「浪费掉的比例」和「能拿回来的收益」，中间隔着一个分母。**
96% 白算 ≠ 能快 96%，因为这件事本身只占全局的 4%。

（同一个实验还有一次自我更正：原预测密度 10–20%，实测 4.17%，**错了 2.5–5 倍**。
错因是拿配置里的 `max_response_length=1536` 当实际值，而实测 response 中位只有 **422**。
⇒ **估算里出现配置项的数字，先问一句「实际值是多少」。**）

### ⑥ 第二把筛子：硬件拓扑

把模型切开分片，**三卡每步 1182 秒 vs 单卡 198 秒——多给卡慢 6 倍**。
根因是这台机器卡间没有直连、只有 6.4 GB/s（NVLink 的 1/140）。
改成数据并行后取得 **3.00× 线性扩展**。

⇒ **「把模型切开、每步再拼回来」整一类方案在这台机器上不是慢一点，是不能用。**

### ⑦ 想上 30B MoE —— 先用零 GPU 的探针拦下三件事

**半天、纯 CPU、一张卡都没占**：
1. 读 config 的 `architectures` 字段 ⇒ 原定模型**当前栈根本不支持**，换模型；
2. 用真 config 核算 ⇒ 分片时每个 micro-batch 要 gather **61.1 GB 而只用得上 10%**
   （MoE 每次只激活 128 个专家里的 8 个）⇒ **分片路线堵死**；
3. 在 meta 设备上数模块 ⇒ **18,673 个线性层里 18,432 个（98.7%）在专家里**
   ⇒ LoRA 的默认配置会让可训练参数变 26 倍、每步同步量从 132 MB 变 3.39 GB。

⇒ ★ **教训两条**：「day-0 支持」必须落到 `architectures` 字段去验证，不能引用新闻稿；
**继承来的默认值，换了模型结构要重新审一遍**（两分钟、零显存）。

### ⑧ 于是量化在这条线上第一次有了正当动机

**★ 量化的目的是省通信，不是省显存本身。**
把冻结的基座压到 4bit（约 17 GB），**每张卡放完整一份**，纯数据并行，每步只同步 132 MB 的 LoRA。

三摆法实测：分片 / 4bit 复制 / 专家并行——
**每步训练侧通信从〔A2〕降到 132 MB，训练侧吞吐〔A2〕**。
精度侧**不止 PPL**：任务级配对回归（MDE 0.05）+ 采样分布 ESS〔A2〕
——**生态的量化验证止步 PPL，而 PPL 量不出"采样分布偏了多少"。**

⚠️ **一条不许复活的理由**：量化的动机只能是省通信。
别退回「省显存换 KV 池」——那条因果链已被实测整条推翻
（命中率 96.7–97.5%、KV 池用不到一半、零 preemption）。**推翻过的理由不许复活。**

### ⑨ 这块卡到底什么能点亮：能力探底

sm_120 是消费级 Blackwell：**有原生 FP4/FP8，没有 TMEM**（数据中心 Blackwell 才有）
⇒ 编程模型退回 Ampere 式 `mma.sync`，**Triton + inline PTX 全覆盖，没有够不着的指令**。
但生态几乎没人点亮它——Triton 的低精度路径在这块卡上会**静默退化成 bf16**。

⇒ **「这块卡上什么是真的、什么是假的」本身就是没人做过的测量**：
静默退化复现〔**A3**〕、FP8 GEMM roofline〔**A3** 实测 TFLOPS〕、
FP4 `mma.sync` inline PTX〔**A3**〕。

### ⑩ 最后一层：执行层的空转

以 nsys/ncu 定位 decode 阶段 GPU 空转的根因，按瓶颈类型逐项归因与消除〔**E14**〕。
⚠️ 这一步的门槛是先把一步的时间完整拆开〔**A5** · E01〕——**没有拆解就谈消泡是编。**

### ⑪ 收束：这条线的纪律

> **不是「我会写 kernel」，是「我能证明该写哪个 kernel」。**

反面教材就在本项目里：早期规划过一条因果链（前缀缓存不够 ⇒ 量化扩容 ⇒ 写 kernel），
**被实测整条推翻**（命中率 96.7–97.5%、KV 池只用不到一半、零 preemption）。
**当时那道菜没过任何一把筛子，靠的是推演。**

⇒ **这条 track 已经两次用实测否决了自己原定的开发计划**（E11 主动降级、上面那条因果链）。
⇒ ★ **「证明了不该做」和「做成了」在工程上都是产出**，只是前者写不进简历的成果栏
——**所以要主动在面试里讲，别等被问。**
