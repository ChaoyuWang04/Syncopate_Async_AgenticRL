## 1 · 问题与预测

**问题**：异步下「下发的」和「训练到的」分布是否有系统性差异？特别是长任务会不会被稀释？

**★ 预测（写死于 `TRACK-B` §0.5）**：
- **P-B5**：异步下训练到的轨迹**长度分布短于**下发的 ⇒ 长任务被系统性稀释。
- 若无差异，说明 partial rollout 的续写机制生效良好。

## 3 · 方法

两端各取一份，比**分布**不比均值：
- **下发端**：`dispatched.jsonl`（我们自己的 `record_dispatch` 写的）
- **训练端**：`rollout_dumps/*.jsonl`（verl 写的，训练实际消费的）
- 对照量：条数 / 轮数分布（逐桶）/ 墙钟耗时 / 截断率 / reward
- 辅助：日志里的 `fully_async/count/dropped_stale_samples`、`fully_async/partial/*`

## 5 · 结论

1. **「完成 → 训练」这一段零漂移。** 7200 = 7200，逐桶相同，`dropped_stale_samples` 全程 0。
2. **陈旧是存在的，但不是「跨版本生成」**：`stale_trajectory_processed` 中位 288
   （占 `total_generated_samples` 444 的 65%）⇒ 大量轨迹是**用旧版本权重整条生成、之后才被训练**；
   而 `partial/*` 全程 0 ⇒ **没有任何一条轨迹跨越两个权重版本**。
   ⇒ **staleness ≠ partial，这次把两者分开量出来了。**
3. **`partial_rollout=True` 设了但一次都没触发。** 需要解释——见 §8-②。
4. ⇒ **P-B5 在本配置下未发生。**
5. **★ 「是仪器没测到，还是漂移真没发生？」——答案是后者为主，且有旁证：**
   - 仪器缺口是真的（§6），但 **artifact 文件提供了一个绕过它的观测点**（§4.4）；
   - 那 400 条未入账的轨迹**长度分布与已入账的无差异**（轮数均值 4.540 vs 4.597，
     ≥7 轮 23.25% vs 23.96%，截断率 7.50% vs 7.31%）⇒ **没有长度偏差**；
   - **机制上也说得通**：轨迹耗时中位 **17.8 s**，而同步周期约 **296 s**
     ⇒ 一条轨迹只占同步周期的 **6%**，绝大多数能在两次同步之间跑完；
     `partial/*` 全程 0 也印证**没有轨迹被真正中断过**。
   ⇒ **漂移没发生的主因是「轨迹远短于同步周期」，不是「我们没测到」。**
6. ⚠️ **成立范围（必须连着引用）**：上条只在 **轨迹时长 ≪ 同步周期** 时成立。
   M8 之后轨迹变长、或 `sync_every` 调小、或 `staleness_threshold` 收紧，**条件就变了**。
7. ⬜ **遗留**：那 400 条（5.3%）为什么写了产物却没入账，仍未查清——
   `record_dispatch` 就在 `score_and_persist` 的下一行。**这是记账缺口，需要单独查**（§8-④）。

## 6 · ⛔ 推翻了什么 / 结论的边界

> **原猜想（P-B5）**：异步下训练到的轨迹长度分布短于下发的。
>
> **实测**：**完全没有差异**（逐桶零差，7200=7200）。
>
> **推翻后**：**不是"我们解决了漂移"，是"触发条件没出现"**——
> 没有丢弃（`dropped_stale_samples`=0）、没有中断续写（`partial/*`=0），
> 两端自然相同。**零差是"什么都没发生"的零差，不是"发生了但被修好了"的零差。**
>
> **★★ 教训（本报告最重要的产出）：仪器装错了位置。**
> `record_dispatch` 的调用点在 `verl_agent_loop.py:300` —— **rollout 跑完、算完分之后**。
> 所以它记的是「**跑完了**」，不是「**发出去了**」。
> ⇒ 我们量的是「**完成 → 训练**」这一段，而 **AReaL 说的漂移在「发出 → 完成」那一段**：
> **被中断/超时/丢弃的轨迹根本到不了 `record_dispatch`，也就永远不会出现在"下发"里。**
> ⇒ **偏长的轨迹如果在完成前就被杀掉，我们这套仪器一条都看不见。**
>
> 这是本项目「机制在但没接上」的又一个变种：**机制接上了、判据也打了、数也出了——
> 但仪器装在了下游，测的是一段本来就不会有差异的区间。**
> ⇒ **以后设计观测点，先问一句：「我要量的那个差，物理上发生在哪两点之间？」**

## 8 · 下一步 / 衍生问题

1. **★ E08-c · 把仪器移到真正的下发点**（🟢 写码）——
   在 case 被交给 agent loop 的那一刻记一条（含 case_id + 起始 param_version），
   与完成端配对。**这样才能量出「发出 → 完成」的存活率，以及它和轨迹长度的相关性。**
   ⚠️ 现在这个文件名叫 `dispatched` 但记的是完成——**改之前先想清楚是改语义还是加一个新文件**，
   别让历史数据的口径变了却没人知道。
2. **为什么 `partial_rollout` 一次没触发？**（🟢 读码 + 🔴 验）
   假设：rollouter 在同步前会**排空**在飞的请求，所以没有轨迹被真正中断。
   若为真，则「abort → 续写」这条路径在我们的负载上从未被走过，
   **`partial_rollout=True` 是一个没生效的开关** ⇒ 又一个「机制在但没接上」。
   反证也简单：轨迹耗时中位仅 17.8 s，而同步周期约 296 s、同步本身 55.8 s。
3. **把系统推到触发条件上**（🔴）——要测出漂移，得让它发生：
   调小 `staleness_threshold` / 调小 `sync_every` / 用更长的轨迹（M8 之后）。
   **这是一个需要设计的实验，不是把参数拧一拧就跑。**
4. **★ 查那 400 条的记账缺口**（🟢 读码）——
   `record_dispatch` 就在 `score_and_persist` 的下一行，理论上不该差 5.3%。
   候选原因：① 权重同步时 `abort_replicas` 取消了 agent loop 的 asyncio task，
   恰好卡在两行之间；② 整组被下游拒绝（50 个**完整的 8 人组**这个形状强烈暗示是**组级**动作，
   不是随机取消）；③ 多进程追加同一文件的丢写。
   **②最可疑**：GRPO 组内 8 条 reward 全同 ⇒ advantage 恒 0 ⇒ 组被丢弃，是已知的常见行为。
5. **E08-b · colocate 同机基线**（🔴，30 分钟）——所有加速比至今没有同机分母；
   而且现在手上有 one_step_off 和 fully_async 两个模式的数，就差这个分母把它们放到同一把尺子上。
