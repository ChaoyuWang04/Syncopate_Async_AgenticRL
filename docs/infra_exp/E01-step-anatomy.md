## 1 · 问题与预测

**问题**：`update_actor + old_log_prob + ref` 占一步的 72–85%。**那段时间的 GPU 在算什么？**

**★ 预测（看数据之前写死）**

> **P1**：trainer 侧 GPU 时间以 **GEMM 为主（>50%）**，其中 lm_head 投影是可辨认的一大块
> —— 这是 E11「监督密度 4.17%，95.8% 的 lm_head 白算」赖以成立的前提。
> **如果 GEMM 不占大头**，E11 的整条论证就要重估。
>
> **P2**：attention 占比**不大**（<20%）—— 我们的序列只有 3.5k+1.5k，不是长上下文负载。
>
> **P3**：能按阶段切开。（⛔ **这条当场就错了** —— 没有 NVTX 就切不开，见 §6.1）

## 4.5 ★★★ A5 · 阶段归属（`--nvtx` + nsys 重采，2026-08-17 20:28）

给 verl 的 `marked_timer` 套上 NVTX（`verl_patches`，两侧各打判据行，实测 12 条）之后重采。
数据 `_audit/infra/a5_e01_nvtx_nsys.json` · 采样窗口 28.2 s（实际覆盖，见 §7-2 的截断问题）。

| 阶段（NVTX range） | kernel 时间 | **占比** | kernel 数 | 对照：墙钟占步（B2-512） |
|---|---|---|---|---|
| `update_actor` | 20.91 s | **44.8%** | 350,220 | 52.6% |
| `old_log_prob` | 10.19 s | **21.8%** | 147,272 | 16.4% |
| `ref` | 7.74 s | **16.6%** | 76,532 | 14.1% |
| **⇒ 三次前向合计** | **38.84 s** | **83.2%** | 574,024 | **83.1%** |
| （不在任何 range 内） | 7.89 s | 16.9% | 132,109 | ← 主要是 rollout 侧（不在 trainer 的 range 里） |

### ★★ 这张表回答了 B12 最关键的那个问题

**kernel 口径 83.2% ≈ 墙钟口径 83.1%** ——
⇒ **那 83% 是 GPU 真在算，不是在等、不是在同步、不是在搬。**

这条**排除了一整类解法**：
```
❌ 更好的重叠 / 流水 / 消泡          —— 没有泡可消，卡是满的
❌ 挪到闲着的 rollout 卡              —— 挪过去还是要算这么多，只是换张卡付
✅ **做更少的计算**                   —— 只剩这一条：要么不做（关 KL）、要么算得更少（稀疏）
```
⇒ **E17 的三臂设计（关 ref / 降频 / 共享前向）方向是对的**，而「挪卡」那条可以划掉了
（原本写在 E17 §8-3 里，作为"若 ref 大部分在等就挪卡"的备选 —— **前提不成立**）。

⚠️ **成立范围**：单次采样、窗口 28 s、`--steps 16` 那一跑（v13 / bucket 512 / dynamic_bsz=False）。
kernel 占比与墙钟占比的口径不同（前者是 GPU 忙的时间构成，后者含 CPU 侧与等待），
**两者接近本身就是结论**，但不该当成同一个量。

## 4.6 ⛔ 空泡分析：**「卡是满的」这句话说过头了**（2026-08-18）

§4.5 的结论写的是「kernel 口径 83.2% ≈ 墙钟口径 83.1% ⇒ **那 83% 是真在算，不是在等**」，
并据此划掉了"消泡"整类解法。**把空档真正算出来之后，这句话要收窄。**

尺子：`analyze_nsys_step.py` 新增的 `gap_analysis` —— 把每个进程的 kernel 按时间排好，
算相邻之间的空档，再**按长度分档**（分档很关键：一堆小空档和几个大空档，解法完全不同）。

| 进程 | 跨度 | 忙 | **空** | 忙占比 | 空档按长度分布（秒） |
|---|---|---|---|---|---|
| trainer rank A | 28.2 s | 21.1 | **7.2** | **74.6%** | <10µs 0.28 · 10–100µs 1.26 · **0.1–1ms 3.67** · 1–10ms 0.27 · **>10ms 1.74** |
| trainer rank B | 27.8 s | 21.7 | **6.1** | **78.2%** | <10µs 0.29 · 10–100µs 1.04 · **0.1–1ms 2.90** · 1–10ms 0.31 · **>10ms 1.58** |
| trainer rank C | 6.0 s | 3.9 | 2.1 | 65.7% | 0.1–1ms 0.86 · >10ms 0.72 |

> **原说法**：「那 83% 是真在算，卡是满的，没有泡可消。」
> **实测**：trainer 卡在采样窗口里**只忙 74.6–78.2%**，**有 21.8–25.4% 的时间是空的**。
> **推翻后**：两件事要分开 ——
> **① 构成**（83% 的 GPU 工作属于三次前向）**成立，没被推翻**；
> **② 密度**（那段时间卡满不满）**我当时没测，却当成测过了** —— 实际是四分之一的空档。
> **教训**：**「A 占 B 的 83%」和「B 期间卡是满的」是两个独立的命题**，
> 我用前者的证据下了后者的结论。⇒ 占比类结论**不能推出**密度类结论。

### 4.6.1 那这些空档是什么、值不值得打

```
0.1–1 ms 档   3.67 s（占全部空档的 51%）   ← 数量多、单个不大 —— 像是 kernel 之间的调度/派发间隙
>10 ms  档   1.74 s（24%）                 ← 少数大空档 —— 像是同步点（等别的 rank / 等 CPU）
```

⇒ **0.1–1 ms 那一档是最大的一块，合计约占墙钟的 13%**。
⚠️ **但这不等于"能省 13%"** —— 要先知道它们**为什么存在**：
CPU 侧派发不过来（E01 §4.4 量到 92.5 万次 launch、中位 4.2 µs）、
等 memcpy、还是等别的进程。**本节只回答"有多少、多长、在谁身上"，不回答"为什么"。**

⇒ **下一步（排成 A18）**：把每个空档与当时 CPU 侧正在执行的 API 调用
（`CUPTI_ACTIVITY_KIND_RUNTIME`）对齐，得到「空档 → 成因」的归属表。
**这才是"该不该消泡"能被回答的地方**，而这一步同样是可计算的，不需要图形界面。

## 4.7 ★ 术语澄清：**这些百分比的分母各是什么**（2026-08-18 应问补写）

同一份报告里出现过好几个百分比，它们**分母不同**，混着读一定会乱。逐个钉死：

| 说法 | 分母是什么 | 怎么量的 | 典型值 |
|---|---|---|---|
| **① 三次前向占步 83%** | **一个 global step 的墙钟时间** | verl 的 `timing_s/*` 行（CPU 侧计时） | 83.1%（B2-512） |
| **② 三次前向占 kernel 时间 83.2%** | **该窗口内 GPU 真在跑 kernel 的总时间** | nsys，按 NVTX 阶段归属 | 83.2% |
| **③ trainer 卡忙 74.6%** | **该进程的时间跨度**（忙 + 空） | nsys，kernel 区间求并 | 74.6–78.2% |
| **④ 整机占空比 31%** | **四张卡 × 墙钟**（含 rollout 那张几乎全闲的卡） | `nvidia-smi` 每 2 秒采样 | 31% |
| **⑤ GEMM 占 58%** | **该进程的 kernel 时间**（不是墙钟） | nsys，按算子归类 | 58% |

**⇒ 回答"83% 是什么的 83%"**：是 **①一个 global step 的墙钟时间**里，
`update_actor + old_log_prob + ref` 这三段加起来占的比例。
**②是一个独立的验证**：在 GPU 真在算的那部分时间里，这三段也占 83.2% ——
**两个不同的分母给出几乎相同的比例**，这才是「构成」这个结论可信的原因。

**⇒ 而③是另一件事**：它说的是**密度**（那段时间卡满不满），答案是 **74.6–78.2%，
也就是有 21.8–25.4% 的空档**。①②③ 三者不矛盾：
```
一个 step 的墙钟里，83% 属于三次前向（①）
这 83% 的时间里，GPU 有约 3/4 在跑 kernel、1/4 是空档（③）
而这些 kernel 里，58% 是矩阵乘（⑤）
```
⚠️ **④（整机 31%）不能和①②③直接比** —— 它的分母含**那张几乎全闲的 rollout 卡**，
而且是 `nvidia-smi` 的粗采样（有 kernel 在跑就算忙，不看跑得满不满）。

## 5 · 结论

1. **trainer 侧 GPU 时间的主体是 GEMM（58%）**，attention 只有 10–12%，
   elementwise 有 24–25%（比预期高，值得下一轮细看是谁）。
2. **当前栈在 sm_120 上跑的是 Ampere 代（`cutlass_80` / `s16816`）的 tensorop kernel。**
   E16 的立足点从「文档这么说」升级成「热点路径实测如此」。
3. **E13 已落地的优化在 kernel 层被独立证实**：每步 CPU 快照 8.309 GB → **0.26 GB**。
4. ✅ **阶段归属拿到了**（§4.5）：三次前向的 **kernel** 时间合计 **83.2%**，
   与墙钟口径的 83.1% 几乎相等 ⇒ ★ **那 83% 是真在算，不是在等**。
   ⇒ 这条**排除了「消泡 / 重叠 / 挪到闲卡」一整类解法**，只剩「做更少的计算」。

## 6 · ⛔ 推翻了什么

### 6.1 「有了 nsys trace 就能把一步按阶段切开」

> **原猜想**：采到 trace 就能回答「update_actor / old_log_prob / ref 各占多少」——
> A5 因此被标成「🐟 挂在任意一次训练上零成本做掉」。
> **实测**：trace 里 NVTX 只有 3 条，全是 NCCL 自己打的（`NCCL Progress 0` ×8、`NCCL` ×4、`CCCL` ×4）。
> **verl 默认不打阶段 range**，而 CUDA kernel 名字里没有阶段信息。
> **推翻后**：A5 = 「采 trace」+「**先给 verl 打 NVTX**」两件事，不是一件。
> 前者零成本、后者要写码，而且**要挂在我们自己的跑上**（改的是启动路径）。
> **教训**：**「挂在别人的跑上零成本」只对「不需要改被测对象」的观测成立。**
> 需要打标记的观测，天然要求控制启动 —— 这一条在排队列时被漏掉了，
> 于是 B12 的门槛看起来比实际低。

### 6.2 「每 rank 每步都在搬 8 GB」（差点写进结论）

> **看到的**：三个 trainer rank 各有 8.31 GB 的 D2H 和 8.31 GB 的 H2D。
> **差点得出**：E13 的修复没生效 / 又退化了。
> **实测**：按 5 秒分桶一看，**全部集中在窗口开头的两个桶**，之后每次只有 0.26 GB。
> **推翻后**：那是一次性事件（疑似 ckpt 保存），稳态是 0.26 GB，**E13 的修复好着**。
> **教训**：**总量除以时间会把「一次性事件」摊成「持续开销」。**
>   凡是要区分「一次性 vs 每步」的量，**先按时间分桶再下结论**。

## 7 · 踩的坑

1. **`deviceId` 全是 0，不能当成「都在 GPU0 上」。**
   Ray 给每个 worker 只设一张卡的 `CUDA_VISIBLE_DEVICES` ⇒ 每个进程眼里自己那张卡就是 0。
   ⇒ 按 `deviceId` 聚合会把四张卡叠成一张，算出「GPU0 忙 97%」这种假数。
   **正确做法是按进程聚合**（一个进程 = 一张物理卡）。
   ★ 这和 E18 §7-1（`/proc/<pid>/environ` 是 exec 时快照）同一个形状：
   **拿到的字段名对，含义却是进程局部的。**
2. **trace 被截断，绝对时长不可用。**
   请求 180 s，实际 kernel 只覆盖 **75.17 s**；而且三个 trainer rank 里有两个在 t≈30 s
   就不再有 kernel（rank0 到 75 s）。
   ⇒ **不能**据此说「rank0 干了 9 倍的活」。构成比可用（三个 rank 互相印证），时长不可用。

3. **sqlite 中间产物 9.4 GB**（.nsys-rep 只有 386 MB）。分析完就删，别让它躺在盘上。
