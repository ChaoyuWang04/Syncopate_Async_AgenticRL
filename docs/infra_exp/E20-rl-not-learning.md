## 1 · 现象（业务侧的说法 + 我们的数）

Chaoyu 的观察：**跑完整个数据集、100 多步之后，更新量太小太小，能力几乎没有变化。**
而把 `lr` 从 `1e-5` 提到 `3e-5` 就会 ESS 崩。

我们手上正好有 `lr=3e-5` 的两次 60 步跑（B16 的两臂），把关键指标按时间取首末：

| 指标 | ref_on（**52 次更新**） | ref_off（**60 次更新**） | 说明 |
|---|---|---|---|
| `rollout_is_seq_mean` | **0.993 → 0.492** | 1.054 → 0.578 | 序列级 IS 权重的均值，理想值 1.0 |
| `rollout_is_seq_std` | 0.291 → **0.672** | 0.348 → 0.647 | 方差翻倍 |
| `rollout_is_seq_min` | 0.300 → **0.0000** | 0.177 → **0.0000** | ★ **有序列的权重被打到 0** |
| `log_ppl_diff`（每 token） | **0.00010 → 0.02308** | — | ★★ 230× |
| `response_length/mean` | 505 → **694** | — | 序列还在变长 |
| `actor/grad_norm` | 0.0018 → **0.0007** | 0.0073 → 0.0015 | ★ **梯度反而在变小** |
| **权重位移** `‖ΔW‖/‖W‖` | **0.102%** | 0.119% | 正常 LoRA 微调是 0.5–5% |

**⇒ 一句话：策略只动了 0.1%，而 rollout 与 trainer 之间的序列级权重比已经塌了一半，
梯度跟着变小 —— 模型在"越学越不敢学"。**

⛔ **口径更正（2026-08-18，由主线 17 §7.1 指出并复核）**：上表原写「13 次 / 15 次更新」，
**那是 timing 行数（= `param_version` 数），不是优化器更新次数**。
真正的更新次数 = `rollout_dumps/` 的文件数，**逐文件数过：52 / 60**（`sync_every=4`，52/4=13）。
⇒ 本报告 §3.6 算出的「110 步 ⇒ 109 次更新」是**对的**，而 §1 这里错了 4 倍 —— **报告内部曾自相矛盾**。
★ 交叉验证（也是判定 52/60 才对的依据）：
```
每次更新的位移  m7b(lr 1e-5) 0.0487%/110 = 0.00044%
               B16 (lr 3e-5) 0.102% /52  = 0.00196%   ⇒ 比值 4.4 ≈ lr 比值 3  ✅
若按 13 次记                  0.102% /13  = 0.00785%   ⇒ 比值 18×            ❌
```
★★ **教训**：同一份日志里有**三个都叫 step 的计数器** ——
`training/global_step`（每 fit step 跳 `sync_every`）· ckpt 目录名（= `param_version`）·
**dump 文件数（= 真正的优化器更新次数）**。**引用"步数"之前先说清是哪一个。**

## 2 · ★★ 机制：序列级 IS 在长序列上是指数脆弱的

序列级重要性权重是逐 token 的乘积：

```
w_seq = Π_t  π_train(t) / π_rollout(t)  =  exp( Σ_t Δlogp_t )  ≈  exp( L · Δlogp̄ )
                                                                    ↑ 序列长度
```

代入我们的实测：

```
L ≈ 694 token，Δlogp̄ ≈ 0.023   ⇒   L · Δlogp̄ ≈ 16
⇒ 未截断的权重会落在 e^{±16} 这种量级上 —— 而截断阈值是 2.0
⇒ **绝大多数序列要么被顶到 2.0、要么被压到 0**，中间几乎没有
（观测到的 mean 0.49 / std 0.67 / min 0.0 正是这种两极分布）
```

★ **这不是"陈旧度有点大"，这是"尺子本身在这个长度上失效"**：
即使每 token 只差 0.023（很小），乘上 694 个 token 也会指数放大。

⛔⛔ **2026-08-18 晚就地更正（主线 MAINLINE-HANDOFF §11.4 指出，接受）** ——
原文这里写的是：

> ~~而且它会随训练自然恶化：`response_length` 从 505 涨到 694 —— **模型学会走更长的链路**
> （这是我们想要的能力），而序列级 IS 恰恰对长度最敏感 ⇒ **越成功越崩**。~~

**这句话逻辑上不成立。** [`E22`](E22-lora-never-synced.md) 已证实 **rollout 策略全程没更新过**
—— 它不可能"学会"任何东西。主线按步段实测也否掉了"每步内容变长"这个机制：

```
步段        平均步数   截断率
  1- 20      4.75    11.4%
 61- 80      5.34    16.0%
101-120      4.92    14.6%     ⇒ 步数只涨约 4%，而 response_length 涨了 38%
```

⇒ **长度增长是"抽到的题变了"（动态分池按设计降权饱和题，而饱和题恰是最短的 CHAT/HIGH/CLAR，1–2 步），
不是能力增长。** 这是**采样组成的漂移**。

✅ **仍然成立的**：序列级 IS 对长度的**指数敏感性**是数学性质，与策略学没学到无关。
🔴 **作废的**：「越成功越崩」这个**因果叙事** —— 它把一个采样组成的漂移读成了能力增长。
★ 教训：**"指标涨了"和"能力涨了"之间隔着一个"样本组成没变"的前提**，而那个前提从没验过。

```
token 级   χ² = 0.0649  ⇒  ESS/N = 1/(1+χ²) = **0.939**
序列级     χ² = 64.19   ⇒  ESS/N =            **0.015**
                            ⇒ **同一批数据、同一时刻，两种口径差 989 倍**
```

## 3.6 ★★★ 另一个更根本的原因：**一整个 epoch 只更新 109 次**

在追 IS 之前，先把最朴素的账算一遍（零 GPU，纯算术）：

```
train_batch_size      = 6      每个 fit step 收 6 条 case
ppo_mini_batch_size   = 6      ⇐ **和 batch 一样大**
ppo_epochs            = 1
⇒ 每个 fit step 的优化器更新次数 = (6/6) × 1 = **1 次**

数据集 659 条 / 每步 6 条 = 109 个 fit step
⇒ **跑完一整遍数据集，优化器一共只更新了 109 次**
```

★ **对照：正常的 LoRA 微调是几千次更新。** 我们的 B16 那两跑（60 步）**只更新了 13–15 次** ——
难怪位移只有 0.10%。

⇒ **这解释了"跑完一遍数据集能力几乎没变"里很大一部分**，而且它和 IS 是**两个独立的原因**：

```
原因① 估计量崩了     ESS 0.89→0.27，67% 的样本被截断压平 ⇒ **每次更新的有效信号变小**
原因② 更新次数太少   一个 epoch 只有 109 次           ⇒ **总位移 = 每次位移 × 次数，次数就少**
```

### 3.6.1 增加更新次数的三个旋钮（都是标准 PPO 做法，不是我们发明的）

| 旋钮 | 现在 | 改成 | 每 epoch 更新次数 | 副作用 |
|---|---|---|---|---|
| `ppo_mini_batch_size` | 6（= batch） | **2** | 109 → **327** | batch 内后面的 mini-batch 是**离策略**的 ⇒ PPO 的 clip 就是为这个设计的 |
| `ppo_epochs` | 1 | **2** | ×2 | 同上，同一批数据被用两遍，离策略程度更大 |
| `total_epochs` | 1–3 | 更多 | 线性 | 最朴素，但要更多 rollout（最贵的那部分） |

⚠️⚠️ **★ 这两个原因是耦合的，顺序不能反**：
把 `ppo_mini_batch_size` 调小 ⇒ 一批数据内策略走得更远 ⇒ `π_new/π_old` 的比值更大
⇒ **序列级 IS 会崩得更快**。
⇒ **所以必须先修 IS 的口径（§4-①），再加更新次数** —— 反过来做只会更快撞墙。

### 3.9.1 verl 自己的文档（我们用的这个框架）怎么说

来源：[verl · Mathematical Formulations of Rollout Correction Methods](https://verl.readthedocs.io/en/latest/algo/rollout_corr_math.html)

```
token 级    有 **O(T² · Δ_max) 的偏**（T = 序列长度，Δ_max = 每 token 的最大策略偏离）
            ⇒ **偏随序列长度的平方增长**
序列级      **数学上无偏**，但方差大（逐 token 比值连乘）
```

原文的适用建议是：

> "Token-level works well when rollout policy stays within the trust region of training policy."
> "When mismatch is significant, the bias becomes intolerable and **sequence-level correction is preferred**."

⇒ **和我说的正好相反**：文档说不匹配大的时候**该用序列级**。
⇒ 而且 verl 的预设方法里**序列级的变体占多数**（`decoupled_seq_is` 之类）。

### 3.9.2 ★★★ 但文档也点出了序列级的致命伤 —— **而它正打在我们身上**

> 长序列会把策略漂移**乘起来**。若每 token 差 10%（比值 1.1）：
> `10 token → 1.1^10 ≈ 2.6`（通过）　`100 token → 1.1^100 ≈ 13,780`（爆掉，被拒）
> ⇒ 文档管这个叫 **"Context Collapse"**：
> **"the model preferentially learns from short, shallow answers and rejects long chains of thought."**

**⇒ 这一句就是我们项目的核心风险**：我们的业务能力**就是走长链路**，
而序列级 IS 会**系统性地偏向短、浅的回答**。
⇒ 这和我们观测到的「67% 的序列被压到下界」是同一件事的两个说法。

### 3.9.3 ★★ 所以不是二选一 —— **verl 里有第三条路，而且我们从没打开过**

`rollout_rs`（拒绝采样）是**和 `rollout_is` 正交**的一族机制：
IS 是**加权**（`w_t · logπ · A`），RS 是**掩码**（直接把离群的 token/序列从 `response_mask` 里剔掉）。
**我们的配置里 `rollout_rs: null` —— 一直是关着的。**

| 方法 | 机制 | 对长序列 |
|---|---|---|
| `token_k1` | 每 token 比值设上下界 | 逐 token 过滤，颗粒细 |
| `seq_sum_k1` | 整条序列的比值连乘设界 | 🔴 **就是"长度陷阱"本身** |
| **`seq_mean_k1`（几何级）** | **按长度归一**：`ρ_geo = ρ(y)^(1/T)` | ✅ **专门治长度陷阱** —— 把"总漂移"（外延量）变成"每 token 平均漂移"（内涵量），10 token 和 100 token 拿到**同一个信任分** |
| `seq_mean_k3` | K3 散度（≈ 反向 KL）做探测器 | 更平滑、无符号翻转问题 |

⇒ ★★ **`seq_mean_k1`（几何级）看起来才是我们该用的那个** ——
它保留了序列级的思路，但**把长度带来的指数爆炸除掉了**。
⇒ 已排 **E20-i**（见 §4）。

## 3.10 RS 是什么（写给三个月后的自己，用最直白的话）

### 一句话：**IS 是打折，RS 是质检**

数据是 rollout（旧权重）生成的，而我们要更新的是 trainer（新权重）。两者不一致，怎么办？

```
IS（重要性采样）= **加权**
   每条数据都留着，但按"可信度"给它的梯度贡献乘一个系数 w = π_train / π_rollout
   ⇒ 像打折：可信的按原价算，不太可信的打个折

RS（拒绝采样）  = **掩码**
   不打折，只做"要 / 不要"的判断：偏得太离谱的直接从 response_mask 里剔掉
   ⇒ 像质检：超出公差的扔掉，留下的**一视同仁按原价算**
```

**两者正交，可以叠加**（verl 原文："Rejection sampling can be added to **any combination**
of operating mode and aggregation level"）——先质检掉离谱的，再给剩下的打折。

### 真正的变量是：**按什么单位判**

| 模式 | 判的单位 | 怎么判 |
|---|---|---|
| `token_k1` | 每个 token | 每 token 的比值要落在 `[下界, 上界]` 内 |
| `seq_sum_k1` | 整条序列（**连乘**） | 所有 token 的比值乘起来要落在界内 |
| **`seq_mean_k1`（几何级）** | 整条序列（**按长度开方**） | `ρ_geo = ρ(y)^(1/T)`，即**每 token 的平均漂移** |
| `seq_mean_k3` | 整条序列（K3 散度） | `K3 = mean(ρ − log ρ − 1)`，≈ 反向 KL，更平滑 |

### ★ 用我们自己的数看差别（每 token 实测差 0.023）

| 序列长度 | 连乘的比值 | 几何归一后 | 界设 `[0.5, 2]` 时 |
|---|---|---|---|
| 10 | 1.26 | 1.023 | 连乘 ✅ · 几何 ✅ |
| 50 | 3.16 | 1.023 | 🔴 **连乘被扔** · 几何 ✅ |
| 200 | 99.5 | 1.023 | 🔴 连乘被扔 · 几何 ✅ |
| **694（我们的实际长度）** | **8.6 × 10⁶** | **1.023** | 🔴 连乘被扔 · 几何 ✅ |

⇒ **同样的"每 token 偏 0.023"，连乘口径下长度一变结论就翻天；几何口径下永远是 1.023。**
⇒ 这就是 verl 文档说的「把**外延量**（总漂移）变成**内涵量**（每 token 平均漂移）」。

### ⚠️ 但它给我们**加了两个新旋钮**，而且有代价

```
rollout_rs            选哪种模式（现在是 null = 完全关闭）
rollout_rs_threshold  界设在哪 —— **这个很敏感**：
                      太紧 ⇒ 大部分数据被扔掉  太松 ⇒ 等于没开
```

⚠️⚠️ **和我们另一个问题正面冲突**：RS 是**扔数据**，而我们本来就数据紧
（每步只有 6 条 case，一个 epoch 只更新 109 次，见 §3.6）。
**扔掉 30% 就等于把本来就不多的梯度信号又砍掉三成。**
⇒ 所以 RS 在我们这里**不能当第一手段**，更像是「token 级 IS 之外的一个备选口径」。

### ⇒ 排序建议（不要一次动三个变量）

```
1. 先把 token 级 IS + 更新次数这条线跑完（batch9/batch10）—— 它们不扔数据
2. 拿到"位移 / ESS / grad_norm / 任务分"四件判据的基线
3. 再单独试几何级 RS，**只改这一个变量**，看它是不是比 token 级更好
   判据要多加一条：**被剔掉的序列是不是系统性更长**（可以直接从 rollout dump 里量）
```

## 3.11 ★★ 为什么这条线是「长程能力」的**前提**，而不是一个孤立的调参问题

> 起因：Chaoyu 2026-08-18 提的一段思考 —— 「异步除了吞吐，对训练长程能力是不是必需的？
> 但真的会把 10 小时的任务原样扔进训练吗？10 小时之后那条轨迹早就过期了。」
> **查证之后：这段判断基本成立，而且它把 E20 从"修一个估计量"抬成了"长程能力的前提"。**

### 3.11.1 查到的三条外部事实

**① 长尾确实是异步的正当理由**（不只是"想快一点"）

> "GPU idling, where resources for short trajectories remain underutilized while waiting for
> long ones to finish, which severely degrades training efficiency and **necessitates an
> asynchronous training framework**." —— [Efficient RL for Long-Horizon Tool-Use Agentic Tasks](https://arxiv.org/html/2608.10357)

**② 而"不把超长任务原样跑完"是有名字的做法：partial rollout（Kimi k1.5）**

> 设一个**固定的输出 token 预算**给每条轨迹；超出预算的部分**存进 replay buffer，
> 下一轮接着跑**。⇒ 长轨迹是**被切成段、跨多轮完成**的，不是一口气跑到底。
> —— [Kimi k1.5](https://arxiv.org/pdf/2501.12599)

**③ 伪等待/模拟环境是主流，不是我们的偷懒**

> "The engineering overhead of maintaining real-world APIs has led **LLM-based environment
> simulation to become the dominant paradigm** in agentic RL tool-use domains."
> ⚠️ 但它有记录在案的代价：幻觉、不一致、状态管理不足。
> —— [ToolVerse](https://arxiv.org/html/2607.15660)

⇒ 我们的 `latency_scale=0.01`（480 秒的工具等待压成 4.8 秒）**正是这条路**，
而且我们的沙盒是**规则式**的、不是 LLM 模拟的 ⇒ 避开了幻觉那一类问题，
代价是另一类（"沙盒 ⊂ runtime"，已记在记忆里）。

### 3.11.2 ★★★ 而这直接接上 E20：**partial rollout 一旦生效，序列级 IS 必然崩**

把②和 E20 §2 放在一起：

```
partial rollout 的定义就是   「一条轨迹的前半段用版本 k 的权重生成，后半段用版本 k+n」
⇒ 这条轨迹**天然横跨多个策略版本**
⇒ 它的逐 token 对数概率差 Δlogp 只会**比普通陈旧轨迹更大**
⇒ 而序列级 IS 是 exp(L · Δlogp̄) ——  **L 更长、Δlogp̄ 更大，指数项双重放大**
```

⇒ **结论：想训长程能力（= 想让 partial rollout 真正生效），就必须先把 IS 的口径换掉。**
**这两件事不是并列的两个待办，是前置关系。**

⚠️ **我们现在还没到那一步**（实测，B16 那跑）：
```
partial/total_partial_num = 0    partial_ratio = 0    max_partial_span = 0
⇒ `partial_rollout=True` 设了，但**一次都没触发**（E08 §8-② 早就记过）
   原因：轨迹中位十几秒 ≪ 同步周期，还没有轨迹长到需要被切
```
⇒ 所以现在的 ESS 崩塌**还只是"陈旧度"造成的**；等 partial rollout 真的开始工作，
**同样的机制会更狠**。⇒ **现在修，比等到那时候修便宜得多。**

### 3.11.3 一个必须分清的区别：**"长"是长在 token 上还是长在墙钟上**

```
长在 token 上（上下文/步数）   —— 文献里的 "long-horizon" 基本都是这个意思
                                 我们：响应从 505 涨到 694 token，**正在变长**
长在墙钟上（真实等待）         —— 我们**主动用 latency_scale 把它换掉了**
                                 实测轨迹中位 17.8 秒，不是 10 小时
```

⇒ **我们目前的"长程"是前者，不是后者。** 这也意味着：
「10 小时的任务怎么训」在我们这里**暂时不是真问题**，
而「轨迹越来越长导致序列级 IS 崩塌」**已经是真问题了**。

⇒ ★ **要报告的新指标**：`max_global_steps − min_global_steps`
（这条轨迹横跨了几个策略版本）—— 字段一直在（我们当初为了让 fully_async 不崩才补上的），
**但从没被当成指标看过**。它才是"长程 × 陈旧度"的直接度量。排成 **E20-j**。

token 级全程 ≈1.0。**方向与 §2 的机制一致。**

#### 7.6.1 ⛔ 但幅度要整个下调 —— §3.5 的 "0.449 → 1.000" 是坏基线上的数

```

干净基线（本节）   序列级 ESS **0.909 → 0.852**  vs  token 级 **0.999 → 0.999**
```
⇒ 坏基线上"陈旧度"实际是**无穷大**（rollout 策略恒为 π₀，见 [E22](E22-lora-never-synced.md)），
序列级 IS 在那种条件下当然崩得更狠。
⇒ ★ **在干净基线上，序列级 IS 更差，但没有崩。**
⇒ **"指数崩塌"这个说法要收窄成"对长度敏感、在长序列上更差"** —— 机制成立，**幅度不成立**。

#### 7.6.2 ⛔ `critic/score` 的差（+0.140 vs +0.109）**不可读**

[E08 §6.4-②](E08-async-rl.md) 刚实测：同底座三跑的 `critic/score` 末值跑间差 **0.064**，
与 RL 本身的效应（+0.101）同量级。⇒ 这里 0.031 的差**在噪声里**。
⇒ **判决只能由任务级尺子给**（队列 T5b：两臂各自与合法基线配对 + **两臂直接配对**）。
### 7.7 ★★★ R1 的判决（队列 T5b）：**估计量改善了，任务分没有** —— 一个否定结果

两臂各自与[合法基线](E24-merge-loss-on-task-score.md)配对，**并且两臂直接配对**：

⇒ 🔴 **在任务级尺子上，token 级 IS 与序列级 IS 没有可检出的差异。**
⇒ 逐题 41 好 / 33 差**近乎对称**，与噪声一致；变差集中在 `FRESH×10`。

#### 7.7.1 ⇒ E20 的主叙事要再改一次

实测     ESS 确实改善（0.999 vs 0.909→0.852，见 §7.6）

```

⇒ ★ **真正把 RL 从"跑完一个 epoch 几乎没变"变成"+0.101"的，是 [E21](E21-ddp-not-syncing.md) + [E22](E22-lora-never-synced.md) 的修复，
不是 IS 的聚合口径。** 原因① 是真的，但在这个尺度上**不是主因**。

#### 7.7.2 ✅ 这条纪律又救了一次

项目纪律原话是「**只报吞吐不报任务精度的优化不算完成**」。
这次是它的同构版本：**只报 ESS 不报任务精度的优化不算完成**。
⇒ 如果停在 §7.6 的 ESS 对照，我们会得出「token 级 IS 修好了 RL」——
**而任务尺子说：没有。**

#### 7.7.3 ⛔ 「没测出差异」不等于「没有差异」

① MDE = 0.016 ⇒ 比这更小的效应本来就看不见（compare 自己也打了这句话）
② 只跑了 60 步。⚠️ 序列级的 ESS 是**在衰减的**（0.909 → 0.852）——
   **更长的训练里它可能真的塌下去**，这条曲线只画到 60 步
③ 只在 lr 3e-5 / 一份数据 / 一个种子上测过
```

#### 7.7.4 ⇒ 默认值维持 `--rollout-is token`（但理由要改）

```
❌ 不能再说   "token 级 IS 能提升任务分"        —— 实测 +0.000
✅ 只能说     "token 级 IS 的估计量更健康（ESS ≈1.0 vs 0.85–0.91 且不衰减），
              **零吞吐代价**，而任务分在 60 步上打平"
⇒ 在"更健康且不要钱"与"更差且在衰减"之间选前者，**理由是稳健性，不是收益**。
```
### 7.8 ⛔ T6b（`mini_batch 6→3`）**结论不可归因** —— "更新次数"这个口径又崩了一次

```
r1_tokenis (mini_batch=6)  每个 dump **48 行**（6 题×8 采样）× 60 文件 = **2880 条**
e20e_mini3 (mini_batch=3)  每个 dump **24 行**（3 题×8 采样）× 60 文件 = **1440 条**
两跑的 training/global_step 都是 59
```

⇒ 🔴 **同样 60 步，`mini_batch` 减半之后训练到的序列数也减半了** —— 这**不是**"更新次数翻倍"。

#### 7.8.1 主线 §4 那条口径更正有一个**隐藏前提**

```
主线 MAINLINE-HANDOFF §4：「rollout_dumps 文件数 = 优化器更新次数」
   —— 它在 m7b 上成立，**因为那时 ppo_mini_batch_size == train_batch_size（都是 6）**
   ⇒ 每个 fit step 恰好 1 次更新 ⇒ 文件数 == 更新次数（**巧合**）
⛔ 一旦 mini_batch ≠ train_batch，这个等式**立刻不成立**
```
⇒ ★ 这是今天第 N 次同一形状：**一个判据在某个配置下"碰巧正确"，换个配置就量错了对象。**
⇒ **产物里没有任何计数器能给出真实的优化器更新次数** ——
`training/global_step`（fit step）· dump 文件数（dump 次数）· metric 记录次数（param_version）
**三个都不是它。**

#### 7.8.2 ⇒ 处置

```
⛔ T6b 的数（critic 0.7047→0.7712、grad_norm 0.176→0.224）**不作为"更新次数"的证据**
   —— 我不知道它到底更新了多少次，也不知道那 1440 条是"少训了一半"还是"dump 只记了一半"
✅ E20 原因②（一个 epoch 只更新 110 次）**仍然是一个悬而未决的问题**，不是被 T6b 回答了
⬜ 要答它，先补一个**真正的优化器步数计数器**（探针，几行）
   ✅ **已补**：`SYNCOPATE_OPT_STEP_PROBE=1`（`verl_patches._patch_opt_step_counter`）——
   直接数 `FSDPEngine.optimizer_step` 被调了几次。**这是唯一不会因配置变化而变成另一件事的口径。**
   ⇒ 队列第四段 A1/A2 用它把 `mini_batch 6 vs 3` 的真实更新次数量出来。
```

#### 7.8.3 T8b（`mini_batch 3 + lr 1e-4`）：同样不可归因，但有一条能干净读的观察

### 7.9 ★★★ defer 崩塌：总分连着盖住了**两个**真实差异（队列 T7b）

`defer` = 该延后/拒绝时是否真的这么做。这是安全相关的行为维度。

| | 该 defer | 误 defer | 与基线的任务分 |
|---|---|---|---|
| **合法基线**（RL 起点） | **97%** | 4.1% | — |
| `r1_seqis`（序列级，lr 3e-5） | **97%** | **0.1%** | +0.101 |
| `r1_tokenis`（token 级，lr 3e-5） | **83%** 🟠 | 1.3% | +0.101 |
| `e20f_lr1e4`（token 级，**lr 1e-4**） | **0%** 🔴🔴 | 0.0% | +0.063 |

#### 7.9.1 🔴🔴 `lr 1e-4` 让模型**彻底丧失拒绝能力**，而总分还是正的

```
该 defer 的比例  97% → **0%**   —— 一次都不拒绝了
而它与基线的配对差值仍然是 **+0.063（t=+3.9，显著为正）**
⇒ **总分完全盖住了一次行为塌陷。**
```
⇒ 与 §7.8.3 的"最激进的配置指标最躁动"、§7.5.1 的 `fabricated_safety_line_cap +3`、
`REJ −0.188` 连成一条一致的图景：
**在当前 reward 下，RL 会系统性地学会"不拒绝"，而 lr 越大越彻底。**
⇒ ⚠️ **这是 reward 设计的问题，不是 infra 的问题** —— 需要主线知道。

#### 7.9.2 ★★ 序列级 IS 在这条维度上**明显比 token 级好** —— §7.7 的判决要补一句

```
§7.7 的总分对照   序列级 → token 级 直接配对 **+0.000**（MDE 0.016）⇒ "没测出差异"
本节的 defer      序列级 **97%** vs token 级 **83%**  ⇒ **差 14 个点**
```
⇒ **总分打平，安全维度上序列级明显更好。**
⇒ ⛔ §7.7.4 那条「默认值维持 `--rollout-is token`」**需要重新审**：
```
支持 token   ESS 更健康（0.999 vs 0.909→0.852）且不衰减、零吞吐代价
支持 sequence 该 defer 保住 97%（token 掉到 83%）、误 defer 更低（0.1% vs 1.3%）
⇒ **这是一个真实的权衡，不是"token 全面更好"。**
⇒ 需要：① 队列 C1（序列级 120 步）看 ESS 会不会真塌
        ② 各多跑一个种子 —— 现在每臂只有 1 次
```

#### 7.9.3 ★ 方法论：**今晚第二次，总分盖住了真实差异**

```
第一次  §7.5  总分 +0.101 很漂亮，而"该 defer"从 97% 掉到 83% —— 逐题三计数才让它显形
第二次  §7.9  总分 +0.000"打平"，而 defer 差 14 个点 —— **连三计数都没让它显形**
              （41 好 / 269 没动 / 33 差，近乎对称，看起来就是噪声）
```
⇒ ★ **三计数比均值好，但它仍然是一个"打包"的判据。**
⇒ **要看的是"哪一类行为变了"，而不只是"多少题变了"。**
⇒ ⬜ 建议把 `defer` 双向率、`REJ` 类分数、`fabricated_safety_line_cap` 提成**常驻判据**，
每次评测都打 —— 它们各自是"某一类行为"的直接读数，不会被总分吸收掉。
### 7.10 ✅ 原因② 的算术是对的，**错的是实验设计**（队列 A1/A2 实测）

装上真正的优化器步数计数器（`SYNCOPATE_OPT_STEP_PROBE=1`）之后，同配置只改 `mini_batch`：

| | `mini_batch=6`（A1） | `mini_batch=3`（A2） |
|---|---|---|
| fit step 数 | 24 | 24 |
| **优化器更新次数** | 最高打到 **20** | 最高打到 **20**（**一样**） |
| dump 文件 × 每文件行数 | 24 × **48** | 24 × **24** |
| **总训练序列数** | **1152** | **576（减半）** |

⇒ 🔴 **更新次数一样，数据量减半。** `mini_batch=3` **不是**"更新次数翻倍"，
是"**每次更新只看一半数据**"。

#### 7.10.1 ⇒ 但原因② 的算术没错 —— 错的是我们怎么测它

```
每个 epoch 的更新次数 = 数据集题数 / ppo_mini_batch_size
   655 / 6 ≈ **109**   ← 与 §3.6 记的「110 次」完全对上 ✅
   655 / 3 ≈ **218**   ← mini_batch 减半，**每个 epoch 的更新次数确实翻倍**
```
⛔ **但我们的跑固定的是 `--steps`（步数），不是 epoch。**
⇒ 固定步数下，减小 `mini_batch` 只让**每步的数据减半**，更新次数不变
⇒ **这个设计根本测不到"每个 epoch 更新几次"这件事。**

#### 7.10.2 ⇒ 处置

```
✅ 原因②（一个 epoch 只更新 ~110 次）**仍然成立**，算术与实测的 fit-step 口径一致
⛔ T6b / T8b（mini_batch=3，60 步）**训练数据只有 T2/T7 的一半** ⇒ 从来不是同尺子的对照
   （幸好 §7.8 已经先一步拒绝给它们下结论）
⬜ 要真的测原因②，实验必须**固定数据量（跑满一个 epoch）而不是固定步数**，
   或者至少在"消耗了同样多的 prompt"这个点上比。
```

★ **教训**：`--steps` 这个旋钮在 `mini_batch` 变化时**换了含义** ——
它固定的是"更新多少次"，而我以为它固定的是"训练多久"。
⇒ 与今晚其它几条同族：**一个参数在配置 A 下的含义，换到配置 B 就不是同一件事。**
