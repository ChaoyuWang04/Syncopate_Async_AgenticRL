## 1 · 现象（业务侧的说法 + 我们的数）

Chaoyu 的观察：**跑完整个数据集、100 多步之后，更新量太小太小，能力几乎没有变化。**
而把 `lr` 从 `1e-5` 提到 `3e-5` 就会 ESS 崩。

我们手上正好有 `lr=3e-5` 的两次 60 步跑（B16 的两臂），把关键指标按时间取首末：

| 指标 | ref_on（13 次更新） | ref_off（15 次更新） | 说明 |
|---|---|---|---|
| `rollout_is_seq_mean` | **0.993 → 0.492** | 1.054 → 0.578 | 序列级 IS 权重的均值，理想值 1.0 |
| `rollout_is_seq_std` | 0.291 → **0.672** | 0.348 → 0.647 | 方差翻倍 |
| `rollout_is_seq_min` | 0.300 → **0.0000** | 0.177 → **0.0000** | ★ **有序列的权重被打到 0** |
| `log_ppl_diff`（每 token） | **0.00010 → 0.02308** | — | ★★ 230× |
| `response_length/mean` | 505 → **694** | — | 序列还在变长 |
| `actor/grad_norm` | 0.0018 → **0.0007** | 0.0073 → 0.0015 | ★ **梯度反而在变小** |
| **权重位移** `‖ΔW‖/‖W‖` | **0.102%** | 0.119% | 正常 LoRA 微调是 0.5–5% |

**⇒ 一句话：策略只动了 0.1%，而 rollout 与 trainer 之间的序列级权重比已经塌了一半，
梯度跟着变小 —— 模型在"越学越不敢学"。**

---

## 2 · ★★ 机制：序列级 IS 在长序列上是指数脆弱的

序列级重要性权重是逐 token 的乘积：

```
w_seq = Π_t  π_train(t) / π_rollout(t)  =  exp( Σ_t Δlogp_t )  ≈  exp( L · Δlogp̄ )
                                                                    ↑ 序列长度
```

代入我们的实测：

```
L ≈ 694 token，Δlogp̄ ≈ 0.023   ⇒   L · Δlogp̄ ≈ 16
⇒ 未截断的权重会落在 e^{±16} 这种量级上 —— 而截断阈值是 2.0
⇒ **绝大多数序列要么被顶到 2.0、要么被压到 0**，中间几乎没有
（观测到的 mean 0.49 / std 0.67 / min 0.0 正是这种两极分布）
```

★ **这不是"陈旧度有点大"，这是"尺子本身在这个长度上失效"**：
即使每 token 只差 0.023（很小），乘上 694 个 token 也会指数放大。

⇒ **而且它会随训练自然恶化**：`response_length` 从 505 涨到 694 —— 模型学会走更长的链路
（这是**我们想要**的能力），**而序列级 IS 恰恰对长度最敏感** ⇒ **越成功越崩**。

---

## 3 · 关键分解：崩塌来自陈旧度，不是来自数值失配

`log_ppl_diff`（rollout 与 trainer 的逐 token 对数似然差）的**第一个数据点是 0.0001**。
那一步 rollout 与 trainer **是同一个 param version** ⇒

```
0.0001  = vLLM 与 FSDP 的**纯数值失配地板**（不同 kernel、不同精度路径）
0.0231  = 训练到末尾时的实际差距
⇒ 230×，其中 229/230 来自「rollout 用的是旧版本权重」
```

⇒ **数值失配（TIS 那条线关心的东西）在这里不是主因**，主因是**陈旧度**。
⇒ 也就是说：**同步得越少，这个问题越严重** ——
而 B19 刚刚测出"`sync_every` 4→8 白捡 10%"。**两者直接冲突**，见 §5。

## 3.5 ★★★ 决定性证据：**verl 已经在同时记两种口径了，差 989 倍**

⛔ **先更正我自己的两处错**：
1. 我在 E08 §4.8 写过「这一跑里没有 verl 自报的 ESS 字段」——**错的**，
   字段一直在：`rollout_corr/rollout_is_eff_sample_size`。我用 CV 代理算了半天，属于没查就写。
2. 我把 `rollout_is_seq_mean` 说成"逐 token 连乘"——**也不准**。读码（`rollout_corr_helper.py:763`）：
   它是**每条序列内部先对（已截断的）权重取均值，再对 batch 取均值**。
   指数放大发生在**权重本身的计算**里（序列级模式下 log-ratio 是整条求和的），不在这个统计里。

**真正的证据在这两个字段上** —— verl **同时**记了两个口径的卡方散度
（χ² 就是 IS 权重的方差，而 `ESS/N ≈ 1/(1+χ²)`）：

`lr=3e-5`（B16，13 次更新）：

| 更新 | `chi2_seq`（序列级） | `chi2_token`（token 级） | verl 自报 `ESS/N` | 被截到下界的比例 |
|---|---|---|---|---|
| 首 | 0.14 | 0.0007 | **0.888** | 3.5% |
| 末 | **64.19** | **0.0649** | **0.270** | **67.2%** |

★★★ **把同一时刻的两个 χ² 各自换算成 ESS**：

```
token 级   χ² = 0.0649  ⇒  ESS/N = 1/(1+χ²) = **0.939**
序列级     χ² = 64.19   ⇒  ESS/N =            **0.015**
                            ⇒ **同一批数据、同一时刻，两种口径差 989 倍**
```

⇒ **这不是"预计 token 级会好一些"，这是"数据已经在那儿，token 级好 3 个数量级"。**
⇒ 观测到的 0.270 落在两者之间，是因为**截断**在硬撑
（67.2% 的序列被压到下界）——**截断把方差摁住了，代价是把 2/3 的样本变成了几乎没有梯度的样本**。
⇒ 这正好解释了另一个观测：**`grad_norm` 随步数变小**（0.0018 → 0.0007）。

`lr=1e-6`（B19/B10）对照：`chi2_seq` 全程 0.06–0.18，ESS 0.85–0.90 ——
**在这个 lr 下两种口径没有差别，因为策略几乎没动**。⇒ 再次印证 §5 的那条警告。

## 3.6 ★★★ 另一个更根本的原因：**一整个 epoch 只更新 109 次**

在追 IS 之前，先把最朴素的账算一遍（零 GPU，纯算术）：

```
train_batch_size      = 6      每个 fit step 收 6 条 case
ppo_mini_batch_size   = 6      ⇐ **和 batch 一样大**
ppo_epochs            = 1
⇒ 每个 fit step 的优化器更新次数 = (6/6) × 1 = **1 次**

数据集 659 条 / 每步 6 条 = 109 个 fit step
⇒ **跑完一整遍数据集，优化器一共只更新了 109 次**
```

★ **对照：正常的 LoRA 微调是几千次更新。** 我们的 B16 那两跑（60 步）**只更新了 13–15 次** ——
难怪位移只有 0.10%。

⇒ **这解释了"跑完一遍数据集能力几乎没变"里很大一部分**，而且它和 IS 是**两个独立的原因**：

```
原因① 估计量崩了     ESS 0.89→0.27，67% 的样本被截断压平 ⇒ **每次更新的有效信号变小**
原因② 更新次数太少   一个 epoch 只有 109 次           ⇒ **总位移 = 每次位移 × 次数，次数就少**
```

### 3.6.1 增加更新次数的三个旋钮（都是标准 PPO 做法，不是我们发明的）

| 旋钮 | 现在 | 改成 | 每 epoch 更新次数 | 副作用 |
|---|---|---|---|---|
| `ppo_mini_batch_size` | 6（= batch） | **2** | 109 → **327** | batch 内后面的 mini-batch 是**离策略**的 ⇒ PPO 的 clip 就是为这个设计的 |
| `ppo_epochs` | 1 | **2** | ×2 | 同上，同一批数据被用两遍，离策略程度更大 |
| `total_epochs` | 1–3 | 更多 | 线性 | 最朴素，但要更多 rollout（最贵的那部分） |

⚠️⚠️ **★ 这两个原因是耦合的，顺序不能反**：
把 `ppo_mini_batch_size` 调小 ⇒ 一批数据内策略走得更远 ⇒ `π_new/π_old` 的比值更大
⇒ **序列级 IS 会崩得更快**。
⇒ **所以必须先修 IS 的口径（§4-①），再加更新次数** —— 反过来做只会更快撞墙。

## 4 · 候选解法（按**对训练正确性的影响**排，不按实现难度）

| # | 做法 | 为什么可能对 | 代价 / 风险 | 判据 |
|---|---|---|---|---|
| **① 换 token 级 IS** | `rollout_is: sequence → token` | 逐 token 截断，**不在长度上指数放大**；verl 原生支持（`core_algos.py:2397` 明写 `"token"`） | 有偏（token 级 IS 不是严格的序列级修正），但**方差小得多** | ESS 不再随步数塌 + 位移能起来 + 任务分不掉 |
| **② 同步更频繁** | `sync_every 4 → 2 / 1` | 直接减小陈旧度 —— §3 说主因就是它 | **吞吐降 13–16%**（B19 的表反过来读） | 同上 |
| **③ 收紧陈旧度阈值** | `staleness_threshold 0.1 → 0.05` | 同②，但更"外科" | 吞吐降、rollout 卡更闲 | 同上 |
| ⛔ ~~提高 `rollout_is_threshold`~~ | 2.0 → 更大 | —— | **这是把温度计砸了**：权重本来就该被截断，放大阈值只是让崩塌不显示 | 不做 |

| **④ 增加优化器更新次数** | `ppo_mini_batch_size 6→2` / `ppo_epochs 1→2` | §3.6：一个 epoch 只更新 109 次 | 会加大离策略程度 ⇒ **必须在①之后做** | 位移能起来 |
| **⑤ 退回 colocate** | `--mode colocate` | **colocate 下陈旧度 = 0**（生成用的就是当前权重）⇒ 直接消掉主因 | 吞吐 33 → 55 s/步（慢 1.66×） | ★ 也是**最干净的诊断实验**，见 §4.2 |

★ **①和②③是正交的**，可以叠加；但**先单独做①**，因为它不牺牲吞吐。

### 4.2 ★ 一个 30 分钟就能做的**决定性诊断**：colocate + lr=3e-5

**陈旧度是 fully_async 特有的**：

```
colocate       生成前刚同步过权重 ⇒ rollout 用的**就是当前权重** ⇒ **陈旧度 = 0**
               （剩下的只有 vLLM↔FSDP 的数值失配那 0.0001 地板）
one_step_off   恰好落后一个版本
fully_async    落后好几个版本（受 sync_every / staleness_threshold 控制）
```

⇒ **拿 colocate 在 lr=3e-5 下跑一次，看 ESS 还塌不塌**：
```
ESS 不塌  ⇒ 崩塌确实由陈旧度造成（§3 的推断被证实）⇒ 修 IS 口径 + 控陈旧度是对的方向
ESS 还塌  ⇒ 主因不是陈旧度，而是「策略自己走得快 ⇒ π_new/π_old 本来就大」
           ⇒ 那要回去看 clip 范围、mini-batch 划分、优势归一化
```
⚠️ 这个实验**比换 token 级 IS 更早给出方向**，而且它不改任何算法 —— 只换 `--mode`。
⇒ 已排 **E20-d**，优先级与 E20-a 并列。

### 4.1 ★ 这条线该看的六个指标（每个量的是什么、够不够精）

| 指标 | 量的是什么 | 精度/口径 | 目标 |
|---|---|---|---|
| **`rollout_corr/log_ppl_diff`** | **逐 token** 的 `log π_train − log π_rollout` 均值 —— **这就是"训推不一致"本身** | 直接从两侧 logprob 求差，最干净；**第一步的值 = 纯数值失配地板** | 越小越好；**首步值要单独钉住** |
| **`rollout_corr/chi2_token`** | token 级 IS 权重的卡方散度（= 权重方差） | `ESS/N ≈ 1/(1+χ²)` | < 0.1 |
| **`rollout_corr/chi2_seq`** | 序列级 IS 权重的卡方散度 | 同上 | **现在是 64，这是病灶** |
| **`rollout_corr/rollout_is_eff_sample_size`** | **verl 自报的 ESS/N**（`1/mean(w_norm²)`） | ★ 直接用它，别自己拿 CV 代理 | **不随步数塌**；<0.3 是停止线 |
| **`rollout_corr/rollout_is_ratio_fraction_low/high`** | 被截断到上/下界的比例 | 直接计数 | 低比例；**现在 67% 被压到下界** |
| **`actor/grad_norm`** + **位移** | 信号有没有真的到达参数 | `scripts/rl_ckpt_drift.py`：`‖ΔW_eff‖/‖W_base‖` | 梯度**不缩小**、位移**起得来**（现在 0.1%，正常 LoRA 0.5–5%） |
| 任务分 | 最终的业务判据 | 冻结 EVAL 128×8 配对，MDE 0.05 | 不掉 |

★ **精度够不够**：前五个都是 verl 在训练里直接算出来的**真值**，不是采样估计，
够精。**唯一要小心的是"和谁比"**：`log_ppl_diff` 的绝对值没有意义，
**必须和第一步的地板值（0.0001）比**才知道有多少是陈旧度、多少是数值。

## 5 · ⚠️⚠️ 这条发现让**昨晚两个加速结论要打折**

**B19（`sync_every` 4→8 提速 10%）和 B10（`staleness_threshold` 0.1→0.3 提速 8%）
的 ESS 代价，是在 `lr=1e-6` 下量的**（`launch_rl` 的默认值），而 B16 用的是 `3e-5`：

```
lr=1e-6   模型几乎不动 ⇒ rollout 与 trainer 天然贴近 ⇒ ESS 看起来很好（0.87–0.92）
lr=3e-5   模型真的在动 ⇒ ESS 从 0.9 塌到 ~0.35
```

⇒ **B19/B10 测到的"ESS 没掉"，是在一个"什么都没发生"的工况下测的** ——
它们**系统性地低估了陈旧度的代价**。
⇒ ⛔ **在 E20 结案之前，不许把 `sync_every=8` 或 `staleness=0.3` 写进默认配置。**
⇒ 两条都要**在能真正学习的 lr 下重测**（排成 **B21**）。

★ **教训（新的一条）**：**在"系统什么都没发生"的工况下测出来的代价曲线，是没有代价的曲线。**
测一个"节流阀"的代价，必须让被节流的东西真的在流动。
