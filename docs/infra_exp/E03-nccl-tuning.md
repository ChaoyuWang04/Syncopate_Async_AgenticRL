# E03 · NCCL 调优：哪些旋钮真的有用

> 状态：✅ 成文（2026-08-17）。**本报告是汇总**——数据来自 E00/E02/E18 的实测，
> 这里只回答一个问题：**这台机器上，NCCL 的哪些旋钮值得拧，拧的依据是什么。**

## 0 · 结论卡片

| | |
|---|---|
| **Track / 兑现物** | **A** · 筛子②的工具层。它本身不是兑现物，但**所有多卡数字的分母都由它定** |
| **需求从哪来** | 分卡训练起不来（`Cuda failure 217`）、以及 E02 量到分片慢 6 倍 —— 两次都指向「NCCL 到底在怎么传」 |
| **答案** | **只有两个旋钮真的有用**：`NCCL_CUMEM_ENABLE=0`（必设，否则分卡起不来）和 `NCCL_PROTO=LL128`（**只在走 all_gather 的分片路径上**）。其余试过的全部无效或有害 |
| **信心** | 高。每一条都有 A/B，且「无效」的那些是**扫过范围**的（不是试一次没变就下结论） |

| **下一步** | 无。旋钮层已经问完了；**剩下的问题在上游代码里**（E18 §13 / A15） |

## 1 · 必设：`NCCL_CUMEM_ENABLE=0`

**症状**：分卡模式下 FSDP 初始化的第一次参数广播直接炸
```
transport/shm.cc:590 NCCL WARN Cuda failure 217 'peer access is not supported between these two devices'
```

**★ 根因不是「P2P 关了」**（这是第一个被自己推翻的猜想）：裸 `torchrun` 跑 NCCL all_reduce
**默认配置就能通** —— 因为那时每个进程看得见全部 4 张卡。
真正的触发条件是 **Ray 给每个 worker 只设一张卡的 `CUDA_VISIBLE_DEVICES`** ⇒
进程根本看不见对端设备，NCCL 的 SHM 传输要用的 **CUDA IPC 就开不了**。

四种配置的 A/B（⚠️ **旧机器**，见 §3 的成立范围）：

| 配置 | 能不能起来 | 2 卡 all-reduce busbw @1MB / @256MB |
|---|---|---|
| 默认 | ❌ 217 | — |
| `NCCL_P2P_DISABLE=1` | ❌ 217 | — ← **光关 P2P 没用，别照抄网上的偏方** |
| `NCCL_SHM_DISABLE=1` | ✅（退回 socket 传输） | 1.11 / 2.09 GB/s |
| **`NCCL_CUMEM_ENABLE=0`** ★ | ✅（保留 SHM，走老式 cudaMalloc 的 IPC） | **5.20 / 6.44 GB/s** ← 快 3 倍 |

⇒ 已写进 `launch_rl`：`trainer_gpus + rollout_gpus > 1` 时自动设。

## 2 · 按并行策略分设：`NCCL_PROTO`

**⚠️ 这一条的依据在 2026-08-17 被改写过两次**，最终版见 E18 §10。这里只记可操作的结论。

### 2.1 「卡间带宽」不是一个数（E00 / A8，当前机器，256 MB，algbw GB/s）

| 组 | all_reduce | all_gather | reduce_scatter | broadcast |
|---|---|---|---|---|
| 3 卡 | 18.3 | **★ 3.2** | 21.0 | 37.8 |
| 4 卡 | 17.3 | 37.9 | 30.6 | 27.7 |
| 2 卡组内 | 28.2 | 51.0 | 50.8 | 51.0 |
| 2 卡跨 socket | 22.3 | 50.2 | 39.5 | 46.4 |

⇒ **用 all_reduce 的数去推算 all_gather 的代价会错 8–12 倍**（2026-08-17 就这么错过一次）。

### 2.2 协议扫描（3 卡，algbw GB/s）

| 配置 | all_reduce | all_gather | reduce_scatter | broadcast |
|---|---|---|---|---|
| 默认 / `ALGO=Ring` / `PROTO=Simple` | 18.3 | **3.2** | 21.0 | 37.6 |
| **`PROTO=LL128`** | 12.9 (**−30%**) | **22.2 (+6.9×)** | 23.4 | 22.1 (**−41%**) |

⇒ **不能全局开。** DDP 走的正是 all_reduce ⇒ 全局开等于给主路径降速 30%。
⇒ 已写进 `launch_rl`：**只在 `fsdp_size > 1`（真分片）时自动带上**，并打判据行。

### 2.3 ⚠️ 但 LL128 是**绕过症状**，不是治本

E18 §10 刨到底：3 卡 all_gather 塌陷的根因是**每 rank 分块字节数不被 16 整除 ⇒
NCCL 的 Simple kernel 整段放弃向量化**。LL128 之所以能救，是因为它**不走那条 16 字节向量化路径**。
⇒ **正解是把分片补齐到 16 字节**（A14 实测：真实路径上 99.9% 的 all_gather 字节都错位，
而每 rank 只差 **4 个字节**）。LL128 降级为应急手段。

## 3 · 试过但**无效**的旋钮（列出来是为了别再试一遍）

| 旋钮 | 怎么试的 | 结果 |
|---|---|---|
| `NCCL_P2P_DISABLE=1` | 修 217 | 🔴 无效（根因是 CUDA IPC 开不了，见 §1） |
| `NCCL_ALGO=Ring` | 3 卡四算子 | 🔴 无变化（本来就选 RING） |
| `NCCL_PROTO=Simple` | 3 卡四算子 | 🔴 无变化（本来就选 SIMPLE，A14 复测确认） |
| `NCCL_ALGO=Tree` | all_gather | ⚠️ 不适用，该组报错（属预期） |
| **`NCCL_BUFFSIZE`** | 固定 Simple，**1 MB 扫到 32 MB** | 🔴 **无关**：3.3 → 2.8 GB/s，32 倍范围内几乎不动 |
| **NUMA 绑定** | 跨 socket 2 卡 all-reduce | 🔴 **无效**：22.23 → 22.34 GB/s，噪声内 ⇒ 那是 UPI 跳的物理代价 |
| 集合通信**次数** | 固定 4 GB，切 1/8/36/144/576 次 | 🔴 **不是次数的代价**：576 次比 1 次还快 0.7× |

★ 「无效」这一栏是本报告最有用的部分：**它们都是看起来最该试的旋钮。**

## 5 · 结论：三条可直接照做的

1. **多卡必设 `NCCL_CUMEM_ENABLE=0`**（已自动）。别用 `NCCL_P2P_DISABLE=1` 代替它。
2. **NCCL 协议按并行策略分设**（已自动）：走 all_reduce 的用默认，走 all_gather 的开 LL128。
3. **引用「卡间带宽」之前先问是哪个算子、几张卡** —— 一个数会错 12 倍。

## 6 · ⛔ 推翻了什么

> **原猜想**（本报告 2026-08-14 的草稿状态）：「NCCL 调优」是一个**旋钮问题** ——
> 把 `ALGO` / `PROTO` / `BUFFSIZE` 扫一遍就能找到最优组合。
> **实测**：真正有用的旋钮只有两个，而且第二个（LL128）是在**绕过一个上游 kernel 的缺陷**。
> **推翻后**：**这一层的问题已经问完了，剩下的在上游代码里**（E18 §13 / A15）。
> **教训**：**扫旋钮扫不出根因。** 扫描能告诉你「哪个配置更快」，
> 但「为什么这个配置更快」要另外去查 —— 而只有后者能导出正确的建议。
> 停在「开 LL128」会得到一个能用的偏方；多问一句才碰到「补 4 个字节」。
