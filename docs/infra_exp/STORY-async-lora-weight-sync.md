## 0 · 一句话

**训练在学，但学到的东西从来没有送到"负责生成数据"的那一端。
RL 的回路断了两个月，而所有指标都正常。**

---

## 1 · 现象：跑完一整遍数据集，模型几乎没变

Chaoyu 的问题很简单：「跑完一整个 epoch，能力为什么几乎没动？」

当时手上的解释链是这样的，**每一环看起来都成立**：

```
ESS 掉到 0.3 以下  ⇒ 重要性采样权重坏了 ⇒ 只能把 lr 压到 1e-5
lr 太小            ⇒ 位移只有 0.05%    ⇒ 学不动
⇒ 结论：「lr 被夹在两堵墙之间」
```

**这个结论是错的，而且错得很有说服力** —— 它有数据、有曲线、有机制。

---

## 2 · 三个真正的原因，一天里挖出来

### ① 序列级重要性采样在长序列上指数崩塌（[E20](E20-rl-not-learning.md)）

每个 token 的一点点偏差，乘上 694 个 token，就是指数级放大。verl 其实**同时记了两种口径**，只是没人把它们并排看过：同一批数据，`chi2_seq=64.19` vs `chi2_token=0.065`，**差 989 倍**。

### ② 三个 trainer rank 的梯度从没同步过（[E21](E21-ddp-not-syncing.md)）

我们用 3 张卡训练，本该把三份梯度汇总成一份。实际上**三个人各训各的**，每次更新只用了 1/3 的数据，而且三份模型**统计上完全无关**（跨 rank 相对差恒为 √2 —— 那正是两个随机方向之间的距离）。

根因在框架的接缝里：我们说"不要分片"，PyTorch 把它降级成"不分片"，**但把梯度汇总留在了一个只有一个人的小组里** —— 空操作，只打一行 `UserWarning`。

★ 它不是查出来的，是**一句顺手写的断言炸出来的**：写 ckpt 转换脚本时随手加了一句「DDP 下各 rank 的 LoRA 应该相同」。

### ③ ★ LoRA 从没被推给 rollout（[E22](E22-lora-never-synced.md)）—— 影响最大的一条

这条是本文的主角，下面单独讲。

## 3 · 主角：送货单上少了一栏

### 3.1 先理解 LoRA 训练时模型是"两块"的

```
基座 W        80 亿个数字，**冻结**，从头到尾一个字节都不改
adapter A、B  加起来 6600 万个数字，**只有它们在学**
真正的权重 = W + B×A     ← 这个乘加是**每次前向现算的**，从不存下来
```

⇒ **训练学到的东西全部在 A、B 里。**

### 3.2 异步 RL 要"送货"

```
3 张卡（trainer）  在学
1 张卡（vLLM）     在生成对话数据，也需要最新的策略
每隔 k 步把新策略推过去    ← 送货
```

### 3.3 verl 有两条送货路线，只有一条是通的

```
「同居」colocate     先送一次基座，之后每次只送 A、B          ✅ 对，而且便宜（252 MB）
「分居」训推分离      调**同一个取货函数，但只调一次、用默认参数**
                     而那个默认参数的意思是「vLLM 还没有基座，先送基座」
                     ⇒ 🔴 于是它**每次都在送那份从不改变的基座**，A、B 一次都没送过
```

**设计上这条路应该"先送基座、再送 adapter"两步走，代码里只写了第一步。**

⇒ vLLM 手里永远是训练开始那一刻的模型。trainer 越学越远，**生成数据的那一端纹丝不动**。

### 3.4 它是怎么被抓到的

排查清单上有一条红了一整天：「**权重同步的内容** —— 推给 vLLM 的到底是不是当前 trainer 的权重？」
我们验过它的**耗时**（E12 花了一整轮），**从没验过它的内容**。

判据一写就炸：

```
推出去的 q_proj 权重  ‖W‖ = 75.377708
磁盘上起点模型的同一层 ‖W‖ = 75.377708      ← **逐位相同**
4 次独立短跑、每跑 2 次同步，全部一致；含 lora_ 的张量 **0 个**
```

## 4 · ★ 最贵的一课：它制造了一整套**自洽的错误解释**

这条 bug 最坏的地方不是它错，是**那些"看起来像陈旧度"的现象一直在替它顶包**：

| 我们观察到的 | 当时的解释 | 真实解释 |
|---|---|---|
| 固定 `sync_every`，`kl` 单调涨 36× | 陈旧度累积 | π_rollout 恒为 π₀ ⇒ 量的是**累计位移** |
| ESS 沿「lr × 步数」重合，与 `sync_every` 无关 | 巧合 | ESS 是**位移**的函数，与陈旧度无关 |
| 陈旧度阈值放宽 5 倍、陈旧轨迹 6×，ESS 纹丝不动 | 阈值不敏感 | **那个旋钮没接到任何东西** |
| 权重同步"与数据量无关"（8 GB 与 132 MB 同耗时） | 固定开销主导 | **一直都是 8 GB**；"132 MB"是**算出来的** |
| 「模型学会走更长的链路 ⇒ 越成功越崩」 | 能力增长 | **冻结的策略学不会任何东西**；长度增长来自抽题组成漂移 |

⇒ **我们据此追了两个月的"陈旧度"。**
⇒ 教训不是"要更仔细"，而是：**一个自洽的解释不等于正确的解释；要去验它的前提，不是验它的推论。**

## 5 · 为什么框架自带的开关不行

verl 确实有一个开关 `lora.merge=True`：送货前先把 A、B **揉进**基座，再送整份。我们试了，**能送到，但毁掉一半的货。**

### 5.1 原因：改动量比尺子的刻度还小

```
基座每个数字      ≈ 0.023
bf16 的最小刻度    ≈ 0.000091      （bf16 只有 8 位有效数字，相对精度 0.4%）
RL 学到的改动/元素 ≈ 0.000013      ← **比刻度还小 7 倍**
```

> 你要给一栋楼**每一层**加高 1 厘米，而尺子最小刻度是 10 厘米。
> 大部分楼层纹丝不动，少数几层直接跳 10 厘米。
> **总高度大概对得上，但"哪一层高了"完全随机** —— 而 RL 学到的东西全在"哪一层"里。

**实测**（R0-b，同引擎同 dtype，只差合并这一步）：

```
adapter 本身对 logprob 的作用   中位 3.428e-02
bf16 合并造成的偏移            中位 **1.717e-02 = adapter 作用的 50%**
引擎噪声地板                   3.4e-04  ⇒ 合并损失是它的 **50×**
```

⇒ 拿它去重跑，**等于用一个新的混淆变量替换掉旧的**，而且新的和被研究对象同量级。

### 5.2 而"送 A、B 本身"没有这个问题

A、B 自己的数值是 0.01~1 的正常量级，bf16 存它们绰绰有余；乘加在推理时现做，**从不存回基座**。
⇒ **小数字单独存，就不会被大数字淹死。**

### 5.3 为什么 RL 的改动这么小 —— 这是正常的

文献里是共识：**RL 阶段的权重位移比它之前的 SFT 小得多**，而且 RL 的更新是**稀疏**的、SFT 是稠密的。
对照我们的数：SFT 一轮 0.42%、RL 一轮 0.056%（7.5 倍差），**与文献一致**。
⚠️ 我们这次**还额外小**，有两个自己的原因：一个 epoch 只更新 110 次（正常是几千次）+ E21 让每次只用 1/3 数据。

## 6 · 我们改了什么 —— 就是把送货单上缺的那一栏补上

把整条路捋完发现：**两端的能力都在，断的只是中间。**

```
trainer 侧   "只取 A、B"这个功能        ✅ 有（colocate 每次都在用）
vLLM 侧      "从张量直接装 adapter"     ✅ 有（TensorLoRARequest + add_lora，也是 colocate 在用）
             连槽位都建好了（--enable_lora / PunicaWrapperGPU），**一直空着**
🔴 中间      送货单上**没有"这是 adapter"这一栏**
             —— 收货函数 CheckpointEngineWorker.update_weights 的签名里根本没有这个参数
```

补丁（`verl_patches._patch_lora_adapter_sync`，**默认开启**）：

```
trainer 侧  自己记「基座送过了没有」⇒ 首次送基座，之后送 adapter
rollout 侧  收货时带上「这是 adapter」的标记 ⇒ 走 add_lora 那条路
```

两个刻意的设计选择：
- **两侧各自记状态、`peft_config` 在 rollout 侧就地重建** ⇒ 全程不跨进程传任何标志或 PEFT 对象。
  **少一条序列化路径，就少一个静默失败的地方。**
- 两侧都保住 `@register` 装饰器的元数据 —— E12 §262 踩过：包装丢了装饰器，组级方法直接消失。

### 6.1 为什么是打补丁而不是改 verl 源码

1. 改 `.venv` 里的文件**留不住** —— 不进 git、`pip install` 一次就没、没人能 review
2. 补丁在我们自己的代码里**能被开关、被测试、被判据看着**
3. **改动面最小** —— 只拦两个函数，其余原样放行

## 7 · 结果

```
vLLM 引擎里     list_loras() 从 [] 变成 **[123]**       ← adapter 真的进去了
送货量          8,414 MiB → **252 MiB**                 ← 33× 更小
kl（两边差距）   每次送货后回到地板 **0.00032**          ← 坏基线同位置 0.00344，差 10×
送货耗时        6.25 s → **0.974 s**（6.4×）            ← 占一步从 6.5% 掉到 0.8%
60 步 / 15 个 param_version / **0 错误**
```

⇒ **异步 RL 第一次真正跑通。**
⇒ 顺带改写了 E12：那份「权重同步 99.9% 不是传输」是在**误以为只推 132 MB、实际推 8.4 GB**
之下算的。**按真实载荷，同步就是 1 秒的事。**
⇒ 一步的构成变成 **三次前向占 88.9%** —— 吞吐线的靶子现在毫无争议是 E17/B12。

### 7.1 「推了」和「推对了」是两件事 —— 数值也验了

Chaoyu 追问得对：张量数对、大小对、`list_loras()` 非空，**都只证明"推的是 adapter"**。
而补丁里有一个**重建**环节（`peft_config` 在 rollout 侧就地重建）——
**scaling 一旦错，一切表象都正常，策略却被整体缩放。**

```
V1  两侧 peft_config 逐字段比      trainer r=32 alpha=64 scaling=2.0 ｜ rollout 同 ✅
V3  端到端：log_ppl_diff / kl      **落在同版本数值地板 ~3.4e-4** ✅
    —— 它比的就是 vLLM 算的概率 vs trainer 算的概率，同一批 token
    ⇒ scaling 错 / 模块漏装 / 值损坏，**任何一项发生它都会远离地板**
```

| | 全程 kl（15 个版本） |
|---|---|
| 坏基线 | 单调爬升到 0.00732，均值 **0.00385** |
| 修好后 | 无趋势、反复回到地板，均值 **0.00082** |

## 8 · 上游：三份文档，改哪里

⚠️ **提交由另一位负责**（正在做充分检索后提真正的 PR）。这里只记"该让他们改哪儿"。

### 8.1 E21（FSDP 梯度不同步）—— 🔻 **已知结局：不会修**

```
现象已有人报到 PyTorch 论坛，**而且真的提到了 GitHub**
维护者的态度：**FSDP1 已经进入最低限度维护**，这条不会被处理
⇒ 换 **FSDP2** 后端就不会遇到 —— 但 FSDP2 会带来**张量形态不一致**的另一批问题
⇒ **决定（Chaoyu 2026-08-18）：管线刚跑通，先不换训练后端。后面再改。**
```
⇒ 由此 **我们的补丁（拦住退化网格）是长期方案，不是临时的** ——
上游不会来修，而换后端要另付一笔账。
⇒ ⚠️ 这也意味着：**只要还在 FSDP1 上，`SYNCOPATE_FSDP_DDP_FIX` 就必须一直默认开着。**

### 8.2 E22（LoRA 没推给 rollout）—— 论点分三层，从"最不该"到"最该"

| 层 | 让他们改什么 | 论据 |
|---|---|---|
| **① 最低限度：别静默** | 检测到「LoRA + 训推分离 + `merge=False`」⇒ **直接报错** | [verl#2048](https://github.com/verl-project/verl/issues/2048) 里他们**自己写着**「LoRA 只支持同步 rollout，async 会**抛错**」，且关成 `not planned` ⇒ **他们知道不支持；早期会报错，现在这套架构里不报了** ⇒ **失败模式从"响的"退化成了"哑的"** |
| **② 正解：把管子接上** | `engine_workers.py:698` 记住"基座送过没"、别丢弃 `peft_config`；<br>`checkpoint_engine/base.py:323` 的签名加上 `peft_config`/`base_sync_done` 并转交；<br>**收货端一个字都不用改** | 我们已实现并跑通，附实测：载荷 **33×**、`param_sync` **6.4×** |
| **③ 设计建议** | 同步之后取同一层两边比一比，不一致就失败 | 成本每次两个标量；**"送过去的 ≠ 手上的"这一类失败，在任何后端下都该是硬失败** |

★ **② 要强调收益不只是"修对了"**：现在每次同步都在搬一份**完全不变的 8.4 GB 冻结基座**。

### 8.3 E23（采样截尾）—— 不是 issue，是我们自己的决策

verl 的 rollout 报 `processed_logprobs`（截尾后），而 trainer 侧的截尾器**在 verl 里是注释掉的**
（还留着 `TODO: add them back`）⇒ **一开 `top_p/top_k` 两边就不是同一个分布族。**
⇒ 我们的决定：**训练侧不截尾**，把评测对齐到训练。已把 `top_p=1.0 / top_k=-1` 显式钉死。

## 9 · 这条线留下的四条纪律

```
1. 「机制在」不等于「接上了」，「送到了」不等于「送对了」。
   ⇒ 验完耗时要再验内容：判据写成「送过去的那一份 == 手上的那一份」。

2. 一个**自洽的解释**不等于正确的解释。
   ⇒ 这条 bug 制造了四个"看起来像陈旧度"的现象，我们追了两个月。
   ⇒ 要去验它的**前提**，不是验它的推论。

3. **默认值必须是百分之百对的那个来兜底** —— 而"对"不能依赖第三方的默认值不变。
   ⇒ 由此改掉三个默认值、显式钉死两个前提、加两条守卫。

4. **撞到"框架行为不符合预期"时，先花五分钟搜上游 issue / 论坛。**
   ⇒ 今天两个基石级 bug **都能搜到**。成本几乎为零，这次能省的是两个月。
```

★ 还有一条给自己的：**这一天所有的发现，没有一个来自"读代码看着不对"** ——
全是"把两个应该相同的东西摆在一起比"比出来的。
而中途那次"探针假通过"，也是被同一个方法自己拦下的。
