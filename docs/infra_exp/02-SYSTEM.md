# Infra · 真实训练负载与范围

> 2026-09-08 用户裁定。当前队列只认 [TASKS](01-TASKS.md)，执行协议见 [EXPERIMENTS](06-EXPERIMENTS.md)。

## 1. 工作方式与交付

真实训练入口 → 观察瓶颈 → 按证据安排任务 → 解释机制/必要时最小复现 → 实际引入优化 → 原入口 A/B。速度是第一目标，模型只作计算负载；不恢复业务造数、模型选点或完整学习排期。探索允许得到“没有值得优化的瓶颈”，不预设 bug，也不要求先证明存在未解问题才能运行真实训练。

保留真实前向、反向、optimizer、rollout、权重交接和训练数据流，不用纯 tensor 或回放冒充全循环。短运行须覆盖预热与稳态、多个权重版本，按读数是否可解释决定窗口，不追求长期收敛。最低执行健康检查与优化后的正确性验收分阶段，见实验协议。

实验组交付实验、实验性改动和必要 DRAFT；正式 PR 考据、提交及跟进归 upstream。缺失功能也可成为机会：先证实际使用需求/瓶颈、当前路径不支持且没有适用替代，再设计实现和原入口 A/B。框架功能不同不自动代表 bug，不为了补齐表格移植。两个独立 Lab 的 Harness/tool runtime 不在本组施工范围。

## 2. 锁定的范围（上限，不是全排列清单）

| 层 | 允许范围 | 默认选择方式 |
|---|---|---|
| 资源 | Modal，单次真实场景最多8张B200 | 只分配保留真实并行与角色关系所需的卡；不是所有实验8卡；细则见Compute |
| RL框架 | verl、AReaL、ROLL、NeMo-RL、Miles、slime | verl优先；AReaL侧重异步；其他框架仅在真实需求或对照价值明确时选用 |
| 训练引擎 | FSDP2、Megatron | 依当前具体模型与真实入口支持选择；HF/合成模型仅作后续局部参考 |
| 推理引擎 | vLLM、SGLang、TensorRT-LLM | 前两者优先现有训练接线；TensorRT-LLM针对低精度/NVIDIA特性，但须先查实际接线 |
| 主模型 | 一个MoE + 一个dense | 优先复用Volume的Qwen3.6-35B-A3B与Qwen3.8-27B；资源盘点见Compute |
| 阶段 | SFT、RL、async、OPD，全参/LoRA | 先一个真实RL组合；其他阶段有用途再增加，不跑全链作为门槛 |

框架名单表示允许调查，不表示每个框架支持两训练引擎、三推理引擎或这两个模型的所有组合。先核对最新release/main、recipe和源码；缺失记缺失，不降回FSDP1，也不引入名单外后端。模型架构不受支持时登记缺口与替代方案，不偷偷换第三个主模型。

已有两个主模型都包含线性注意力与全注意力；dense不是“纯普通attention”。模型大小、层数、宽度也不同，跨模型比较是两个场景，不是只改MoE开关的因果实验。小模型可辅助检查接口，但不替代主模型的性能证据。

官方调查入口：[verl](https://github.com/verl-project/verl)、[AReaL](https://github.com/areal-project/AReaL)、[ROLL](https://github.com/alibaba/ROLL)、[NeMo-RL](https://github.com/NVIDIA-NeMo/RL)、[Miles](https://github.com/radixark/miles)、[slime](https://github.com/THUDM/slime)、[TensorRT-LLM](https://github.com/NVIDIA/TensorRT-LLM)。这些是导航，实际执行前仍冻结SHA和支持证据。

## 3. 合理的并行和角色摆放

优先实际会采用的状态分片、TP、EP及受支持组合，长上下文需要时考虑CP/SP，容量要求时考虑PP。TP×EP是重要候选，不预先规定所有模型都用同一切法。记录每个角色的进程组成员、world size、参数/激活/KV容量和拓扑；不同框架的EP可能与其他轴复用rank，不能机械相乘。

8卡上限包括trainer、rollout、ref/teacher的同时占卡总数；例如8卡trainer再加rollout就不是8卡实验。优先同机可行摆放；分离容器不自动同机，须记录传输路径。默认本组同时占卡总数也不超过8，独立A/B仅在总上限内并行，否则顺序交叉复验。不要为压到双卡而删除待观察的真实并行机制；也不要为了用满8卡构造不合理DDP。

按完整模型状态估容量：参数、梯度、optimizer/master states、激活、KV和通信缓冲都计入，MoE不能只按激活参数算。首次画像采用当前受支持的生产合理优化配置，不用“全关闭”制造慢基线。

## 4. 数据按负载形状选择

直接复用公开数据，冻结仓库revision/split/样本ID/许可与转换脚本，不进行业务语义清洗或教师扩写。仅做必要schema转换、采样、token化和明确记录的长度筛选；既有同内容可复用就不下载第二份。数据源及盘点见[Compute](../syncopate/05-COMPUTE.md)。

| 维度 | 需要记录/对照的形状 | 可能影响的阶段（不是预设瓶颈） |
|---|---|---|
| 输入长度 | 短/长prompt、工具schema体积、上下文增长 | prefill、激活、KV与训练attention |
| 输出长度 | 短函数参数/长回答或推理，实际token分布 | decode、rollout拖尾、训练有效token |
| 长度离散度 | 相似长度 vs 合理长短混合，P50/P90/P99/max | padding/packing、批内拖尾、rank等待 |
| 多轮深度 | 单轮 vs 多轮、每轮输入/输出/观测长度 | KV生命周期、重入调度、策略版本跨轮 |
| 前缀共享 | 共同system/tools、同prompt多响应，实际重复比例 | 训练重复计算、推理prefix cache、GRPO分组 |
| 并发与组大小 | 活跃序列数、每prompt响应数、有效batch | GPU工作量、显存、调度与组内过滤 |
| 环境等待 | 工具调用次数、观测大小、外部等待分布 | GPU空闲与async重叠；不接管Lab工具实现 |
| 奖励/过滤形状 | 组内奖励是否有差异、零优势/过滤/接受比例 | 实际更新工作量；全零更新会产生虚假的高速度 |
| 输入内容分布 | 自然文本/代码/JSON、语言与token化长度 | MoE专家负载及计算形状；有热点才细查路由 |

长上下文、长输出、多轮长程是三个维度，不能用一份长文问答代表全部。“简单function calling”也可能因工具列表很长而prefill很重。第一轮先挑少量典型切片，不穷举矩阵，实际长度需用选定tokenizer统计。

候选公开来源（2026-09-08仅查来源，尚未下载/冻结样本）：[Salesforce xLAM function-calling-60k](https://huggingface.co/datasets/Salesforce/xlam-function-calling-60k/tree/main)用于函数调用格式；[LongBench](https://github.com/THUDM/LongBench)用于长输入候选，不能冒充可交互多轮环境。长输出及多轮轨迹需另选适用公开训练数据/框架官方环境，核验许可和训练用途；使用benchmark样本只作标注清楚的infra负载，不再把同份数据成绩当独立评测。

静态工具调用文本不等于真实执行工具；需要多轮等待时使用当前框架已有环境或明确标注的观测回放。回放仅用于固定工作量定位，不替代真实训练入口；任何模拟延迟必须披露，不能制造收益。

## 5. 观察与下钻

先记录完整阶段墙钟、各rank/角色等待、有效训练/生成token、更新数、GPU利用率/显存、同步与终态积压。GPU利用率低只作信号，不等于通信慢或有优化收益；重叠区间不能相加冒充总墙钟。轻量监测常开，昂贵trace在单独诊断窗口采集。

只有画像给出占比、拖尾、内存压力或吞吐异常，才引用下方参考选择定位方法。记录触发run、影响阶段和规模、候选解释、反证、最小改动。缩小实验仍保留原场景的消息形状、调度和依赖；解释后回到原场景，比较同工作量整体时间、成本和副作用。

无明显瓶颈或收益不超过噪声，记录场景覆盖和局限后结项；不人为找错误。新的场景由真实需求和覆盖价值决定，不由“哪个组合更容易出bug”决定。
