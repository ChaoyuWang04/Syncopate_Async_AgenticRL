## 1 · 问题与预测

**问题**：verl 对全部 token 算 logprob/entropy，而 agent 负载里绝大多数 token 不进 loss。
这笔浪费有多大？大到值得自己写算子吗？

**★ 预测（2026-08-14 写死于 `TRACK-A` §4，跑之前）**：

- **P-A1**：RL 侧真实监督密度 **10–20%**。
  理由：结构上 response ≤ 1536/5120 ≈ 30%，再扣掉多轮工具返回。
- **如果 > 50%**：整道菜作废（写进报告，不删）——说明 agentic 的稀疏性没有我们以为的强。
- **P-A4**：切片对照组能拿到显存收益的**大部分**，但打不满。

## 3 · 方法

对每条轨迹，把 `token_trace` 拆成三类并按 token 数聚合：

| 类 | 定义 | 进 loss？ |
|---|---|---|
| prompt | `prompt_token_count`（system 规则书 + 工具文档 + 首轮 user） | ❌ |
| 工具返回 | segments 中 `mask==0` 的段（tool / 报错反馈等环境插入） | ❌ |
| 助手 | segments 中 `mask==1` 的段（模型自己生成） | ✅ |

**监督密度 = 助手 token / (prompt + response) token。**
两个口径都报：**聚合**（总量比，等于真实计算量占比）与**逐条**（看分布，防均值骗人）。

## 4 · 数据

### 4.1 全体聚合

| 类 | token | 占比 |
|---|---|---|
| prompt | 6,225,244 | **88.3%** |
| 工具返回 | 532,415 | 7.6% |
| **助手（进 loss）** | **293,998** | **4.2%** |
| 合计 | 7,051,657 | 100% |

**★ 监督密度（聚合） = 4.17%　⇒ 白算 95.83%**
response 内部密度 = 35.58%（即：若只切掉 prompt 能达到的密度）

### 4.5 三档改法的计算量对照

| 改法 | 参与 lm_head 的 token 占比 | lm_head 计算量 |
|---|---|---|
| 现状（verl 全算） | 100% | 1× |
| **只切掉 prompt**（最笨的改法） | 11.7% | **省 8.5×** |
| **完整按 mask 筛** | 4.17% | **省 24×** |

⇒ **大头在最笨的那一步**：切 prompt 拿 8.5×，完整方案再多 2.8×。

## 5 · 结论

1. RL 侧监督密度 **4.17%**，与 SFT 侧实测的 3.8–4.9% **同一量级**——
   ⇒ 「agent 负载的监督极稀疏」不是 SFT 独有的现象，**是这类负载的结构性特征**。
2. 这笔浪费**足够大，值得做**（远未触及「>50% 则作废」的门槛）。
3. **但先做切片对照组，不要直接写 kernel**（P-A4 的方向被数据支持）。
4. ⚠️ **省的只是最后一步投影**（hidden → 151936），不是整个前向：
   前面 36 层对 prompt 仍然要算（要它当上下文）。lm_head 约占 Qwen3-4B 参数量 10%
   ⇒ **时间收益的量级仍需 E01 拆解才能给**，本报告不给时间数字（P-A3 继续留空）。

## 6 · ⛔ 推翻了什么

> **原猜想（P-A1）**：RL 侧监督密度 **10–20%**。
> 依据是「response ≤ 1536/5120 ≈ 30%，再扣掉工具返回」。
>
> **实测**：**4.17%**（1755 条轨迹聚合，中位 3.94%，p90 5.56%）。**错了 2.5–5 倍。**
>
> **推翻后**：稀疏性比预期强得多，E11 的价值上调；且**切片对照组的收益（8.5×）
> 比预想的更接近完整方案（24×）**——最笨的改法拿走了大部分收益。
>
> **教训**：**错因是拿「配置上限」当「实际值」**——
> 用 `max_response_length=1536` 去估算，而实测 response 中位数只有 **422**（上限的 27%）。
> 模型远没有说满，而 prompt 是**打满的**（中位 3584 = 上限）。
> ⇒ 这是本项目「用推断代替测量」的一个新变种：**不是没测，是拿参数表上的数当测量值。**
> **凡是估算里出现配置项的数字，都要先问一句「实际值是多少」。**
