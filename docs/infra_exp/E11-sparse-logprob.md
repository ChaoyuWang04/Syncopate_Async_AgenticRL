## 1 · 问题与预测

**问题**：verl 对全部 token 算 logprob/entropy，而 agent 负载里绝大多数 token 不进 loss。
这笔浪费有多大？大到值得自己写算子吗？

**★ 预测（2026-08-14 写死于 `TRACK-A` §4，跑之前）**：

- **P-A1**：RL 侧真实监督密度 **10–20%**。
  理由：结构上 response ≤ 1536/5120 ≈ 30%，再扣掉多轮工具返回。
- **如果 > 50%**：整道菜作废（写进报告，不删）——说明 agentic 的稀疏性没有我们以为的强。
- **P-A4**：切片对照组能拿到显存收益的**大部分**，但打不满。

## 3 · 方法

对每条轨迹，把 `token_trace` 拆成三类并按 token 数聚合：

| 类 | 定义 | 进 loss？ |
|---|---|---|
| prompt | `prompt_token_count`（system 规则书 + 工具文档 + 首轮 user） | ❌ |
| 工具返回 | segments 中 `mask==0` 的段（tool / 报错反馈等环境插入） | ❌ |
| 助手 | segments 中 `mask==1` 的段（模型自己生成） | ✅ |

**监督密度 = 助手 token / (prompt + response) token。**
两个口径都报：**聚合**（总量比，等于真实计算量占比）与**逐条**（看分布，防均值骗人）。

## 4.6 ★★ E11-b 微基准（2026-08-14，4 卡空闲、31°C 冷机、独占）

台架：`scripts/bench_sparse_logprob.py`（预测写在文件头，跑之前钉死）。
形状取真实值：`hidden=2560 / vocab=151936 / packed=16384`（= `--max-token-len-per-gpu`）。
每档 warmup 2 次、跑 5 次取**中位**。

### 4.6.1 kernel 本身（verl 的 `linear_cross_entropy`）

| 配置 | N | 仅前向 (ms) | 加速 | 前向+反向 (ms) | 加速 | 理想线性 |
|---|---|---|---|---|---|---|
| 稠密（verl 现状） | 16384 | **65.59** | 1.00× | **271.57** | 1.00× | 1.0× |
| 切 prompt (11.7%) | 1916 | 8.19 | **8.01×** | 39.30 | **6.91×** | 8.6× |
| 按 mask 筛 (4.17%) | 683 | 3.61 | **18.15×** | 18.29 | **14.84×** | 24.0× |

⇒ **接近线性**（前向 76–93%、前反向 62–80% 的线性度）。小 N 下的偏离来自
**权重矩阵 0.778 GB 的读取是与 N 无关的固定成本**。

### 4.6.2 ★ 分母：lm_head 在整个前向里只占 4.28%

真实 Qwen3-4B、同一 packed=16384：

```
36 层主体（不含 lm_head）    1128.95 ms
整个前向（含 lm_head）      1179.44 ms
⇒ lm_head 占前向              4.28%
```
（已验证 `logits.shape = (1, 4096, 151936)`、`logits_to_keep` 默认 0 ⇒ **全量 logits 确实算了**，
不是新版 transformers 只算最后一个 token 的假象。）

按 verl 实际路径（融合 kernel）算份额：
```
仅前向     65.59 / (1128.95 + 65.59)  = 5.5%
前向+反向  271.57 / (1128.95×3 + 271.57) ≈ 7.4%   （反向按 2× 前向估）
```

### 4.6.3 显存：融合 kernel 已经把这块钱赚走了

| 配置 | N | 峰值显存 (GB) | 较稠密 |
|---|---|---|---|
| 稠密 | 16384 | **1.492** | 1.00× |
| 切 prompt | 1916 | 0.860 | 1.73× |
| 按 mask 筛 | 683 | 0.807 | 1.85× |

对照：**朴素物化 logits `[16384 × 151936]` bf16 = 4.98 GB**（前向一份、反向再一份）。
⇒ 融合 kernel 把 ~10 GB 压到 1.49 GB —— **这正是当初开 `use_fused_kernels` 拿到的 −5.0 GB**。
⇒ **E11 在这基础上只再省 0.69 GB**（占 actor 峰值 13.92 GB 的 5%）。

### 4.6.4 ★★★ 端到端收益换算（用 M7 的真实步骤分解 296.4 s）

| 步骤 | 耗时 | kernel 份额 | 按 mask 筛可省 | 只切 prompt 可省 |
|---|---|---|---|---|
| update_actor（前反向） | 98.1 s | 7.4% | 6.9% → **6.8 s** | 6.3% → 6.2 s |
| old_log_prob（纯前向） | 76.3 s | 5.5% | 5.2% → **4.0 s** | 4.8% → 3.7 s |
| ref（纯前向） | 39.2 s | 5.5% | 5.2% → **2.0 s** | 4.8% → 1.9 s |
| **合计** | 296.4 s | — | **≈ 12.8 s = 4.3%** | **≈ 11.8 s = 4.0%** |

## 5 · 结论

1. RL 侧监督密度 **4.17%**，与 SFT 侧实测的 3.8–4.9% **同一量级**——
   ⇒ 「agent 负载的监督极稀疏」不是 SFT 独有的现象，**是这类负载的结构性特征**。
2. 这笔浪费**足够大，值得做**（远未触及「>50% 则作废」的门槛）。
3. **但先做切片对照组，不要直接写 kernel**（P-A4 的方向被数据支持）。
4. ⚠️ **省的只是最后一步投影**（hidden → 151936），不是整个前向：
   前面 36 层对 prompt 仍然要算（要它当上下文）。lm_head 约占 Qwen3-4B 参数量 10%
   ⇒ **时间收益的量级仍需 E01 拆解才能给**，本报告不给时间数字（P-A3 继续留空）。

## 6 · ⛔ 推翻了什么

> **原猜想（P-A1）**：RL 侧监督密度 **10–20%**。
> 依据是「response ≤ 1536/5120 ≈ 30%，再扣掉工具返回」。
>
> **实测**：**4.17%**（1755 条轨迹聚合，中位 3.94%，p90 5.56%）。**错了 2.5–5 倍。**
>
> **推翻后**：稀疏性比预期强得多，E11 的价值上调；且**切片对照组的收益（8.5×）
> 比预想的更接近完整方案（24×）**——最笨的改法拿走了大部分收益。
>
> **教训**：**错因是拿「配置上限」当「实际值」**——
> 用 `max_response_length=1536` 去估算，而实测 response 中位数只有 **422**（上限的 27%）。
> 模型远没有说满，而 prompt 是**打满的**（中位 3584 = 上限）。
> ⇒ 这是本项目「用推断代替测量」的一个新变种：**不是没测，是拿参数表上的数当测量值。**
> **凡是估算里出现配置项的数字，都要先问一句「实际值是多少」。**

> **原猜想 ②（H1，写在 `scripts/bench_sparse_logprob.py` 文件头）**：
> lm_head+CE 约占整个前向的 **8–12%**（按参数量 389M/4.02B ≈ 9.7% 推的）。
> **实测**：**4.28%**。**低估了一半以上。**
> **推翻后**：按参数量比例估 FLOPs 份额**在这里不成立**——36 层主体里有大量
> 非 GEMM 开销（attention、norm、激活、kernel 启动），而 lm_head 是一个
> 极其规整的大 GEMM，**跑得比"按参数量分摊"应得的份额快得多**
> （实测 lm_head 段 ~252 TFLOPS vs 主体 ~104 TFLOPS）。
> **教训**：**用参数量占比去估时间占比，会系统性高估那些"规整大 GEMM"的份额。**
> 想知道一个算子占多少时间，只能测。

> **原猜想 ③（整条线的价值预期）**：E11 是 Track A 的第一道菜、"下一个要做的"。
> 依据是「96% 的 lm_head 算完被扔」+「kernel 可省 24×」。
> **实测**：kernel 层面确实省 18.15×（前向）/ 14.84×（前反向），**但端到端只有 4.3%**。
> 显存也只再省 0.69 GB（融合 kernel 已经把 ~10 GB 压到 1.49 GB，那 −5.0 GB 早就赚走了）。
> **推翻后**：**E11 降级，不写自定义 kernel。**
> 自写 vs 切片只差 **0.3 个百分点**（4.3% vs 4.0%）。
> **教训（本报告最值钱的一条）**：
> **「浪费掉的比例」和「能拿回的收益」是两个数，中间隔着一个分母。**
> 96% 被浪费是真的，但那 96% 本来就只占 4.28% 的时间 ⇒ 拿回来也只有 4%。
> ⇒ **看到一个惊人的浪费比例时，下一步不是动手，是先量它的分母。**
> 这和 ostinato §4.0（前缀缓存那条因果链）是**同一个形状的第二次**：
> 推理链越顺，越要先量分母。**区别是这次只花了半小时微基准就查清了，不是两周的 kernel。**

⇒ 已回写 `TRACK-A-hardware-kernel.md` §4 预测表。
