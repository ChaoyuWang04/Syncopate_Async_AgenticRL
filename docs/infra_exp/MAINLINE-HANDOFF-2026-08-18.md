## 2 · 🔴 E20 的核心归因很可能要重写：三条独立观测指向"陈旧度不是主因"

E20 §3 的推理是：`log_ppl_diff` 第 1 步 = 0.0001（rollout 与 trainer 同版本 ⇒ 纯数值失配地板），
末尾 0.0231 ⇒ 230×，其中 **229/230 来自陈旧度**。

**这个推理有一个洞**：**地板只在第 1 步量过一次，然后被当成常数外推。**
如果地板本身随位移增长（vLLM↔FSDP 的失配随 LoRA 增量变大），这个归因就不成立。

主线这边有三条独立观测，都指向同一个方向：

### 观测 A · 固定 k 下 `rollout_corr/kl` 单调涨了 40 倍 `[主线实测 logs/rl_v13e1.log，27 个指标周期]`

```
主线 v13-e1（lr 1e-5、sync_every=4 全程不变）
step   3    kl = 3.375e-4      ESS = 0.912
step 107    kl = 1.205e-2      ESS = 0.348          ⇒ kl 涨 36×
```
**纯 staleness 模型预测 kl 是常数**（k 由 `sync_every` 固定），而它单调上涨。

### 观测 B · 两个 lr 的跑在「lr × 步数」这条轴上大致重合 `[主线实测]`

| lr×步数 | ESS @1e-5 | ESS @3e-5 |
|---|---|---|
| 2e-4 | 0.710 | 0.728 |
| 4e-4 | 0.606 | 0.543 |
| 6e-4 | 0.483 | 0.507 |
| 1e-3 | 0.460 | 0.338 |

⇒ **ESS 更像是"累计位移"的函数，而不是"每步陈旧度"的函数。**

### 观测 C · B10 的数据自己就反着说 `[E08 §4.8]`

`staleness_threshold` 0.1→0.3→0.5，**处理过的陈旧轨迹 32→112→192（6×）**，
而 ESS 代理值 0.884→0.892→0.903（**没动，甚至略升**）。
⚠️ 成立范围：那是 12 步、`lr=1e-6` 的跑（E20 §5 已指出这个工况本身有问题）
⇒ 只能当**弱证据**，但方向一致。

### 2.1 ⇒ 两个候选解释，需要区分

```
H-陈旧度    kl 的增长来自"rollout 用的是旧版本权重"                  ← E20 现在的说法
H-位移      kl 的增长来自"策略走远了之后，vLLM 与 FSDP 的实现失配变大"
            —— 它也是位移的函数，所以在观测 A/B 上和 H-陈旧度长得一样
H-E21       ★ 第三个候选：E21 之下 rank1/2 的 π_old 已经偏离了推给 vLLM 的那一份，
            而这个偏离**随训练累积** ⇒ 它会同时解释 A 和 B
```

### 2.2 判据（两条，都很便宜，**排在重跑之前**）

| # | 动作 | 区分什么 |
|---|---|---|
| **I4** | **按 rank 分别打 `log_ppl_diff`**（一行 print） | 若 rank0 ≈ 地板而 rank1/2 明显更大 ⇒ **H-E21 成立，E20 §3 要重写**。⚠️ 这条只在**修复前**的跑上有意义 —— 若已全部换到修复后的代码，改成在**修复前后的两跑**上对比同一指标 |
| **I5** | **E20-d（colocate + lr 3e-5）顺带把地板量成一条曲线**：把 `log_ppl_diff` 的**首步与末步都记下来**，而不是只用首步 | colocate 下陈旧度恒为 0 ⇒ 整跑量到的**就是地板随位移的曲线**。地板保持 1e-4 量级 ⇒ H-陈旧度成立；地板随位移上涨 ⇒ H-位移成立 |

★ **I5 是零成本的**（E20-d 本来就要跑，只是多记两个数），但它能把 E20 的主结论钉死。

## 3 · 🟠 ESS 这把尺子本身的三个问题

### 3.1 verl 报的 ESS 是**截断之后**算的 `[主线实测源码]`

`verl/trainer/ppo/rollout_corr_helper.py:751-757`：

```python
weights_for_ess = rollout_is_weights.clamp(min=0.0, max=rollout_is_threshold)   # clamp 到 [0, 2.0]
metrics["rollout_is_eff_sample_size"] = 1.0 / masked_mean(normalized.square())
```

⇒ 高侧尾巴被砍掉 ⇒ **报出来的 ESS 系统性偏高**，而且 `fraction_high` 越大越乐观
（主线跑里它从 0.7% 涨到 12%）。E20 §3.5 的读法（"截断在硬撑"）是对的，这里补代码出处。

### 3.2 停机线 0.3 是个**比例**，隐含了一个大 batch 的假设

```
上游语境  batch ~1024 条，ESS/N=0.3  ⇒  有效 307 条  → 够用
我们      batch    48 条，ESS/N=0.3  ⇒  有效  14 条  → 快没了
```
⇒ 决定梯度质量的是 **`N × ESS/N`（绝对有效条数）**，不是比例。

### 3.3 ★ 上游原话是「换聚合方式」，被我们写成了「停机」

`00-research-question §7` 里我们自己抄下来的原文：

> verl 文档：*若 ESS < 0.3, **consider switching to geometric aggregation***

而 `06-rl-run-protocol §2` 写的是「**立即停：ESS/N < 0.3**」。
⇒ **E20-a 换成 token 级之后 ESS 直接回到 1.000、零吞吐代价 —— 这就是上游那句话的实证。**

### 3.4 ⇒ 主线会把停机线改成这样（`17 §2.4`），跑之前请确认口径一致

```
🔴 停机 · 梯度质量没了      N × ESS/N < 24 条序列          ← 绝对条数
🔴 停机 · 估计量失效（H3）  fraction_low + fraction_high > 40%
🟡 不停机，改配置           ESS/N < 0.3 ⇒ 换聚合口径（--rollout-is token）
保留：决策位熵 <0.05 / grad_norm 跳两个数量级 / reward 涨但 cap 不降
```
⚠️ 24 与 40% 是**按当前 batch 反填的工程值，是拍的** —— 第一次跑完用实测反填。

## 4 · ⚠️ 口径更正：「更新次数」被 param_version 顶替了，差 4 倍

`[主线实测，逐文件数过]`：

```
checkpoints/grpo/m7b_v13e1/rollout_dumps/      110 个文件 × 48 行  ⇒ 110 次优化器更新
checkpoints/grpo/b16_ref_on_60/rollout_dumps/   52 个文件          ⇒  52 次
checkpoints/grpo/b16_ref_off_60/rollout_dumps/  60 个文件          ⇒  60 次
```

而 **E20 §1 / §3.7 的表写的是「13 次 / 15 次更新」** —— 那是 timing 行数 = `param_version` 数
（`52/4=13`、`60/4=15`，`sync_every=4`）。**E20 内部是矛盾的**：
§3.6 算出「110 步 ⇒ 109 次更新」（**这条对**），§1/§3.7 却按 13 记。

**交叉验证**（判定 52/60 才对的依据）：

```
每次更新的位移   m7b(lr 1e-5)  0.0487% / 110 = 0.00044%
                B16 (lr 3e-5)  0.102%  /  52 = 0.00196%   ⇒ 比值 4.4 ≈ lr 比值 3   ✅
若按 13 次记     0.102% / 13   = 0.00785%                 ⇒ 比值 18×              ❌
```

⇒ **要改**：`E20 §1`、`E20 §3.7`、`E17 §5.1` 的分母。
⚠️ **E17 §5.1 的 A/B 结论不受影响**（两臂同一个错分母，比值不变），但那两个绝对值
（0.00783% / 0.00790%）要各除以 4。

★ 教训（建议写进 ONBOARDING 的坑列表）：**同一份日志里有三个都叫 step 的计数器** ——
`training/global_step`（跳 `sync_every`）· ckpt 目录名（= `param_version`）· dump 文件数（= 真正的更新次数）。
**引用"步数"之前先说清是哪一个。**

## 5 · ★★ 一条判据观念：**位移是输入，不是产出**

E20-a 实测：token 级 IS 让 ESS 从 0.449 → 1.000、`grad_norm` 趋势反转，
**但位移几乎没变（0.1071% → 0.1101%）**，E20 §3.7 据此判定"原因②独立、还没被碰过"。

**这个判定是对的，但推理要补一层**：

```
AdamW 的更新量 = lr · m̂ / (√v̂ + ε)      ← 梯度被自己的二阶矩除掉了
⇒ 梯度大 10 倍，步长几乎不变
⇒ **位移 ≈ lr × 更新次数**，与梯度好坏无关
```

⇒ ✅ **E20-a「位移没变」完全在意料之中，绝不是"没起作用"的证据。**
   估计量买到的是**方向质量**，不是**距离**。

⇒ ⚠️ **由此得到对下一批实验的硬约束**：
```
下一批把 lr 拉到 1e-4 + mini_batch 6→2，位移**必然**涨约 10 倍。
那是算术，不是证据。
⇒ 只报"位移起来了"等于什么都没证明。
⇒ 判据必须是任务级尺子（B5）——这就是 README §4 那条纪律在正确性线上的同一句话。
```

★ **判定 E20-a 有没有用的唯一有效尺子**：在两臂**位移几乎相同**（0.107% vs 0.110%）的前提下，
跑冻结 EVAL 配对，比「**显著变好 / 显著变差 / 没动**」三个计数，**不看均值**
（`16 §2.5` 的教训：M7-b 均值 +0.020 读作"没测出"，逐题拆开是 85 涨 / 70 跌 / 188 没动）。

## 6 · ⚠️ 主线侧会改变重跑数据分布的两件事

这两件不是 infra 的活，但**会影响重跑的数字**，跑之前要知道：

### 6.1 轨迹变长同时打在**两条线上** `[E20 + 主线实测 5280 条 rollout]`

```
response_length/mean   505 → 694 → 743
整体截断率             13.1%，且 11.4% → 14.6%（不降反升）
被截断轨迹的 reward    0.145   vs 未截断 0.591
```
- **infra 侧**：长度是序列级 IS 的指数底数（E20 §2「越成功越崩」）。
- **主线侧**：长度撞上 `max_response_length=1536` ⇒ 13% 的 rollout 掉进 0.145 的悬崖。

⇒ ✅ **换成 token 级 IS 之后，ESS 与长度脱钩 ⇒ 主线第一次可以安全地加长度预算。**
⇒ ⚠️ **但那会改变 reward 分布**，所以「加长度预算」和「重测基线」不能同时做，得排序。

### 6.2 位移预算正在被格式类问题吃掉 `[主线实测]`

```
multi_tool_per_step_cap   18.75%   ← 格式/协议问题
max_steps_cap             12.16%   ← 长度问题（= 6.1）
```
⇒ 前两名合计命中约 31% 的轨迹，**它们才是 GRPO 组内方差的主要来源**。
⇒ 主线会去修（不吃 GPU），但**修完 reward 分布会变** ⇒ 又一个"重跑基线要在它之后"的依赖。

### 6.3 顺带两条健康的（别去动）

```
零方差组占比 10.4%（v11 时代是 35.9%）· 组内 std 0.258   ⇒ 动态分池是有效的
logprob_coverage 全样本 = 1.0000                          ⇒ 不存在占位 logprob 污染 IS
```

## 10 · 🆕 追加（2026-08-18 下午）：**训练与评测的采样参数不一致** —— 需要 infra 定

> ⛔⛔ **2026-08-18 晚更正：本节的排除法有漏洞，读之前先看 §11。**
> infra 查出「trainer 的权重从没推给 rollout engine」之后，
> §10.2 那句「**只剩采样分布这一处差别**」**不成立** —— 至少还有两个混淆变量。
> **结论（要不要对齐采样）仍然值得答，但不能拿本节当证据。**

> 这是主线查 `multi_tool_per_step_cap` 时挖出来的，**但修法牵扯 TIS/ESS，主线不单独动。**

### 10.1 现象：同一个模型，同一套规则，命中率差到 0% vs 18.8%

```
                          训练 rollout(5280 条)   冻结评测(343 case)
multi_tool_per_step_cap          18.8%                 0.0%
```

⚠️ 评测的 `caps` 是**8 次采样的并集**。若每条 rollout 的违规率真是 18.8%，
并集应当是 `1-(1-0.188)⁸ ≈ 82%`。**实测 0%** —— 不是聚合口径能解释的。

**按纪律先怀疑判据，三条都排除了**：
- 这条 cap 在 EVAL 桶 **327/343** 条上是开着的（`active_caps` 里有）；
- 检测器 `Trajectory.multi_tool_steps()` 逻辑正常（按 step 计数）；
- ★ **训练和评测走的是同一个 `run_rollout` / 同一个 `parse_step`**
  （`verl_agent_loop.py:359`）—— 解析路径完全相同。

### 10.2 根因：只剩采样分布这一处差别

| | temperature | top_p | top_k |
|---|---|---|---|
| 评测 `eval_local.py:160-168` | 1.0 | **0.95** | **20** |
| 训练 verl `rollout.yaml` | 1.0 | **1.0** | **-1（不截）** |

`launch_rl` **没有覆盖**这三项 ⇒ 全用 verl 默认。
而 `eval_local.py:92` 的注释写着「采样参数逐项对齐 **HF 路径**」——
**他们把 eval-vLLM 对齐到了 eval-HF，但没有人把 eval 对齐到训练。**

⇒ 这是 `§10` 之前那条（**P0-1：训练 3584/1536 vs 评测 5120/2048**）的**第三例**：
**两个入口各写各的常量。** 主线已经把长度预算合并成一份（`syncopate/train/rollout_budget.py`），
采样参数**没有**合并 —— 因为它牵扯 TIS。

### 10.3 为什么它对 infra 这条线很要紧

**① 评测测的不是训练的那个策略。**
训练侧从完整分布采样，评测侧截了尾巴。而那截尾巴**几乎全是格式违规**
（截尾采样下 0%）⇒ **评测分数系统性高估了训练时的策略。**
⇒ E20 / B5 的所有任务分，都是在一个比训练**更窄**的分布上量的。

**② 它污染了 GRPO 的梯度（主线实测）。**
```
组内 std（现状）              0.2580
组内 std（把命中的剔掉再算）    0.1844
⇒ 29% 的组内方差来自这一条 cap
其中 45 个组，剔掉之后组内方差**归零** ⇒ 那些组的梯度**完全**由"这次有没有踩进采样尾巴"提供
```
⇒ 近三成的梯度信号在教「别进采样尾巴」，与任务无关。**这直接稀释了 E20 想量的东西。**

**③ 110 步下来它没有下降**（16.8% → 19.2%，无趋势）——
合理：策略梯度很难压掉一个自己在截尾下几乎不产生的行为。

### 10.4 🔴 要 infra 定的问题

**要不要把训练侧的采样对齐到 `top_p=0.95 / top_k=20`？**

```
✅ 好处  ① 直接把 18.8% 打到接近 0，回收 29% 的组内方差
        ② 消除第三个训推不一致 —— 评测终于在量训练的那个策略
🔴 代价  截尾之后「**实际采样的分布**」≠「**算 logprob 的分布**」
        ⇒ 重要性采样的比值分母不再是真实的行为策略
        ⇒ 直接影响 TIS / ESS / chi2 —— 正是 E20 那条线在量的东西
```

⚠️ **主线不动这一项**，等 infra 判断。两个具体问题：

1. **verl 算 `rollout_log_prob` 时用的是截尾后的分布还是模型的完整分布？**
   若是完整分布，那截尾会引入一个**系统性**的 IS 偏差
   —— 而且它会长得很像"陈旧度"（§2 里那三条观测的第四个候选解释）。
2. **若不对齐，另一条路是主线把违规拦在发生点**（解析器只执行第一个调用）。
   那样训练分布不变、TIS 不受影响，但**训练与评测的策略仍然不是同一个**。
   ⇒ 这条主线可以自己做，**但它解决不了 §10.3-①**。

### 10.5 主线这边已经做了什么（不影响 infra）

```
① multi_tool_per_step_cap 的 ceiling 从 **0.0** 提上来
   —— 0.0 是全项目最狠的一档（和"提示词注入"同级），
      而"没打招呼就改预算"才 0.30。一个协议格式问题被罚得狠一个量级，明显标定错了。
② 解析器层面拦截：一步多调用时只执行第一个，依赖前一个 observation 的那个调用不再被执行
   ⇒ **危害消失**（不会出现"没看到政策就改预算"），cap 退化成纯协议信号
⇒ 这两条都不改采样分布、不碰 TIS。
```

## 11 · ⛔⛔ 2026-08-18 晚：**权重从没推给 rollout engine** —— 主线这边的独立佐证与影响面

### 11.1 主线数据独立佐证了这条 bug

`rollout_corr/kl` 量的是 rollout 策略与 trainer 策略的逐 token 距离。
**如果权重同步在工作**（`sync_every=4`），它应当是**锯齿**：每次同步后回落到
「数值失配地板」（首步实测 **0.00034**），然后在 4 步内重新爬升。

主线 v13-e1 全跑 27 个 param_version 的实测：

```
0.00034 0.00028 0.00168 0.00122 0.00160 0.00208 0.00344 0.00259 0.00407
0.00429 0.00488 0.00437 0.00657 0.00843 0.00732 0.00678 0.00932 0.00694
0.00662 0.00972 0.00712 0.01165 0.00956 0.01055 0.00948 0.01096 0.01205
```

⇒ 有小幅震荡（批次间抽到的题不同），**但从第 3 个版本起再没回到过 0.0004 量级**，
末尾是首步的 **36×**。**"距离"从不重置 ⇒ rollout 侧拿的一直是同一份权重。**

### 11.2 ★ 由此得到一条零成本、永久的判据（建议写进停止条件）

```
判据：每次权重同步之后，`rollout_corr/kl` 必须回落到**首步那个数量级**（数值失配地板）。
      不回落 = 同步没生效。
```

★ 它是「两个东西应当相同」型的判据 —— 不需要阈值、不会因基线漂移失效，
而且**这条 bug 静默跑了整整两轮训练**（M7 + M7-b），没有任何指标报警。
⚠️ 附带把地板值单独钉住：首步的 `kl` / `log_ppl_diff` 就是它，**每跑必记**。

### 11.3 它一次性解释了此前四个「解释不了」的观测

| 观测 | 出处 | 现在的解释 |
|---|---|---|
| ESS 是**累计位移**的函数，不是陈旧度 k 的函数（两个 lr 的跑在 `lr×步数` 轴上重合） | 本文 §2 观测 B | π_rollout 被钉死在 π₀ ⇒ "陈旧度"就是**整跑的累计位移** |
| 固定 k 下 `kl` 单调涨 36 倍 | 本文 §2 观测 A | 同上 —— k 根本不是 1–2，是"从头到现在" |
| B10：陈旧度阈值 0.1→0.5（陈旧轨迹 6×）**不动 ESS** | 本文 §2 观测 C | 队列深度这个旋钮管不着"权重压根没推过去" |
| `log_ppl_diff` 0.0001 → 0.0231（230×），归因给陈旧度 | E20 §3 | **归因方向是对的**，但那个"陈旧度"是 bug 不是设计参数 |

⇒ ★ **好消息**：这四个谜题一次收口，指向同一个根因。
⇒ 🔴 **坏消息**：`E20` 关于「序列级 IS 在长序列上指数脆弱」的**机制**仍然成立
（数学上就是指数的），但**观测到的量级是在一个无界陈旧度下测的**
⇒ **E20 的所有数字要在修好之后重测**，「异步的代价」这条线尤其。

### 11.4 🔴 E20 §2 的「越成功越崩」这句叙事，逻辑上不成立了

> E20 §2：「`response_length` 从 505 涨到 694 —— **模型学会走更长的链路**
> （这是我们想要的能力），而序列级 IS 恰恰对长度最敏感 ⇒ **越成功越崩**。」

⚠️ **rollout 策略全程没更新过，它不可能"学会"任何东西。**

主线实测（同一跑，按步段）：

```
步段        平均步数   截断率
  1- 20      4.75    11.4%
 61- 80      5.34    16.0%
101-120      4.92    14.6%     ⇒ 步数只涨了约 4%，而 response_length 涨了 38%
```

⇒ 长度增长**不是**每步内容变长带来的，**最可能是动态分池改变了抽到的题**
（它按设计降权饱和题，而饱和题恰恰是最短的那批：CHAT/HIGH/CLAR 只有 1–2 步）。
⇒ **这是采样组成的漂移，不是能力增长。** 建议 E20 §2 整段重写。

### 11.5 ⚠️ 它把 §10 的排除法打穿了

§10.2 的推理是「三条判据都排除了 ⇒ **只剩采样分布**」。现在至少还有两个混淆变量：

```
① 训练 rollout 的策略 = models/Qwen3-4B-sft-v13-e1（**合并**模型，
   bf16 存储丢了 36% 的 SFT 增量 —— 见 §3.3 / 主线 18 §3.3）
   评测基线的策略     = models/Qwen3-4B + SFT adapter（**完整**增量）
   ⇒ 两边根本不是同一个模型
② 权重同步 bug 本身
```

⇒ **「18.8% vs 0% 全部由采样参数造成」这个结论不再成立**，它退回成"最可能的候选"。
⇒ **§10.4 那个问题（要不要对齐 `top_p/top_k`）仍然值得答**，理由也仍然成立
（评测确实测的不是训练那个策略），但**不要拿 18.8% vs 0% 当它的证据**。
⇒ 主线已排 **G-2 探针**（同 ckpt 下 `base+adapter` vs `合并权重` 的 logprob 逐 token 比）
来拆掉混淆变量①。

### 11.6 主线已做的四项改动，受影响程度

| 改动 | 影响 |
|---|---|
| 长度预算统一（3584/1536 → 5120/2048） | ✅ **不受影响** —— 证据是两个文件里的两个常量，静态 |
| `compare` 逐题三计数 | ✅ **不受影响** —— 纯尺子；引用的具体数字只当"跑通了"的例子 |

| 一步多调用：拦在发生点 + ceiling 0.0→0.50 | ✅ **两项修法都仍然对**（0.0 比"越权花钱"0.30 狠一个量级，是刻度自洽性问题）<br>🔴 **根因归属要降级**（§11.5）<br>🔴 「110 步命中率不下降 ⇒ 罚不掉」这条**解释作废** —— 真正的原因是 rollout 策略压根没变<br>🟡 「29% 的组内方差」在冻结策略上测的，**要重测** |
