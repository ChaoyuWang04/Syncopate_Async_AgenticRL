**2026-08-16 一次独立验收审计的两条结论。**

## ① 空门槛的正确读法是「无法判定」，不是「通过」

M7 §31.2 的六条毕业条件里，**三条的门槛写的是【待定】，一条的尺子根本不存在**：

```
premature_decision 命中率 < 【待定】     门槛空着
目标意图 reward mean ≥ 【待定】          门槛空着
E2E 成功率按读/写分桶均达标              ★ 全项目没有任何代码按读/写分过桶
D1 通用能力未退化                        没有域外数据，测不了
```

而交接文档把 M7 记成「✅ 已验收」，**这句话被下游引用了两天**。

**Why**：一条判据"看起来完整"（有名字、有方向、有复选框）就很容易被当成已满足，
**尤其当它旁边几条是真的绿的时候**。同理：M6 是 6 条过 3 条，记成了"条件毕业"。

**How to apply**：
1. **门槛空着 = 这一条不算数。** 宣布验收之前，先数有几条是可判定的。
2. **门槛写成「相对基线 + 配对 MDE」，不写绝对数。** 各意图基线差很远
   （SCALE 0.637 vs CRE 0.889），一个绝对数对谁都不对；而**低于 MDE 的"提升"
   尺子分辨不出来，写进门槛等于允许拿噪声毕业**（配对 MDE = 0.013，见
   [[rl-step-size-is-lr-times-steps]]）。
3. **指标只有名字、没有量它的代码 ⇒ 要么补尺子，要么显式划掉**，不能挂在毕业条件里。

## ② 补上读/写分桶尺子，第一次量就看见了一直被盖住的东西

```
                  n     reward   满分成功率   cap/次
只读             86     0.909       69%       0.08
含写动作        112     0.722    ★ 20%        0.40      ← cap 命中是读的 5 倍
读−写 差值                +0.187
```

**M7 那个「平均 reward 0.803」是被读操作撑起来的。真正花钱的那一桶，成功率只有 20%。**

设计文档 §21 早就写着「读 ⊥ 写不可合并，混在一起大量读操作会稀释掉写操作的风险」——
**它一直没被看见，不是没人想到，是没有尺子。**

⇒ 尺子在 `eval_local._report_read_write`；分组依据是 gold 里有没有 `kind="write"` 的工具
（取自工具注册表，不另立一套清单）。
⇒ `eval_local --from-audit <审计> --batch <当初那个 batch>` 可以对历史审计重出报告，
**补了新尺子不必重跑几小时 GPU**。⚠️ 必须用那份审计当初跑的 batch，
拿另一版 gold 分组，数看起来正常但它谁也不是。

## ★★ 2026-08-17 第三条：**判据太宽 ⇒ 它会为错误的理由"通过"**

M9 那条「C 档动作必须走审批」的测试，第一版判据是
`count(approval_cases) == 1`。后来给 worker 接上检索，这条测试**当场变绿了** ——
不是因为 C 档修好了，是因为「检索为空」触发了**另一个**降级，照样开出一张单。

⇒ **判据要指名道姓**：改成断言审批单的 `trigger_reason` 里含 `tier_c`，立刻又红了。

★ 这条比「门槛空着」更隐蔽：门槛空着至少一眼看得出没填；
**判据写满了、还真的在跑、还变绿了 —— 只是它量的不是你以为的那件事。**
⚠️ 用 `xfail(strict=True)` 钉缺口时尤其危险：**xfail 会把"为错误理由失败/通过"一起吞掉。**
⇒ 配套动作：每次改完实现，用 `pytest --runxfail` 看一眼**它到底停在哪一行**。

## ★★ 2026-08-17 第四、五条：同一族的两个新变种（都在半天内撞到）

**④「式子对 ≠ 这次跑的是这个式子」。** 我读了 verl 基类 `separation/ray_trainer.py` 的保存判据
（`global_steps % save_freq`）就下了结论，**而 fully_async 覆盖了它**
（`current_param_version % save_freq`，param_version 每次权重同步才 +1）。
结论碰巧对（110 步只存一次），**机制全错**。
⇒ **读到一个判据式子，先查子类有没有覆盖它**；判据是**这次真正加载的那条路径**（看日志里的 import），
不是记忆里的实现。同族：归属 16 字节对齐时我点了 FSDP2 的函数，而我们跑的是 FSDP1。

**⑤「判据为空时，先怀疑解析器，再怀疑现象」。** 分析 NCCL 日志的正则只认数字格式
（`Algo 1 proto 2`），而这台打的是名字（`Algo RING proto SIMPLE`）⇒ 「协议选择」整列空白，
**我差点写下「本次没拿到协议选择」当成一条观测**。
同族：nsys 的 `deviceId` 全是 0（Ray 给每个 worker 只设一张卡 ⇒ 进程眼里自己那张就是 0），
按它聚合会算出「GPU0 忙 97%」这种假数 —— **字段名对，含义却是进程局部的**。

⇒ 合起来一句：**判据失效有三种长相 —— 空着、太宽、以及"看起来在量但量错了对象"。
第三种最贵，因为它会产出一个具体的数字。**

## ★★★ 2026-08-17 第六条：**均值是相抵之后的残差 —— 它会让真实的行为迁移完全隐形**

M7-b 的 RL 跑完，冻结 EVAL 上配对差值 **+0.020 = MDE 0.020**，读法是「没测出差异」。
按老习惯，这一跑会被记成"模型基本没变"。**逐题拆开之后完全不是那回事：**

```
显著变好(>+0.05)   85 条
显著变差(<-0.05)   70 条
基本没动           188 条
```

**85 涨和 70 跌相抵，剩下的残差才是那个 +0.020。** 模型动得很厉害，只是净额约等于零。

再往下拆，方向非常清楚 —— **它在学「什么时候该 defer」，但还没稳定**：

```
该 defer 时 defer 了      89% → 61%     🔴 退了 28 个点
不该 defer 却 defer 了    3.1% → 0.4%   ✅
含写动作那一桶 reward     0.694 → 0.751 ✅ 满分率 13%→18%、cap/次 0.45→0.34
```

**Why**：均值把双向变化压成一个数，而 RL 早期恰恰是**双向的** —— 它同时在对一部分题变好、
对另一部分题变坏。只看均值，会把"正在学、还没学稳"误读成"没在学"，
于是去调 lr / 加步数，**而真正该看的是那 70 条为什么退**。

**How to apply**：
- **任何 A/B 比较，均值旁边必须放三个计数**：显著变好 / 显著变差 / 没动。
  一行代码的事，`eval_local` 的配对差值已经逐题算出来了，只是没打印。
- 三个数里 **"变差"那一列非零就不能说"没变化"** —— 要去看变差的是哪一类题
  （M7-b 里变好前四和变差前二全是 FRESH，一眼就看出焦点在哪）。
- 同族尺子一起看：**分桶**（[[blank-thresholds-are-not-passes]] ②）拆的是"哪一类题"，
  **逐题计数**拆的是"同一类题内部有没有对冲"。两把尺子少一把都会漏。
- ⚠️ 这条和 [[rl-step-size-is-lr-times-steps]] 的位移尺子是**互补而非冗余**：
  位移量的是"权重动了多少"，逐题计数量的是"行为动了多少"。
  M7-b 里位移只有 0.0487%，行为却动了 155 条 —— **小位移不蕴含小行为变化**。

## ★★★ 2026-08-18 第七、八条：判据自己的两种新失效（一天里各撞一次）

**⑦「判据太宽 ⇒ 它会制造假警报，而假警报会训练人忽略这条判据 —— 那比没有判据更糟。」**

建作废数字登记表时，我把 `18.8%` 和 `13.1%` 当成标记串去全库扫，当场误伤两处：
`18.8%` 在 infra 文档里指的是**权重同步占步 18.8%**（一个**时间**测量，**仍然有效**），
`13.1%` 在 `learning-notes/05` 里是工具调用频次表。
⇒ **加任何"黑名单型"判据之前，先 `grep -rl` 确认它只命中你想要的那处。**
★ 这条和「门槛太宽会为错误的理由通过」是**镜像**：那条是漏放，这条是错杀，
  而错杀的长期代价更大 —— 人会开始忽略这条判据，等于把它变成装饰品。

**⑧「匹配不上时，宁可报"没有"，也不要猜。」**

写 SFT 选点工具时，用**文件名模糊包含**去找审计（`_epoch1.` in name），
给 `checkpoints/sft/v13/epoch1` 匹配到了 **v3 时代**的 `M1_ctrl_epoch1.json`，
打出「决策位熵 0.483 / 有梯度 44」——**一组看起来完全合理、其实是另一个模型的数字**。
⇒ 改成只认审计 label 里出现该候选的**相对路径**，认不出返回 `None`。
★ 这是本文 ④「式子对 ≠ 这次跑的是这个式子」的近亲：
  **数据源对 ≠ 这条数据源说的是这个对象。** 而它同样会产出一个具体的数字。

⇒ 合起来：**判据失效现在有五种长相** —— 空着 · 太宽（漏放）· 太宽（错杀）·
  看起来在量但量错了对象 · **匹配到了另一个对象**。
  ★ 后三种都会**产出一个具体的数字**，这是它们比"空着"贵得多的原因。

## ★★★ 2026-08-19 第九条：**判据太宽会误伤，而且我一天里犯了四次**

前面第三条记的是「太宽 ⇒ 为错误的理由**通过**」。这次是它的另一半：
**太宽 ⇒ 为错误的理由**报红**，而假警报会训练人忽略这条判据。**

一天里四次，全是我自己写判据时犯的：

```
① "不许有脚本传 --rollout-is"     误伤 24 处：其中一处是 say 的**提示文本**，
                                   23 处是 infra 的 A/B 实验脚本（**扫这个参数正是它们的用途**）
② "全部 runtime 工具必须是协程"    用 callable() 筛 ⇒ 把两个**异常类**也算进来了
③ "data_maturity 不再硬编码"       grep `"mature"` 命中了**解释修复的注释**
④ 跨文档 §引用检查                 正则太严 ⇒ 30 处可疑里大半是假阳性
```

⇒ **共同点：判据命中的对象比我想的宽。** 而每一次的表现都是"报了个红，而且看起来有道理"。

### ★ 可操作的两条

```
① 黑名单型判据落地**之前**先跑一遍，看它命中了什么 —— 不要写完就提交
   （守则③已经写了"先 grep -rl 确认"，而我四次都是**跑了才发现**）
② 判据要**分清"该管的范围"**：
   · 注释 / 字符串 / 文档里的提及  ≠  真正的代码行为
   · 另一条线的文件               ⇒ 只报告，不判红（交界）
   · 异常类 / 常量                ≠  函数
```

### ⚠️ 而假警报的代价是**复利**的

判据红了但"其实没事"发生几次之后，人就会开始默认它是噪声 ——
**下次它抓到真问题时也会被跳过。** 那时候它比没有判据更糟：
它占了"这件事有人在看"的位置，却不再提供保护。
